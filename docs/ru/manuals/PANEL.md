# Веб-панель qeli — установка и использование

> **Статус документации:** текущая ветка разработки **0.8.3**; планируемый full-IPv6 релиз **0.8.3**;
> версия пакетов в этом руководстве **0.8.3**.
> Фактическую версию установленного бинарника показывает `qeli --version`.
> Готовые файлы и статус публикации нужной версии — в [GitHub Releases](https://github.com/litvinovtd/qeli/releases).
> Ссылки на файлы этой версии работают после её публикации.

Встроенная админка демона: профили, пользователи/группы, живые клиенты,
identity-ключи и выдача `qeli://`-ссылок/QR. Запускается **внутри** `qeli server`
(процесс-супервизор), управляет данными через тот же конфиг/users-файл и
control-сокет.

- **Self-contained:** CSS/JS/шрифты встроены в бинарь и отдаются с `/assets/*` —
  **никаких CDN в рантайме**, панель работает на сервере без исходящего интернета.
- **Стек:** `axum` + `alpine.js`; REST `/api/*`; сессия — HMAC-кука. Ключ подписи выводится через
  HKDF из отдельного случайного секрета, хеша admin-пароля и поколения
  отзыва сессий; отдельные сессии на сервере не хранятся.
- **Языки:** переключатель RU/EN внизу сайдбара (по умолчанию English; выбор
  запоминается в браузере).

CSS на Tailwind 4 рассчитан на Safari 16.4+, Chrome/Chromium 111+
и Firefox 128+. Это минимальные требования upstream, а не подтверждение
проверки каждой версии браузера. См.
[руководство по совместимости](https://tailwindcss.com/docs/upgrade-guide).

> Справочник всех ключей `[web]` — [CONFIG.md](CONFIG.md#веб-панель-web). Здесь —
> как поднять и как пользоваться.


Фоновый опрос при ошибках увеличивает интервал вдвое до 60 секунд, после успешного
ответа возвращается к исходной частоте. Скрытые вкладки не опрашивают сервер;
ручное обновление доступно сразу. Чтение API ограничено 15 секундами.

При выдаче ссылки/QR выключенные профили помечены «Выключен». По умолчанию выбирается
первый включённый профиль; выключенный можно выбрать для подготовки конфигурации,
но подключение заработает после его включения и рестарта сервера.

## 1. Установка / включение

Панель настраивается секцией `[web]` серверного конфига. Минимум для доступа
**по внешнему IP** (безопасно):

```ini
[web]
enabled = true
# или конкретный внешний IP (для self-signed SAN лучше IP)
bind = 0.0.0.0
port = 8080
username = admin
# ОБЯЗАТЕЛЕН на ЛЮБОМ bind, включая loopback — пусто = панель не стартует
password_hash = $argon2id$v=19$m=...$...
# встроенный HTTPS (rustls); cert self-signed авто. Заходить по https://, не http://
tls = true
# (опц.) белый список источников. Отсутствует, пусто или "" = любой источник.
# allowed_ips = 203.0.113.4, 10.0.0.0/8
# (опц.) хост для share-ссылок; ещё и разрешённый CSRF-origin
public_host = vpn.example.com
# (опц.) доп. браузерные origin'ы для доступа по LAN/домену/прокси без него панель грузится, но POST (логин/сохранения) отдаёт 403
# allowed_origins = 192.168.88.8:8080
```

После рестарта сервера панель доступна на **`https://<bind>:<port>`**.

### Admin-пароль (обязателен)

Сервер хранит только **argon2id-хеш** (`web.password_hash`), не открытый пароль.
**Fail-closed:** с пустым `password_hash` панель **не стартует ни на каком bind,
включая loopback** (в лог — ошибка; VPN `:443` при этом работает — это отдельный
процесс). До 0.7.12 loopback был исключением и отдавал ОТКРЫТУЮ панель — то есть
полный админ-доступ любому локальному процессу и любому SSRF на хосте; если это
действительно нужно, теперь это запрашивается явно через `web.insecure_no_auth = true`,
и сервер предупреждает об этом при старте. Способы задать хеш:

- **CLI `qeli set-web-password` (проще всего, для свежей установки без доступа в
  панель)** — генерирует/хеширует пароль, прописывает `web.username`/`password_hash`
  прямо в конфиг (комментарии сохраняются) и включает панель:
  ```bash
  qeli set-web-password                    # случайный пароль, печатается один раз
  qeli set-web-password --password 'PASS'  # свой пароль
  qeli set-web-password --username admin --password 'PASS' --no-enable   # только креды
  qeli set-web-password --config /etc/qeli/server.conf                   # путь по умолчанию
  ```
  После — `systemctl restart qeli` (пароль виден только в момент генерации).
- **В самой панели:** Config → Web → «Set admin password» (вводите пароль →
  хешируется в поле → Save) — когда доступ уже есть и нужно сменить пароль.
  Сохранение `[web]`-настроек через панель (админ-пароль/юзер, IP-allowlist, CSRF-origins)
  применяется **сразу, без рестарта**, если ответ содержит `web_settings_applied: true` —
  смена пароля тут же инвалидирует текущую сессию. При `false` INI сохранён, но прежние
  настройки панели продолжают действовать; ответ предупреждает об этом.
  Socket-поля (`bind`/`port`/`tls`) по-прежнему требуют полного рестарта. (CLI `set-web-password`
  выше — отдельный процесс, поэтому ему рестарт нужен.)
- **CLI `argon2` (вручную):** `printf '%s' 'ВАШ_ПАРОЛЬ' | argon2 "$(head -c12 /dev/urandom|base64)" -id -t 3 -m 15 -p 1 -e`
- **Через API** (только если панель уже доступна — то есть пароль уже задан либо стоит
  `web.insecure_no_auth = true`; на свежей установке без пароля панель не запущена,
  используйте `qeli set-web-password` выше):
  `curl -s localhost:8080/api/hash-password -H 'Content-Type: application/json' -d '{"password":"..."}'`

### TLS (`tls = true`)

Панель сама отдаёт HTTPS (rustls, провайдер `ring`) — реверс-прокси не нужен.

- **Self-signed (по умолчанию):** при пустых `tls_cert`/`tls_key` сертификат
  генерируется при старте и сохраняется в `/etc/qeli/web-tls-cert.pem` +
  `/etc/qeli/web-tls-key.pem` (ключ `0600`), SAN включает `bind`-адрес/IP,
  `localhost`, `127.0.0.1`. Браузер предупредит один раз (трафик шифруется) —
  можно принять/запинить.
- **Свой сертификат** (без предупреждений, нужен домен):
  ```ini
  tls = true
  tls_cert = /etc/letsencrypt/live/vpn.example.com/fullchain.pem
  tls_key  = /etc/letsencrypt/live/vpn.example.com/privkey.pem
  ```
- PEM-файлы должны быть обычными файлами размером не более 4 МиБ каждый;
  симлинки на обычные файлы (в том числе Let's Encrypt) поддерживаются. FIFO
  и другие спецфайлы отклоняются без ожидания. Если из автосозданной пары
  остался только сертификат или только ключ, панель не запускает HTTPS и не
  перезаписывает оставшийся файл: восстановите второй из backup либо удалите
  **оба** файла для осознанной генерации новой пары.
  `qeli check-config` проверяет существующую пару тем же TLS-загрузчиком. Если
  автопара ещё не создана, команда допускает первый запуск и не создаёт файлы.
  Для явно указанных TLS-путей серверный INI должен быть доверенным: обычный файл
  владельца root/эффективного UID, без записи для группы и остальных, без symlink.
  При TLS-файлах вне `/etc/qeli` панельный Backup вернёт HTTP 409: сделайте
  отдельную резервную копию внешней пары.
- При `tls = true` к сессионной куке автоматически добавляется `Secure`.

> Альтернатива публикации: оставить `bind = 127.0.0.1`, `tls = false` и ходить в
> панель **через SSH-туннель** (`ssh -L 8080:127.0.0.1:8080 root@server`). Тогда
> TLS не нужен — трафик шифрует SSH.

### IP-allowlist (`allowed_ips`)

Самый сильный барьер для публичного bind: список CIDR/одиночных IP, которым
разрешён доступ; остальным — `403`. Редактируется в Config → Web → «Source-IP
allowlist». **Не забудьте включить свой текущий IP**, иначе сами получите `403`.

**Как разрешить доступ отовсюду.** Выберите один из трёх вариантов ниже. Они равнозначны — парсер конфига
снимает окружающие кавычки, поэтому `""` это просто явный способ написать «пусто»:

```ini
# allowed_ips = …    ; ключа нет вовсе
# ключ есть, значение пустое
allowed_ips =
# то же самое, что строка выше
allowed_ips = ""
```

Без записей IP-фильтра нет, и защита держится на TLS + пароле + rate-limit.

> **Голый `403` при простом ОТКРЫТИИ панели — это всегда allowlist.** Он применяется ко
> всем маршрутам (страницы, ассеты, API) и отдаёт 403 с ПУСТЫМ телом. CSRF так сделать не
> может: он пропускает `GET`/`HEAD`/`OPTIONS`, а его 403 несёт текстовое тело с названием
> отклонённого origin.
>
> **Готча — дубликаты ключа складываются.** ВСЕ строки `allowed_ips` в `[web]` сливаются в
> ОДИН список (а не «побеждает последняя»). Забытая выше строка `allowed_ips = 1.2.3.4`
> держит фильтр включённым, даже если та строка, которую вы правите, выглядит пустой. Если
> 403 необъясним — `grep -n allowed_ips /etc/qeli/server.conf` и проверьте лог старта:
> `Web panel source-IP allowlist active (N entries)`; нет такой строки = фильтра нет.
> Отклонённый запрос пишется как `panel: blocked request from <ip> (not in web.allowed_ips)`.

### Доступ по LAN-IP, домену или через reverse-proxy (CSRF-origin'ы)

Чтобы вредоносная страница не могла заставить залогиненного админа отправить запрос,
панель принимает **изменяющие** запросы (POST логина и любые сохранения) только если
браузерный `Origin`/`Referer` совпадает с разрешённым хостом. **По умолчанию разрешены:**
адрес `bind` и loopback (`127.0.0.1` / `localhost` / `[::1]`).

Поэтому если открыть панель по **LAN-IP, домену или за reverse-proxy** (что угодно, кроме
loopback) — страница грузится (`GET /login` → `200`), но `POST /login` и любые сохранения
отдают **`403`**. Тело 403 теперь называет отклонённый origin и подсказывает, что именно
добавить; в логе также: `CSRF: rejected POST … (origin/referer=…)`.

Чинится — добавь этот адрес в разрешённые origin'ы в `[web]`, затем `systemctl restart qeli`:

```ini
[web]
# твой LAN-IP / домен — host или host:port
allowed_origins = 192.168.88.8:8080
# public_host тоже принимается как origin; хост без порта совпадает и с портом bind
```

Либо, без правки конфига, открывай панель через SSH-туннель на loopback (он разрешён
всегда): `ssh -L 8080:127.0.0.1:8080 root@<сервер>` → открыть `https://127.0.0.1:8080` и
принять ожидаемое предупреждение о hostname у созданного установщиком сертификата. `http://`
используется только если `web.tls = false` был задан явно.

**За reverse-proxy на сабпасе** (например `https://host/qeli/`, а не в корне домена): задай
`base_path = /qeli` в `[web]` и проксируй префикс **без среза**. Панель переустановит все свои
ассеты, API-вызовы и редиректы под префикс и учтёт `X-Forwarded-Prefix`. Полный пример nginx —
см. «Reverse-proxy sub-path» в [CONFIG.md](CONFIG.md).

### Что ещё обеспечивает безопасность (автоматически)

- **Security-заголовки** на всех ответах: HSTS (при `tls`), `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy`, CSP (same-origin).
- **CSRF** — изменяющие запросы (POST логина и любые сохранения `/api/*`) проверяются по
  `Origin`/`Referer`; принимаются только `bind`, loopback и заданные origin'ы (см.
  «Доступ по LAN-IP, домену или через reverse-proxy» выше).
- **Анти-брутфорс** — жёсткая блокировка по source-IP + tarpit по username (чужой
  логин нельзя залочить перебором имени).
- **Сессия** — кука `HttpOnly; SameSite=Strict; Path=/` (+`Secure` при TLS),
  токен HMAC-подписан ключом, выведенным из отдельного секрета, хеша пароля
  и поколения отзыва. Смена пароля или отзыв всех сессий делает прежние токены
  недействительными. При `web.persist_session_key = true` (по умолчанию) секрет
  хранится в файле с правами `0600`; при отключении или недоступности файла
  используется секрет процесса, поэтому перезапуск завершает сессии.

## 2. Использование

### Вход
`https://<bind>:<port>` → логин `admin` + пароль. Внизу сайдбара (и в углу
страницы входа) — **выпадающий список языка** (RU/EN).

### Dashboard
- **Быстрый старт** — плитки режимов (REALITY / HTTPS-fake-tls / Obfuscated /
  QUIC): один клик создаёт готовый профиль (TUN/NAT/DNS/пул/обфускация), применяет
  и перезапускает сервер. Пресеты несут боевую **stealth-постуру** — Poisson
  flow-shaping вместо ~15-с heartbeat-маяка, MTU 1400 и stream bonding на TCP-режимах.
  **Mobile / LTE:** большой пост-квантовый хендшейк может попасть в чёрную дыру за
  path MTU < 1500; на сервере накати OS-тюнинг (внешний MSS-кламп + BBR / PMTU
  probing) — см. [CONFIG.md](CONFIG.md) → «sysctl + iptables». Установщик
  `install-qeli-server.sh` делает это автоматически.
- **Живые клиенты** — кто подключён (профиль, IP, peer, сборка клиента, аптайм,
  трафик, лимит), действия **Kick** и **Set bandwidth**. Фильтр по профилю,
  автообновление 10с.
  Колонка **Client** показывает версию и платформу, которые сессия сообщает по
  туннелю (например `0.7.14 android`) — быстрый ответ на вопрос «кому ещё
  обновляться». Прочерк означает, что клиент их не сообщает: все сборки, вышедшие
  до этой возможности, и GUI-клиенты, пока в них не появится этот кадр. Значение **сообщает сам клиент,
  и сервер его не проверяет** — любой прошедший аутентификацию пир может написать
  что угодно, поэтому это метка, а не доказательство того, что реально запущено.

### Метрики хоста и туннеля на Dashboard
Две карточки вверху страницы обновляются **раз в 2 с** (при скрытой вкладке поллинг
останавливается и возобновляется при возврате). Данные готовит семплер супервизора: он
снимает дешёвые счётчики `/proc` и агрегаты воркера **раз в секунду** и держит кольцевой
буфер на 300 точек (= 5 минут). Эндпоинты — `/api/system` (последний снимок) и
`/api/metrics` (история для графика); на запрос `/proc` не парсится.

- **Host load** — CPU % (и число ядер), RAM % плюс абсолютные «использовано / всего»,
  load average (1/5/15), процент занятого места на `/`, строка **qeli proc** (pid
  воркера дата-плейна, его CPU % в шкале top, где 100% — одно полностью занятое ядро, и RSS),
  **WAN net** — ↓/↑ Мбит/с по физическим интерфейсам хоста (`lo`, `vpn*`, `tun*` исключены,
  чтобы туннель не считался дважды), **conns · uptime** — число установленных TCP-сокетов
  и UDP-сокетов именно этого воркера, а также аптайм хоста. Сокеты других сервисов в том же
  network namespace не учитываются. Если семплер недоступен, в заголовке появляется
  «· unavailable».
- **Tunnel throughput** — суммарная скорость по всем живым сессиям (↓ сервер→клиент,
  ↑ клиент→сервер) и график за последние 5 минут с подписью пикового значения. Кнопка
  **load** дополнительно накладывает CPU хоста (пунктир) и число клиентов (точки).

Ниже — плитки *Connected clients / Active profiles / Total sent / Total received*,
карточки профилей и таблица живых клиентов (обновление раз в 10 с).

### Состояние транспорта (Transport Health)
Страница **Transport health** в сайдбаре объединяет живые сессии воркера с намеренно
очищенной от секретов проекцией текущего дискового конфига. Карточка каждого профиля
показывает listener, состояние, сессии, bonded-потоки, трафик и потери из-за серверного
backpressure. В развёрнутой части видны TUN-адрес/пул/MTU/очереди, маршрутизация/NAT, DNS,
маскировка/heartbeat/shaping/multipath, socket/TUN-буферы и лимиты подключений. Отдельные
предупреждения сообщают о недоступном воркере, отсутствующем `iptables` при включённом NAT,
реальных drops и комбинации liveness-настроек, способной навсегда удержать мёртвый peer.
Обновление — раз в 5 с, в скрытой вкладке фоновый polling приостанавливается.

Status и Transport health используют общую асинхронную проверку наличия iptables.
Если утилита не найдена в обычных системных каталогах, `--version` через PATH получает
15 секунд вместе с ожиданием свободного слота. Одновременно выполняется не более
четырёх таких async-проб iptables/ip6tables; сюда входит IPv6 discovery Quick Start.
При отсутствии профилей с NAT проверка для этих двух страниц не запускается.
`Could not verify iptables availability` означает ошибку проверки (например timeout
или отказ доступа); Transport health показывает её как warning. Подтверждённое
отсутствие утилиты остаётся critical. Наличие утилиты не проверяет работу правил NAT.
[Проверки отзывчивости и ограничения](../reports/audit-0.8.2/AUDIT-Q05-HEALTH-PROBES.md).

Проекция выбирает безопасные поля по одному: obfs/reality credentials, пароли, приватные
identity-ключи и session keys `/api/transport/health` никогда не возвращает.

### Действия над живым клиентом (Kick, Set bandwidth)
В таблице живых клиентов у каждой строки две операции; обе уходят в дата-плейн через
control-сокет и применяются сразу.

- **Kick** (`POST /api/clients/{username}/kick`) — с подтверждением рвёт все сессии
  этого пользователя на указанном профиле. Если пользователь не подключён, панель
  ответит «user … not connected».
- **Set bandwidth** (`POST /api/clients/{username}/bandwidth`) — лимит в Мбит/с, целое
  число, `0` = без лимита. Одинаковый предел применяется **независимо и одновременно**
  к upload и download: например, `50` означает до 50 Мбит/с в каждом направлении
  (до 100 Мбит/с суммарно при full-duplex). Все multipath-потоки одной сессии делят
  лимит своего направления; TCP и UDP ведут себя одинаково. Значение применяется к живым
  сессиям **и записывается в
  users-файл**, то есть переживает рестарт; если запись файла не удалась, панель прямо
  скажет, что лимит применён только к сессии и будет потерян при рестарте. Дробное,
  отрицательное или слишком большое значение отклоняется с ошибкой, а не превращается
  молча в «без лимита».

### Резервная копия и восстановление (Backup / Restore)
Кнопки **⤓ Backup** и **⤒ Restore** в шапке карточки *Host load*.

- **Backup** (`GET /api/backup`) — браузер скачивает `qeli-backup-<unixtime>.tar.gz`:
  это `tar czf` всего каталога **`/etc/qeli`**, то есть серверный конфиг, users-файл,
  **identity-ключи профилей**, `usage.json`, `notify.ini`, клиентские профили и
  TLS-сертификат панели. Артефакты прошлых восстановлений
  (`.pre-restore-*`, `.restore-*`) исключаются, чтобы архив не вкладывался сам в себя;
  локальная история отката редактора (`.config-history`) тоже исключена, чтобы переносной
  backup не накапливал уже заменённые credentials.
  Файл уходит **с сервера на вашу машину** — это off-box копия. Если хотя бы один
  критичный файл (identity, `server.conf`, users) оказался нечитаемым, скачивание
  **отклоняется** с объяснением, а не отдаёт архив, который выглядит целым.
  Активный конфиг, внешний users-файл, identity-ключи профилей и явно заданные TLS-файлы
  **включённой HTTPS-панели** должны иметь нормальные абсолютные пути внутри
  `/etc/qeli`. Произвольные имена и подкаталоги внутри него поддерживаются. Если активный путь относительный или находится
  вне управляемого корня, panel backup и restore отвечают HTTP 409 вместо молчаливой выдачи
  или применения неполного архива; используйте ручную копию со всеми внешними путями.
  > **В архиве секреты.** Приватные identity-ключи, argon2-хеши паролей, обратимо
  > зашифрованные значения `password_enc` и клиентские профили с паролем в открытом
  > виде. Храните архив как ключевой материал — на шифрованном носителе, не в общем
  > облаке и не в репозитории.
  >
  > **Чего в архиве НЕТ: ключа расшифровки `password_enc`.** Файл
  > `/var/lib/qeli/panel-secret.key` намеренно хранится вне `/etc/qeli`, чтобы скачанный
  > без дополнительного шифрования архив не содержал одновременно ciphertext и ключ.
  > После восстановления только панельного архива на другой машине Argon2-хеши продолжат
  > аутентифицировать пользователей, но старые пароли нельзя будет расшифровать и повторно
  > выдать в `qeli://`/QR: для этого потребуется сбросить пароль. Для полного ручного
  > disaster-recovery сохраняйте также `/var/lib/qeli` и защищайте полученный архив как
  > содержащий ключ расшифровки. Старый `/etc/qeli/panel-secret.key` при обновлении
  > автоматически переносится в новый каталог.
  >
  > **Ключ подписи сессий панели тоже не входит в обычный архив.** Это отдельный файл,
  > который легко спутать с `panel-secret.key`, потому что оба — «ключи панели». Он лежит в
  > `$STATE_DIRECTORY/session.key` — под systemd это `/var/lib/qeli/session.key`, вне
  > каталога `/etc/qeli`, который и попадает в архив; фолбэк без `StateDirectory` —
  > `/etc/qeli/.session_key`, и только в этом случае он в архив входит. Практический
  > эффект: после восстановления на другой машине все входы в панель придётся выполнить
  > заново. Это не потеря данных, но и не то, что стоит обнаружить в разгар аварии.
- **Restore** (`POST /api/restore`) — выбираете `.tar.gz`, панель предупреждает, что
  текущие конфиг, пользователи и ключи будут **перезаписаны**, и заливает файл телом
  запроса. **Потолок тела запроса — 16 МиБ** (`DefaultBodyLimit` в
  `qeli/src/web/api/mod.rs`), больше — отказ. До распаковки архив проверяется:
  распакованный объём ≤ 64 МиБ и ≤ 5000 записей (защита от tar-бомбы), все пути строго
  внутри `qeli/` (без ведущего `/` и без `..`), только обычные файлы и каталоги —
  симлинки/хардлинки/спецфайлы отклоняются.
- **Восстановление обратимо.** Перед публикацией сервер снимает снимок текущего
  состояния в `/etc/qeli/.pre-restore-<метка>.tgz` (`0600`, хранятся 5 последних).
  Если снимок снять не удалось, восстановление **отменяется** — иначе изменение стало бы
  необратимым. Откат: `tar xzf /etc/qeli/.pre-restore-<метка>.tgz -C /etc` и рестарт.
- Распаковка идёт в staging-каталог, а не сразу в `/etc/qeli`: содержимое проверяется
  ещё раз (исполняемых файлов быть не должно; `post_up`/`post_down` и `password_command`
  **нельзя ввести или изменить** восстановлением — то же правило, что и у редактора
  конфига; серверный конфиг обязан пройти ту же валидацию профилей, что и при старте).
  Только после этого файлы переносятся атомарными `rename`.
- Два одновременных восстановления не выполняются — второе получит отказ «another
  restore is already in progress». После успешного восстановления **нужен рестарт**,
  чтобы применить, и уходит уведомление *Конфиг восстановлен*.
- Записи серверного INI из панели, `qeli set-web-password` и восстановление
  используют общий lock-файл. `exact`-восстановление сохраняет `.lock` файлы;
  даже если они есть в старом архиве, поверх активных lock-файлов они не
  публикуются. Ручной редактор по SSH эту блокировку не берёт: не редактируйте
  конфиг одновременно с сохранением из панели или CLI.

Восстановленный активный INI требует все identity-ключи профилей: для путей
внутри `/etc/qeli` архив должен содержать обычный файл ровно 32 байта, включая
режим overlay. Ключ не генерируется взамен отсутствующего. Включённый HTTPS
требует полную, читаемую и согласованную PEM-пару; пути внутри `/etc/qeli`
проверяются в staging, внешние — по существующим файлам сервера. Повреждённые
или отсутствующие зависимости отклоняются до публикации. Чужие UID/GID из tar
не восстанавливаются: распаковка создаёт файлы от имени пользователя сервера.
Вложенные `.lock` файлы сохраняют inode и не мешают режиму `exact`.

Подготовка Backup/Restore ограничена общими 60 секундами, включая очередь config lock,
все команды tar и preflight. Portable gzip ограничен 16 МиБ, pre-restore gzip — 64 МиБ;
при превышении размера/срока частичный архив не используется. Нечитаемый файл делает
rollback snapshot неуспешным и запрещает публикацию. После старта публикации файловые
операции завершаются под блокировкой; жёсткий срок для filesystem I/O не обещается.
Отмена запроса не отменяет уже работающий restore. Повторный restore сразу получает
HTTP 409, даже пока первый ожидает config lock. [Диагностика](TROUBLESHOOTING.md#659-backuprestore-timeout-лимит-архива-и-неполный-snapshot).


### Ошибка во время восстановления архива

Restore публикует файлы отдельными atomic rename; всё дерево не является единой
атомарной транзакцией. Ошибка rename или exact-очистки возвращает HTTP 500 и
`ok: false`, `publication_started: true`, `rollback_snapshot` с путём приватного
снимка. Это означает, что часть файлов уже могла измениться. Не перезапускайте
сервер до проверки дерева и ручного восстановления из указанного снимка.
Если процесс погиб, HTTP-соединение оборвётся; ищите последний созданный
`/etc/qeli/.pre-restore-*.tgz`, проверьте его содержимое и восстановите старое дерево.

Команда `tar xzf <snapshot> -C /etc` возвращает файлы из снимка, но сама по себе
не удаляет новые файлы, добавленные неудачным restore. Для полного возврата
сопоставьте дерево с содержимым снимка и уберите только установленные новые файлы.
Сохраните сам снимок и действующие `.lock`; координируйте recovery с остальными
writers. После восстановления проверьте конфиг, пользователей, identity и TLS,
затем выполните рестарт. Автоматического rollback и гарантии при power loss нет.

Снимок создаётся после успешной проверки staging и захвата FileLock активного
конфига и управляемых users/identity из старого и нового конфигов. Ожидание
каждого дополнительного lock — до 5 секунд в пределах общего бюджета подготовки.
Занятый lock возвращает HTTP 409 до публикации. Невалидный архив не ротирует прежние
снимки. После успешного restore остаются пять последних по mtime; текущий recovery
снимок сохраняется обязательно. При ошибке публикации ротация не выполняется.

Загруженный архив не может содержать `.config-history`, `.pre-restore-*`,
`.restore-upload-*` и `.restore-staging-*` ни на одном уровне: это локальное
операционное состояние. Полный pre-restore snapshot используется для ручного
recovery, а не для загрузки через API. Проверка file-only команд охватывает и
`.ini`, и прежние `.conf`; notify.ini проверяется своим парсером. Exact сохраняет
вложенные `.lock` даже в каталоге, которого нет в архиве, удаляя его обычные файлы.

`exact` принимает `true/1/yes/on` и `false/0/no/off` без учёта регистра; пробелы
по краям игнорируются. Отсутствующий параметр означает overlay. Пустое или
неизвестное значение даёт HTTP 400 до запуска restore.


Ошибки открытия/проверки lock из-за файловой системы и сбои tar extraction
возвращают HTTP 500; настоящий timeout ожидания стороннего FileLock — HTTP 409.
Структурно неверный архив по-прежнему отклоняется как HTTP 400. Отказ до публикации
возвращает `publication_started: false` и `rollback_snapshot: null`.
Если файловая система стала read-only после распаковки, удалить staging тоже
невозможно: остаётся приватный `.restore-staging-*` с modes 0700/0600. После
возврата записи и завершения restore проверьте и удалите этот временный каталог.
Новый restore не использует его; portable backup и rollback snapshot исключают
операционные staging/upload пути.

При fresh restore смешанных inline/external пользователей внешний users INI
обязателен в архиве, даже если есть inline accounts. Внешний файл выигрывает
при совпадении user/group names; ссылки на группы проверяются на объединении
обоих источников. После рестарта действуют восстановленные credentials и ограничения.
`/var/lib/qeli/panel-secret.key` остаётся машинным состоянием и в portable archive
не входит. На прежнем сервере сохранённый ключ позволяет повторно выдать прежнюю
ссылку. На новом сервере без этого ключа старые password_hash продолжают работать,
но повторная выдача password_enc требует восстановления отдельного state backup
или явно разрешённого сброса пароля. Ошибка расшифровки сама пароль не меняет.

### Быстрый старт (страница Quick start)
Отдельная страница сайдбара — таблица из десяти режимов маскировки, каждый запускается
кнопкой **Launch**: `reality-tls` (TCP 443, помечен «flagship»), `reality` (8443),
`fake-tls` (8444), `obfs-ws` (8445), `obfs-none` (8446), `plain` (8447), `udp-fake-tls`
(UDP 8448), `udp-quic` (8449), `udp-obfs` (8450), `obfs-awg` (TCP 8451). У каждой
строки — транспорт, порт и одна фраза о том, что режим делает.

Что делает **Launch**:
1. читает текущий конфиг и **проверяет порт**: если этот порт+транспорт уже занят
   ДРУГИМ профилем, появляется попап «Port already in use» со ссылкой в Config (запуск
   того же режима повторно разрешён);
2. спрашивает подтверждение и режим IP **внутри** туннеля: `auto`, `ipv4`, `dual` или
   `ipv6`. При первом запуске профиль строится поверх канонических дефолтов
   (`/api/config/defaults`) и получает bind `0.0.0.0:<порт>`, отдельный TUN `vpn<N>`,
   collision-free адреса, DNS/NAT и стек обфускации выбранного режима.
   - `auto` выбирает `dual` только при обнаруженном публичном GUA на интерфейсе IPv6
     default route и доступном `ip6tables`; иначе сохраняет полностью рабочий `ipv4`;
   - явный `dual`/`ipv6` отказывается запускаться без этих условий или при MTU ниже 1280;
   - IPv6 получает уникальный RFC4193 `/64`, gateway `::1`, IPv6 DNS listener и NAT66;
     `dual` оставляет NAT44, а `ipv6` выключает IPv4 NAT/forwarding;
   - `auto` разрешается один раз. Повторный Launch существующего профиля сохраняет его
     конкретный IP-режим, credentials и ручные настройки. Явный выбор другого режима
     намеренно переключает и нормализует весь egress-контракт, но не ротирует credentials.
   Поэтому ранее выданные клиентские ссылки не перестают работать; для ротации/сброса
   используйте явные действия Config;
3. передаёт ожидаемую ревизию в `POST /api/config/quickstart/{mode}`. Сервер удерживает
   общий lock записи, пока заново читает конфиг, строит и валидирует профиль, снимает снимок
   и атомарно записывает файл; параллельная правка из панели/SSH даёт конфликт, а не
   затирается. Только после успешной операции страница перезапускает сервер.

По завершении модалка показывает имя профиля и endpoint, а для режимов, которым они
нужны, — новые при первом запуске либо сохранённые при повторном **REALITY short_id** и
**obfs pre-shared key** с кнопкой Copy: их надо прописать каждому клиенту. Там же
напоминание, что клиенту требуется ещё и
запиненный публичный ключ сервера (`qeli show-identity` либо Config → Global → Server
identity keys), а для TCP-режимов — предупреждение про mobile/LTE и path MTU.

Режимы независимы: каждый получает свой интерфейс, подсеть и порт, поэтому держать
несколько одновременно — рекомендуемая продовая раскладка (клиент подключается тем
портом, который проходит в его сети).

Полная логика выбора, routed GUA, `off/manual/route/nat66`, NDP proxy, клиентское `ipv6=auto|required|off` и
проверка утечек описаны в [руководстве по IPv6](IPV6.md).

### Config (настройки)

- **Вкладки сверху** — `Global` + по одной на каждый профиль (+ добавить). Внутри
  профиля **всё одной страницей** (без внутренних вкладок); сверху — **липкая
  якорная навигация** (Bind / TUN / Pool / Routing / DNS / DHCP / Obfuscation /
  Performance), прилеплена под шапкой.
- **Профиль** — тумблер `enabled`, и секции со **всеми** полями: транспорт/bind/
  identity-путь, TUN (вкл. `ip_mode`, IPv4/IPv6 gateway, MTU и `queues` multi-queue),
  отдельные IPv4/IPv6 пулы, исключения и резервации, маршрутизация + NAT44 +
  `off|manual|route|nat66` + pushed-routes, dual-family DNS + blocklist,
  DHCP (только для TAP — см. ниже),
  обфускация (mode/cipher/fronting, TLS-маскировка + SNI-пул, REALITY +
  `handrolled`/`peek`, padding, heartbeat, fragmentation, автоматический Reality/H2 carrier (без пользовательского переключателя), traffic-norm,
  anti-fingerprint, QUIC, **multipath**), производительность (лимиты,
  rate-limit/new-session, TCP/TUN-буферы).
- **Global** — Authentication (вкл. `bind_static_to_session` H-1), Web UI (вкл. TLS,
  allowlist, public_host, admin-пароль), Logging, **Server identity keys** (показ
  pinned-ключа каждого профиля + кнопка **Rotate**).
- **Ручная IPv6-маршрутизация (0.8.2):** в Config выберите профиль с `tun.ip_mode = dual`
  или `ipv6`, затем Routing → `IPv6 forwarding / NAT66` → `manual`. В поле
  `Upstream IPv6 NDP proxy` доступны `off`, `auto`, `required`; для on-link префикса
  укажите Ethernet-интерфейс upstream. При переходе `route` ↔ `manual` NDP сохраняется;
  выбор `off` или `nat66` выключает NDP и очищает его интерфейс. Подготовьте firewall,
  forwarding, RA и DNS на хосте, затем используйте `Apply & Restart`. `Save to Disk`
  только сохраняет настройки до перезапуска. Границы ответственности и пример INI —
  в [разделе manual](IPV6.md#manual).
- **Сохранение:** `Save to Disk` (запись в конфиг, применится при следующем
  рестарте) или `Apply & Restart` (сохранить и перезапустить сейчас). Вью
  `Form` / `INI` (raw сохраняет дословно — комментарии целы).
- **Безопасное редактирование:** все представления используют одну ревизию точных байтов
  INI вместе с комментариями. Сохранение не затирает более новую правку из другой вкладки
  или с SSH; переход raw/structured, Reload и уход со страницы предупреждают о потере
  несохранённого. Перед подтверждением показываются пути изменённых полей либо номера строк.
  Каждая изменяющая запись из панели создаёт приватный снимок в
  `/etc/qeli/.config-history` (каталог `0700`, файлы `0600`, хранятся десять последних);
  **History** валидирует и восстанавливает снимок, сначала сохранив текущий файл как ещё
  один. Для data-plane изменений после этого всё равно нужен рестарт.

Сетевой preflight сохранения/restart выполняется асинхронно перед блокировкой записи.
Пробы делят 15 секунд; после наблюдения остаётся пять секунд на ожидание config lock
и подготовку кандидата. Занятый или устаревший preflight требует повторить действие;
revision и пользователи заново проверяются под lock. [Подробности](../reports/audit-0.8.2/AUDIT-Q05-PANEL-TRANSACTIONS.md).

> **`Apply & Restart` требует прав на перезапуск сервиса.** Он выполняет
> `systemctl restart <unit>`. **root**-сервис делает это напрямую; закалённый
> **non-root** сервис `User=qeli` требует polkit-правила. **.deb ставит его сам**
> (`/etc/polkit-1/rules.d/49-qeli.rules`) — делать ничего не нужно. Если ставили
> **иначе** (голый бинарь, tarball), панель обнаружит отсутствие правила и попросит
> один раз выполнить на сервере:
> ```
> sudo qeli install-polkit                 # по умолчанию: user=qeli unit=qeli.service
> sudo qeli install-polkit --unit qeli-server.service --user vpn   # свои значения
> ```
> После этого `Apply & Restart` работает. **Внутри контейнера** systemctl недоступен:
> изменения профилей/data-plane применяются автоматически через перезапуск воркера
> в процессе; изменение **сокета панели** (`web.bind`/`port`/`tls`/`enabled`) требует
> пересоздания контейнера (`docker restart <name>`). Панель теперь показывает точную
> причину, а не молча ничего не делает.

> **DHCP — частая путаница.** В обычном режиме **TUN** IP клиентам выдаёт
> встроенный **пул** (секция Pool → CIDR/резервации), а **не** DHCP. DHCP-сервер
> нужен только для **TAP/bridged**. При выключенном DHCP в TUN адреса всё равно
> назначаются.

### Перезапуск сервера: воркер или полный рестарт
Панель умеет два разных перезапуска, и разница принципиальна.

- **Перезапуск воркера** (`POST /api/server/restart`) — супервизор, а вместе с ним и
  сама панель, продолжают работать; пересоздаётся только процесс дата-плейна, то есть
  VPN-профили (TUN, слушатели, DNS, DHCP) сносятся уходящим воркером и поднимаются
  заново свежим. Панель при этом не падает — JS просто опрашивает `/api/status`, пока
  клиенты не вернутся. Именно это делает **Launch** на странице Quick start.
- **Полный рестарт** (`POST /api/server/full-restart`) — `systemctl restart <юнит>`
  (юнит определяется по cgroup самого процесса, иначе берётся `qeli.service`).
  Заменяется весь процесс, включая сокет панели. Именно это делает кнопка
  **Apply & Restart** на странице Config.

**Полный рестарт ОБЯЗАТЕЛЕН** для полей, которыми панель слушает сеть: `web.enabled`,
`web.bind`, `web.port`, `web.tls`, `web.tls_cert`, `web.tls_key` (а также
`web.base_path`) — они привязываются при старте супервизора, и перезапуск воркера их не
применяет. Полный рестарт также требуется при смене `auth.users_file`,
`web.persist_session_key` или действующих настроек логирования `logging.level`,
`logging.file`, `logging.time_format`. Сохранение сообщает об этом явно. Перед полным
рестартом панель также проверяет,
что конфигурация содержит включённый профиль, у включённой панели задана авторизация
и существующая TLS-пара читается как сертификат и ключ. При ошибке работающий
процесс сохраняется; исправьте конфигурацию и повторите рестарт.

- **Сессия переживает полный рестарт**, пока включён `web.persist_session_key` (по
  умолчанию включён: ключ подписи сессий лежит в файле `0600`). Выключите его — и
  каждый рестарт будет разлогинивать всех.
- **Права.** Перед перезапуском выполняется пре-флайт, чтобы отказать *громко*, а не
  молча: нет systemd (контейнер или запуск руками), нет бинаря `systemctl`, либо сервис
  работает НЕ от root и нет polkit-правила `/etc/polkit-1/rules.d/49-qeli.rules` — в
  последнем случае в ответе прямо сказано выполнить `sudo qeli install-polkit` (в `.deb`
  правило уже стоит). Ответ уходит первым, `systemctl restart` выполняется примерно
  через 0,8 с, чтобы браузер успел его получить.
- **В контейнере** systemctl недоступен; если правка НЕ трогает сокет панели, панель
  сама откатывается на перезапуск воркера и пишет об этом.

### Работа редактора конфигурации и подтверждения

Сохранение показывает текущий черновик и записывает его с ревизией, из которой
он был загружен. Повторное нажатие не запускает второе действие, пока открыто
подтверждение, выполняется запись или перезапуск. Правки, сделанные после открытия
подтверждения, остаются несохранёнными, если отличаются от отправленного черновика.
Apply & Restart останавливается при отмене или ошибке сохранения и при оставшихся
новых правках. Неподтверждённый полный перезапуск сохраняет признак необходимости
полного рестарта для изменений сокета панели.

Reload и переключение Form/INI запрашивают подтверждение перед сбросом черновика.
При уходе со страницы браузер предупреждает о несохранённых изменениях. Ошибка
чтения отображается явно; до успешной перезагрузки сохранение недоступно. Начальные
значения не становятся доступными для записи из-за ошибки чтения. Если недоступны
только значения нового профиля, загруженный конфиг можно редактировать, но Add
остаётся заблокированным.

Identity и History показывают ошибку чтения и кнопку Reload. Ошибка обновления
сохраняет предыдущий снимок. Поздний ответ не заменяет новое окно истории и не
обновляет уничтоженный редактор. Восстановление истории использует текущую ревизию
конфига, перечитывает восстановленную конфигурацию и не перезапускает сервер автоматически.

Общий диалог подтверждения начинает с фокуса на «Отмена», удерживает Tab и Shift+Tab
внутри, поддерживает Escape и возвращает фокус к вызвавшему его элементу, если тот
остаётся доступен. Закрытие вложенного подтверждения восстановления оставляет
окно History открытым.

### Редактор Raw INI

Вид `INI` на странице Config (`GET`/`PUT /api/config/raw`) показывает **файл конфига
дословно** и записывает обратно введённый текст — **комментарии и форматирование
сохраняются**. Вид `Form` разбирает конфигурацию в структуру и сериализует её обратно в
INI, поэтому рукописные комментарии при таком сохранении пропадают; конфиг с комментариями
правьте в виде `INI` или прямо на сервере. Оба вида сохраняют конфигурацию только в INI.

> **Секреты в этом виде замаскированы (с 0.7.13).** Значения `password_hash`,
> `password_enc` и `password` отдаются как `<unchanged>` — раньше редактор показывал их
> дословно, то есть выдавал хеш админского пароля и секреты пользователей всякому, кто
> открыл страницу. Плейсхолдер **можно оставлять как есть**: отправленный обратно
> неизменённым, он означает «сохранить то, что на диске». Чтобы поменять значение —
> впишите новое поверх плейсхолдера. Остальной файл (комментарии, порядок, отступы)
> при этом сохраняется дословно.

Проверки у Raw те же, что у обычного сохранения: текст обязан разбираться; `logging.file`
— внутри `/var/log/qeli`; `auth.users_file` и `identity_key` — внутри `/etc/qeli`;
`web.tls_cert`/`tls_key` — внутри `/etc/qeli` или `/etc/letsencrypt`;
`web.password_hash` обязан быть валидным argon2-хешем (в ручном редакторе
проще всего залочить себя опечаткой); `routing.post_up`/`post_down` нельзя ни
ввести, ни изменить через панель; и конфиг обязан пройти ту же валидацию профилей, что и
при старте сервера. Результат живого применения виден в `web_settings_applied`
ответа сохранения; при `false` действует прежнее состояние панели. Смена `auth.users_file`
или `web.persist_session_key`, а также `logging.level`, `logging.file` или
`logging.time_format` требуют полного рестарта supervisor через `Apply & Restart`
(или `systemctl restart qeli`). Профиль/bind/tun тоже применяются после рестарта.

При записи серверного INI через API (Quick Start, форма, INI-редактор или восстановление
истории) передавайте `expected_revision` из последнего GET конфигурации. Без него либо
со старой ревизией запись отклоняется; перечитайте конфиг и повторите изменение.

### Идентичность сервера: показ и ротация
**Config → Global → Server identity keys** (`GET /api/identity`) перечисляет профили с
их bind-строкой и **сохранённым публичным ключом** (hex) — панельный аналог
`qeli show-identity`; при первом обращении файл ключа создаётся, если его ещё нет.
Панель читает ограниченный снимок текущего INI и отказывает в показе, ротации и
Share, если явный `identity_key` получен из недоверенного файла. Она также не
принимает нестандартный `auth.users_file` из такого снимка для действий с users.

Кнопка **Rotate** (`POST /api/identity/{профиль}/rotate`) генерирует профилю новый ключ.
**Работающий воркер продолжает использовать старый ключ до рестарта**, а после рестарта
**каждому клиенту этого профиля придётся выдать новый `auth.server_public_key`** — ранее
запиненный ключ больше не подойдёт. Список Identity показывает уже записанный новый
ключ; до рестарта он отличается от ключа работающего worker. То есть ротация означает переиздание конфига/ссылки
всем клиентам профиля, и делать её «на всякий случай» не нужно.

### Users (пользователи и группы)
- **Создание/правка:** вводите пароль **открытым текстом** — сервер сам хеширует
  (argon2id) и хранит обратимо-зашифрованную копию (для переиздания конфига, см.
  ниже). Поля: лимит bandwidth и legacy burst только для просмотра, необязательные статические IPv4- и IPv6-адреса, группа,
  max sessions, **разрешённые профили** (изоляция интерфейсов), allowed networks и
  **персональные маршруты**. Очистка любого static-поля или группы действительно удаляет
  сохранённое значение: API различает отсутствующий ключ (не менять) и `null`/пустую строку
  (очистить).
- **Группы** (`/api/groups`) — именованные шаблоны, которые лежат в том же users-файле
  рядом с пользователями (секция `[group:<имя>]`) и несут три поля:
  `bandwidth_limit_mbps`, `max_sessions`, `allowed_networks`. Участник группы наследует
  то поле, которого не задал у себя: **собственное значение всегда перекрывает
  групповое**, а если не задано ни там, ни там — лимита нет. Группу можно создать,
  изменить и удалить; после изменения воркер перечитывает users-файл.
- **Лимит трафика и срок** (кнопка ⚙ у пользователя): пожизненный лимит **загрузки** (ГБ,
  `0` = без лимита) и **срок действия** аккаунта — задаётся как *Expire in (days)* или
  выбором конкретной **даты из календаря** (*Or until date*, оба поля синхронизированы).
  По наступлении срока пользователь не может подключиться, активная сессия рвётся, и
  уходит уведомление *Quota breach*. Кнопка ↺ сбрасывает счётчик трафика.
  - **Квота данных считается ТОЛЬКО по загрузке** (download, сервер→клиент). Отдача
    (upload) не учитывается в квоте — пользователя нельзя заблокировать отправкой. Это не
    относится к скоростному `bandwidth.limit_mbps`: он ограничивает оба направления.
    В колонке трафика два
    направления показаны раздельно: `↓` загрузка (лимитируемая, по ней рисуется полоса
    против лимита) и `↑` отдача.
- Действия: Enable/Disable (с киком сессий), Delete.

### Трафик и квоты (Usage & quotas)
Колонка **Data usage** в таблице пользователей (`GET /api/usage`) показывает
пожизненные счётчики: полосу «загрузка против лимита», `↓` загрузку (лимитируемое
направление), `↑` отдачу, число подключений за всё время (`· N×`) и срок действия.
Кнопки ⚙ (лимит и срок) и ↺ (сброс счётчика) описаны выше, в разделе Users.

- **Где хранится.** Отдельный sidecar-файл **`/etc/qeli/usage.json`**, а не users-файл
  (в котором лежат хеши паролей и который переписывается на каждый CRUD) — так учёт
  ничем не рискует. Пишет его воркер атомарно; панель перечитывает файл на каждый
  запрос `/api/usage` и помечает, кто сейчас онлайн.
- **Как накапливается.** Свип воркера **раз в 10 с** снимает счётчики живых сессий и
  доливает в пожизненный итог только прирост с прошлого раза (идемпотентно по
  `session_id`), поэтому в горячем пути пакетов работы не прибавляется.
- **Лимит считается ТОЛЬКО по загрузке** — `used_down` (сервер→клиент); 1 ГБ =
  1 000 000 000 байт, `0` = без лимита. Отдача (`used_up`) учитывается и показывается,
  но **никогда не лимитируется**: заблокировать пользователя отправкой нельзя.
- **Что происходит при превышении.** Новый вход отбивается ещё на авторизации
  (`AUTH DENIED … download quota exhausted`), а **живую сессию рвёт тот же свип**: она
  отключается, её IP возвращается в пул, в лог уходит `usage: disconnected … over quota
  / expired`, и шлётся уведомление *Quota breach* (не чаще раза в час на пользователя,
  чтобы клиент в цикле реконнекта не спамил). Точно так же обрабатывается наступивший
  срок действия.
- **Установка и сброс** (`POST /api/usage/{username}/limit` и `…/reset`) идут через
  воркер по control-сокету — правится авторитетная users-БД и файл сохраняется.
  Некорректное число отклоняется с ошибкой, а не превращается тихо в «без лимита» /
  «без срока». Сброс обнуляет **обе** стороны счётчика, лимит и срок не трогает.

### Выдача конфига (Share / QR) — без ввода пароля
Кнопка **Share/QR** у пользователя. Укажите только публичный хост (предзаполнен из
`web.public_host`, иначе из последнего использованного) → **Generate**. Пароль
**вводить не нужно** — сервер берёт его из зашифрованной копии и собирает
`qeli://`-ссылку + QR. Пароль при этом **не меняется**.

- **Старые пользователи** (заведены до этой функции — копии пароля нет): панель
  покажет «нет сохранённого пароля» и кнопку **«Reset password & issue config»** —
  один раз сбросит пароль (покажет новый), после чего конфиг переиздаётся всегда.
  (Сброс — единственный путь: старый пароль восстановить неоткуда.)

### Клиент-менеджер (вкладка Client) — исходящие туннели
Отдельная страница сайдбара, где панель выступает **клиентом**: этот сервер сам
дозванивается до ДРУГИХ qeli-серверов (роль клиента рядом с ролью сервера — например,
чтобы завернуть собственный исходящий трафик или связать площадки). К входящим
VPN-клиентам этой машины страница отношения не имеет.

**Добавить профиль** — три кнопки:
- **Import qeli:// link** — вставляете строку вида
  `qeli://user:pass@host:443?mode=…&key=…&sni=…&rsid=…` и, если хотите, имя профиля;
  без имени оно берётся из метки ссылки или из хоста. Импортированный профиль всегда
  **split-tunnel** — признак full-tunnel в ссылке не передаётся.
- **Paste INI config** — вставить клиентский INI целиком (`[qeli]` + `[logging]`);
  он сохраняется дословно, поэтому доступен любой ключ клиента.
- **Add manually** — форма: server `host:port`, протокол tcp/udp, wire-режим
  (`fake-tls` / `reality-tls` / `obfs` / `plain`), пользователь и пароль, TUN-девайс
  (пусто = авто), SNI, **запиненный ключ сервера** (hex; обязателен для `reality-tls`),
  REALITY short_id, obfs-ключ и fronting, AmneziaWG-junk (jc/jmin/jmax), QUIC-маскировка
  (только UDP), автоподключение при старте, `route_local` и full-tunnel. Переключатель
  **Raw INI ↦** в том же окне даёт полный конфиг, а ключи, которых нет в форме,
  сохраняются при переходе туда и обратно.

Размер клиентской Linux TUN-очереди задаётся здесь через **Raw INI**:
`tun.tx_queue_len = 1000` в `[qeli]` (дефолт `1000` пакетов, диапазон `1..32767`,
без auto). Отдельного поля формы нет; ключ локальный, не входит в ссылку/QR
и не задаётся конфигом серверного профиля. Нужен клиент с доработкой development 0.8.2.
С `dev_attach=true` ключ удаляется, поскольку очередью владеет внешняя система.
После сохранения — Disconnect, затем Connect, не server reload.
Бинарник, обслуживающий эту панель, также должен поддерживать ключ: старый редактор
может отвергнуть INI ещё до запуска нового клиента. Речь о локальном хосте панели,
не об обязательном обновлении удалённого VPN-сервера для standalone-клиента.
[Полный контракт](CONFIG.md#client-tun-tx-queue).

При создании и импорте имя должно быть свободным: существующий клиентский профиль
не перезаписывается. Редактор получает ревизию точного INI и передаёт её при сохранении.
Если файл изменился в другой вкладке или вручную, панель отклоняет запись; заново
откройте профиль, сравните изменения и сохраните. Чтение INI ограничено 256 КиБ,
как и в клиентском runtime. Если профиль уже подключён, успешное сохранение
пишет INI на диск, но работающий процесс продолжает использовать прежние настройки.
Для применения нового INI выполните Disconnect, затем Connect; внутренний reconnect
процесса файл заново не читает.

**Где что лежит.**
- Профили — `/etc/qeli/clients/<имя>.conf`, права `0600` (внутри пароль открытым
  текстом). Имя — только `[A-Za-z0-9._-]`, до 64 символов.
- TUN-устройство, если не задано вручную, назначается автоматически: младший свободный
  `vpnN`, не занятый ни другим клиентским профилем, ни уже существующим интерфейсом
  хоста (в том числе TUN серверного профиля).
- Лог каждого туннеля — `/var/log/qeli/client-<имя>.log`; он дописывается между
  reconnect/Connect и после 4 МиБ обрезается со стороны самых старых строк.
- Структурная диагностика — рядом с control-сокетом, файл
  `client-<имя>.status.json` (`0600`). В нём только state/retry, согласованный
  `NetworkPlan` и TX/RX/UDP-счётчики — никаких credentials.

**Connect / Disconnect.** Connect запускает `qeli client -c <файл>` дочерним процессом
супервизора (наследует его права, поэтому может поднять TUN и маршруты). Disconnect
шлёт SIGTERM — клиент восстанавливает DNS и маршруты и выходит; если за 5 с не вышел,
его добивают SIGKILL. **Delete** сверяет ревизию INI до остановки, затем отключает
и удаляет профиль и его лог. При устаревшей вкладке туннель остаётся запущенным,
файл сохраняется; перечитайте список. Прямой API-вызов Delete требует заголовок
X-Qeli-Revision из списка профилей.
Флаг `autostart = true` подключает профиль при старте супервизора. Autostart
читает только стабильный клиентский INI размером до 256 КиБ; изменённый во
время чтения или слишком большой файл пропускается.

**Статус честный, а не «процесс жив».** Список обновляется раз в 5 с и читает
структурный статус Rust-клиента: **● Connected**, **◌ Connecting…**, **⚠ Error — retrying**
(процесс жив, но туннель зациклился на реконнекте — например, `reality-tls` без
short_id) или **○ Disconnected**. **Details** показывает carrier/tunnel-адреса, MTU,
DNS, эффективные маршруты, решения full-tunnel/kill-switch/multipath и
TX/RX/UDP buffer/drop-счётчики. Короткий хвост лога остаётся человеческим audit trail и
fallback для процесса клиента, запущенного старым бинарём. Файл структурного
статуса больше 64 КиБ или изменившийся во время чтения игнорируется; панель
использует лог как fallback.

### Проверки исходников и внешнего вида панели
`python3 scripts/check_panel.py` — dependency-free CI-gate для общего оформления контролов,
клавиатурной доступности custom-switch, дублей RU-ключей и отсутствующих переводов у
контролов и вызовов `qeliT`/`qeliTf`. На подготовленной лабе
`scripts/panel_visual_regression.py` снимает или сравнивает все страницы в матрице из 72
вариантов RU/EN × dark/light × desktop/mobile; сценарий opt-in, потому что ему нужны
запущенная авторизованная панель и проверенные baselines.

> **Full-tunnel на сервере опасен.** Галочка «Full-tunnel (route ALL traffic)»
> заворачивает ВЕСЬ трафик этой машины в удалённый сервер и может отрезать вам и панель,
> и SSH — поэтому по умолчанию она выключена и помечена предупреждением.
>
> **Хуки запрещены.** Профиль, сохранённый через панель, не может содержать
> `post_up`/`post_down` и `password_command` (они выполняются через shell), а
> `password_file` обязан лежать внутри `/etc/qeli`. Нужны хуки — правьте файл профиля
> на самом сервере.

### Логи (вкладка Logs)
Показывает **хвост файла**, заданного в `logging.file` (`GET /api/logs`).

- Если `logging.file` не задан, страница честно пишет, что логи идут в stderr/journald,
  и подсказывает `journalctl -u qeli -n 200 --no-pager`: читать журнал systemd панель не
  умеет.
- Путь обязан находиться внутри **`/var/log/qeli`**, иначе — «log path rejected» (чтобы
  правка конфига не превратилась в чтение произвольного файла вроде `/etc/shadow`).
- Сервер читает только последние ~4 МиБ файла и отдаёт не больше запрошенного числа
  строк: селектор **100 / 200 / 500 / 1000**, по умолчанию 200, жёсткий потолок API —
  2000 строк.
- **Фильтры:** выпадающий список уровня (All / ERROR / WARN / INFO / DEBUG) и строка
  поиска (регистронезависимая). Поиск без выбранного уровня уходит на сервер и
  применяется к прочитанному окну; уровень и поиск дополнительно фильтруют уже
  загруженные строки в браузере — то есть фильтр работает в пределах последнего хвоста,
  а не по всему архиву логов.
- **Auto-refresh** (переключатель) перечитывает лог раз в 5 с и прокручивает вниз;
  кнопки **Refresh** и **Bottom** — то же вручную. В строке статистики видны путь к
  файлу, «показано N из M» и счётчики по уровням; строки подсвечиваются по уровню.

### Blocked IPs (заблокированные адреса)
Отдельная вкладка сайдбара. Показывает source-IP, **залоченные брутфорс-защитой**
(повторный неверный пароль), разделённые на **два независимых журнала**: **VPN
authentication** и **Panel login**. Для каждой записи — адрес, число неудач и сколько
осталось до авто-разблокировки. **Вкладка сама обновляется каждые 5 с** (фоновый поллинг,
без мигания спиннера), а счётчик «до разблокировки» **тикает посекундно** — истёкшие записи
исчезают сами, так что активная блокировка видна в реальном времени (раньше список грузился
один раз при открытии и транзиентный лок было легко не увидеть). Кнопка **Unblock** снимает
блок с одного адреса, **Clear all** — со всех, в пределах своего журнала (снятие лока панели
не трогает журнал VPN). Лок и так снимается сам по таймауту своей поверхности
(`brute_force.lockout_secs`, дефолт 900 с). То же из CLI для журнала VPN: `qeli list-blocked` /
`qeli unblock <ip>` (см. GETTING-STARTED §10).

**Политика блокировки — две независимые политики, правятся вживую на этой вкладке.** С
0.7.7 редактор *Lockout policy* несёт **две** политики рядом:
- **VPN authentication** → `[auth] brute_force`,
- **Panel login** → `[web] brute_force`.

У каждой свой **выключатель**, *Max attempts*, *Window* и *Lockout*, так что туннель и
панель ограничиваются (или отключаются) раздельно. **Save policy** проверяет весь итоговый
INI перед записью и применяет панельную политику через живую перезагрузку настроек, а VPN worker запрашивает обновить через
SIGHUP без разрыва сессий. Изменение действующих порогов сбрасывает счётчики соответствующей
поверхности. Если worker недоступен, вкладка сообщает, что VPN-политика сохранена и применится
при его следующем запуске. Если панельная перезагрузка не удалась, INI остаётся сохранённым, но действующая политика не меняется; вкладка помечает расхождение сохранённой и действующей политик и предлагает проверить INI и журнал до рестарта. При ошибке чтения INI вкладка показывает отказ вместо значений по
умолчанию. Выключите переключатель,
чтобы полностью отключить ограничение для поверхности (для входа в панель безопасно только на
доверенном / loopback-bind). Те же политики правятся и в **Config → Authentication** (VPN) и
**Config → Web UI** (панель).

> Частые `New TCP connection from …` с одного IP на `reality-tls` в логах — это
> **сканеры/пробы**, а не подбор пароля: они прозрачно проксируются на upstream и не
> имеют юзера. Настоящие попытки видны как `AUTH FAIL … user=X — wrong password`.

### Уведомления (Notifications)
Исходящие оповещения о ключевых событиях сервера через **Telegram** и **произвольный
webhook** — два независимых канала, у каждого свой переключатель, реквизиты, набор
событий и кнопка **Send test**. Конфиг в `/etc/qeli/notify.ini` (правится и панелью, и
файлом); отправка best-effort и не блокирует дата-плейн, сертификаты исходящего TLS
проверяются. При отсутствии сохранённых настроек каналы по умолчанию выключены.

Файл использует общий INI-парсер: секции `[notify]`, `[telegram]`, `[webhook]`.
Поля событий относятся к своей секции канала; неизвестные ключи, повторы и неверные
boolean-значения отклоняются. Пример:

```ini
[notify]
server_name = edge-eu

[telegram]
enabled = false
token = ""
chat_id = ""
on_server_start = true
on_quota_breach = true
on_login_lockout = true
on_auth_lockout = true
on_restore = true
on_client_connect = false
on_client_disconnect = false

[webhook]
enabled = false
url = ""
on_restore = true
```

Настройки уведомлений читаются только из INI (до 64 КиБ); слишком большой или
повреждённый файл отклоняется без замены значениями по умолчанию. Если остался
старый `notify.json` без `notify.ini`, загрузка завершится ошибкой: вручную
перенесите настройки в INI и удалите старый файл. Панельный backup не включает
`notify.json`, а restore архива с ним отклоняется. JSON остаётся только форматом
служебного API и webhook-сообщений.

При сохранении панель сверяет ревизию точных байтов `notify.ini`. Если другая
вкладка или ручной редактор уже изменили файл, запись отклоняется; обновите
страницу и проверьте новые значения перед повторным сохранением.

- **Имя сервера (Server name)** — метка, добавляемая в начало каждого сообщения
  (`[имя] …`) и в поле `server` webhook-JSON, чтобы различать несколько серверов,
  пишущих в один чат / хук. Пусто = без префикса.
- **События** (переключаются на каждый канал): *старт / рестарт сервера*, *превышение
  квоты* (юзер исчерпал лимит трафика или срок), *блокировка входа в панель* (IP
  заблокирован после неудачных входов в **панель**), **блокировка IP (VPN-авторизация)**
  (IP залочен брутфорс-защитой после повторного неверного **VPN**-логина/пароля),
  *конфиг восстановлен*. Cooldown квоты/VPN auth — один час на ключ, блокировки панели — десять минут.
  Opt-in connect/disconnect — десять секунд на пользователя и вид события.
- Токен Telegram — **только запись** (после сохранения маскируется); **Send test** шлёт
  пробу в один канал с текущими (даже несохранёнными) настройками.

Лимиты действуют отдельно в worker и supervisor: **128 принятых отправок вместе с
активными**, **8 одновременных запросов** на Telegram, webhook и **Send test** суммарно.
Событие для двух каналов занимает два места. Полная очередь отбрасывает новые
автоматические отправки; `notify: queue full` выводит накопленное число отказов с
экспоненциальным прореживанием. Проба панели получает явную ошибку. Её **общий таймаут
10 секунд включает ожидание в очереди**; timeout или отмена handler отменяют ещё не
отправленную работу. Автоматический HTTP-запрос также ограничен десятью секундами после
перехода в активную группу.

Detail события и отображаемое имя сервера обрезаются по границе UTF-8 до 2048 и 256 байт.
Webhook body ограничен 32 KiB. URL/token/chat id длиннее 4096/512/128 байт отклоняются,
а не обрезаются; сохранённый конфиг не меняется. Graceful stop закрывает приём, ждёт до
десяти секунд, затем отменяет остаток и дожидается завершения задач. Постоянного retry
нет: переполнение, остановка и сетевые ошибки могут приводить к потере уведомлений.
Срок начинается при первом запросе остановки worker/supervisor; очередь завершается
параллельно очистке и не добавляет десять секунд после неё.
HTTP вне 2xx записываются в журнал с именем канала.

<!-- normative-sync: notify-delivery-trust-v1 -->

В Unix sidecar должен быть обычным файлом владельца root или пользователя процесса,
без права записи для группы и остальных. Симлинки отклоняются; рекомендуемые права —
`0600`. Недоверенный файл отключает автоматические каналы и вызывает ошибку панели.
Сохранение в панели не исправляет его права и не разрешает использование его содержимого:
исправьте файл от имени администратора и загрузите его заново. После успешного сохранения
кеш процесса сбрасывается; следующее событие читает текущий стабильный снимок INI,
включая более позднее ручное изменение.

URL webhook сохраняет query-параметры; фрагмент (`#...`) не попадает в запрос.
Пробелы в URL нужно кодировать. Поддерживаются конечные строки статуса HTTP/1.0
и HTTP/1.1 размером до 4 КиБ; промежуточные ответы 1xx не поддерживаются. Успех —
только 2xx. Ответ 3xx означает ошибку; переходов по редиректам нет. Текст некорректного
ответа удалённого сервера не копируется в ошибку панели или журнал.

Перед соединением адреса проходят консервативную проверку публичности, включая
проверку каждого кандидата перед использованием; выбирается и закрепляется только допустимый адрес. Отклоняются
loopback, частные/link-local, документальные, тестовые и зарезервированные диапазоны,
префиксы трансляции/туннелирования IPv6 и специальные протокольные назначения.
Политика также исключает некоторые глобально доступные специальные адреса и не
является точной классификацией доступности IANA. Внутренние webhook и назначения
NAT64 не поддерживаются. HTTPS проверяет сертификат и имя по встроенному хранилищу CA.

### Баннер обновлений (opt-in)
При `[web] update_check = true` панель показывает dismissible-баннер **«Доступна новая
версия»**, если на GitHub есть более новый релиз qeli. Проверку делает **браузер
оператора** (как маркетинг-сайт), а не серверный процесс — никакого серверного beacon;
ничего идентифицирующего не отправляется и ничего не скачивается. Баннер даёт
**копируемую команду обновления** под способ установки (`.deb`: скачать → сверить
SHA256 → `dpkg -i` → restart; Docker: `docker pull`) — выполняете вы. По умолчанию ВЫКЛ.
(У десктоп/мобильных клиентов свой opt-in в Настройках; в CLI — `qeli version --check`.)
См. «Проверка обновлений» в [CONFIG.md](CONFIG.md).

## 3. Хранение пароля (модель и компромисс)

Для аутентификации хранится **argon2id-хеш** (необратим). Чтобы можно было
**переиздавать** конфиг существующему пользователю без знания пароля,
дополнительно хранится **обратимо-зашифрованная** копия пароля:

- Шифр — ChaCha20-Poly1305, ключ панели `/var/lib/qeli/panel-secret.key` (`0600`,
  генерируется автоматически). В users-файле — поле `password_enc` (base64); по
  API **не отдаётся**. Ключ намеренно не входит в создаваемый панелью backup каталога
  `/etc/qeli`; прежний `/etc/qeli/panel-secret.key` автоматически мигрирует при
  обновлении.
- **Компромисс (осознанный):** при компрометации сервера (доступ к ключу + users-
  файлу) эти пароли восстановимы. Это VPN-only креды; так работает большинство
  VPN-панелей. Если нужна модель «только хеш» без переиздания — не задавайте
  пароль через панель/CLI (но тогда Share потребует сброса для каждого).

## 4. Шпаргалка по `[web]`

| Ключ | Назначение |
|---|---|
| `enabled` | включить панель |
| `bind` / `port` | адрес и порт (внешний IP или `127.0.0.1` для SSH-туннеля) |
| `username` / `password_hash` | админ-логин и argon2id-хеш (хеш **обязателен на ЛЮБОМ bind, включая loopback** — пусто = fail-closed, панель не стартует) |
| `tls` | встроенный HTTPS (rustls) |
| `tls_cert` / `tls_key` | свой PEM cert/key; пусто = self-signed авто |
| `allowed_ips` | белый список source-IP/CIDR. Отсутствует, пусто или `""` = любой источник. Дубликаты строк складываются в один список; заблокированному источнику — голый 403 на всех маршрутах |
| `public_host` | дефолтный хост для share-ссылок (можно переопределить в диалоге); ещё и разрешённый CSRF-origin |
| `allowed_origins` | доп. браузерные origin'ы (`host` или `host:port`) для изменяющих запросов — нужны для доступа по LAN-IP / домену / reverse-proxy, иначе логин и сохранения `403` |
| `base_path` | отдавать панель под сабпасом reverse-proxy (напр. `/qeli`); пусто = в корне. См. «Reverse-proxy sub-path» в CONFIG.md |
| `csrf` | CSRF same-origin защита (default `true`); `false` отключает — только на loopback-bind, иначе любой открытый сайт сможет дёргать панель |
| `update_check` | opt-in баннер «доступна новая версия» (default `false`); панель проверяет GitHub в браузере оператора и показывает копируемую команду обновления. См. «Проверка обновлений» в CONFIG.md |
| `session_ttl_secs` | время жизни сессии панели (Max-Age куки + срок токена; default `86400`) |
| `trusted_proxies` | source-IP/CIDR reverse-proxy'ей, чьему `X-Forwarded-For` доверять (для allow-листа и rate-limit); пусто = XFF не доверяется |
| `secure_cookie` | `Secure` на куке (авто при `tls`; вручную — за TLS-прокси) |

Все `[web]`-ключи выше (включая `base_path`, `csrf`, `session_ttl_secs`, `trusted_proxies`,
`update_check`) правятся прямо в **Config → Web UI** — раньше их можно было задать только
ручной правкой INI.

Идентичность сервера, пиннинг ключей, H-1, авторизация по профилям, лимиты,
wire-режимы/REALITY — в [CONFIG.md](CONFIG.md).

### Ручная запись серверного INI и границы ревизии

Форма, INI-редактор, Quick Start, история, CLI-команды записи и Backup/Restore
используют один sidecar lock `<канонический путь конфига>.lock`. Он защищает весь
цикл чтения, проверки и атомарной публикации. Не удаляйте и не заменяйте lock-файл
работающего процесса; `exact` restore сохраняет его inode.

Внешний скрипт или редактор должен удерживать эксклюзивный `flock` на этом же
файле, открытом по каноническому пути, от чтения до окончания записи/rename.
Если редактор не поддерживает такой протокол, сначала остановите Qeli и завершите
параллельные операции панели/CLI, отредактируйте INI, выполните `qeli check-config`
и только затем запускайте службу. Смена уже прочитанного файла определяется по
`expected_revision`; второй read также обнаруживает изменение во время подготовки
сохранения. Это обнаружение конфликта, а не блокировка произвольного root-писателя:
запись без sidecar lock между последней проверкой и rename не защищена.

Сохранение профиля не меняет уже работающие bind/TUN/DNS параметры. Применяйте его
явным restart worker; startup-only поля панели требуют полного рестарта процесса.
Неверный кандидат restart отклоняется до остановки действующего worker. История
применяет допустимые web-поля live, а восстановление архивом требует явного restart.
Подробности проверены общим [runtime-сценарием](../../../scripts/audit_panel_config_lifecycle.py)
и записаны в [реестре D07](../plans/AUDIT-DEBT.md).

## Авторизация API и ограничение попыток

<!-- normative-sync: panel-web-auth-v1 -->

Страницы панели открываются с cookie `qeli_session`. HTTP Basic поддерживается
для `/api/*`; scheme регистронезависим (`Basic`, `basic`, `bAsIc`). Имя пользователя
сравнивается точно, пробелы и двоеточия в пароле сохраняются. Служебный JSON API
не меняет INI как единственный формат конфигурационных файлов.

`[web] brute_force.*` управляет входом администратора и API Basic независимо от
VPN-политики `[auth] brute_force.*`. Блокировка относится к IP клиента; за
настроенным доверенным proxy используется проверенная X-Forwarded-For chain.
Обычный запрос без credentials или с неверной/истёкшей cookie не увеличивает
счётчик попыток. Имя администратора не получает жёсткую глобальную блокировку.

Проверки пароля ограничены общим Argon2 semaphore (2–8 jobs по числу доступных
CPU). После ожидания в очереди IP проверяется повторно: заблокированный источник
получает 429 до вычисления хеша. Уже допущенные jobs могут завершиться; их результат
учитывается до возврата permit, даже если HTTP-клиент отменил запрос.

CSRF применяется к изменяющим API-запросам, включая login и Basic. Origin имеет
приоритет перед Referer; сопоставляются разрешённые host/port. CLI-запросы без
обоих заголовков поддерживаются. `trusted_proxies` также определяет, можно ли
доверять forwarded HTTPS/prefix; прямой клиент не может выдать себя за proxy.

Logout отзывает все ранее выданные сессии администратора через сохранённую
session generation и очищает cookie. Ошибка сохранения возвращает явный 500:
очистка cookie в браузере не является подтверждением успешного отзыва токенов.
При исправных persistent session key/generation результат отзыва переживает restart.
Авторизованная страница входа перенаправляет прямо на канонический корень панели.
TOTP для входа в web-панель не реализован; VPN TOTP — отдельный механизм.

### Ошибка сохранения и подтверждение restart

<!-- normative-sync: panel-transaction-outcomes-v1 -->

Form/INI/Quick Start/history требуют свежий `expected_revision`. Сохранение сначала
публикует приватный rollback snapshot, затем заменяет INI; оно само не перезапускает
worker. После ошибки `published ... persistence is uncertain` файл мог уже измениться:
прочитайте новую ревизию и проверьте INI перед повтором; не считайте ошибку откатом.
Новый пароль и allowlist применяются live, смена пароля отзывает прежние cookie.
Bind/port/base_path/TLS требуют полного рестарта; до него работают startup значения.

`worker restarting` подтверждает отправку команды, готовность проверяйте через status.
Full restart также отвечает до замены supervisor. Если команда отклонена или исход
неопределён, status показывает предупреждение; проверьте unit/journal перед повтором.
После корректного полного рестарта новые listener settings действуют, сессия
сохраняется при исправном persistent session key.


### Повреждённые файлы ключей

<!-- normative-sync: panel-key-storage-v1 -->

Identity, panel-secret и session key читаются как обычные файлы ровно по 32 байта. FIFO, каталоги и оборванные ссылки не считаются отсутствующим ключом и не заменяются автоматически. Ссылки на существующие обычные файлы поддерживаются; чтение само не изменяет их owner/mode. Проверьте права и владельца вручную: сгенерированные файлы приватны (0600), штатный identity-каталог — 0700.

Миграция старого panel-secret выполняется под той же блокировкой, что и создание нового: уже появившийся современный ключ имеет приоритет. Повреждённый или недоступный legacy-файл требует восстановления исходного ключа; удалять его ради генерации нового нельзя, если нужно расшифровывать прежние `password_enc`. При ошибке ключа обратимое хранение нового пароля может быть недоступно; Argon2-хеш остаётся отдельным механизмом входа. Недоступный session key сохраняется без замены, панель использует прежний предусмотренный fallback на ключ процесса и пишет предупреждение: такие cookies не переживут restart.

### API пользователей и действующие подключения

<!-- normative-sync: panel-user-mutations-v6 -->

Тело изменения пользователей/групп/лимитов должно быть объектом; неверные типы не превращаются в Unlimited или успешный no-op. `enabled` — boolean, `bandwidth` — object, password/hash — strings, route gateway — string/null. Конфигурации сохраняются только в INI.

Файловая запись перекрывает одноимённую inline-запись. Удаление такого override запрещено: оно вернуло бы inline-доступ или прежние ограничения группы. Используйте Disable либо удалите inline-определение в server.conf.

После успешной загрузки Users в worker удалённые/выключенные пользователи и запретившие текущий профиль записи теряют открытые TCP/UDP-сессии. Эффективный bandwidth, включая группу, применяется к живой сессии. Ответ API подтверждает сохранение и queued reload; готовность новой авторизации может наступить позже. Периодический sweep перепроверяет права, quota и expiry. `burst_mbps` сохраняется как legacy поле; отдельного burst enforcement нет.

После принятого SIGHUP команды enable-user, disable-user, set-limit и set-bandwidth
используют актуальные inline users/groups. Удалённый inline-аккаунт не возвращается
из стартовой копии; добавленный через reload можно изменять без перезапуска worker.
Отклонённый reload сохраняет предыдущую принятую конфигурацию авторизации.

Изменение эффективного ACL пользователя/группы, `client_subnets` или exit-default
также завершает открытую сессию с прежними правами. Подключитесь заново, чтобы
получить новую политику. Порядок и дубли тех же ACL не влияют на сессию; собственный
ACL перекрывает группу. Снижение `max_sessions` оставляет самые новые устройства
на каждом профиле и отключает лишние старые; изменение bandwidth применяется
без разрыва. `burst_mbps` — только сохраняемое поле совместимости, отдельного
управления burst в текущем data plane нет.

Ожидание lock users-файла ограничено пятью секундами. Ошибка до `rename` сохраняет
старые байты. Если `rename` уже опубликовал INI, а fsync каталога отказал, API
возвращает ошибку с `published=true` и неопределённой долговечностью, перечитывает
базу и пытается поставить reload worker в очередь. `reload_requested` показывает
успех постановки в очередь; это не квитанция применения. Сверьте сохранённый INI
и состояние клиента перед повторной записью. Команды control также перечитывают
опубликованные users и не обещают отсутствующий rollback.

Таблица Users показывает эффективный bandwidth: собственный положительный лимит,
иначе лимит группы, иначе Unlimited. Нулевой собственный лимит восстанавливает
наследование. Legacy burst в форме недоступен для изменения и сохраняется при
редактировании остальных полей; его значение не увеличивает разрешённую скорость.

Замена устройства, держателя fixed-IP или старой сессии при заполненном лимите
завершает прежнее подключение через `session_superseded`. Поддерживающий management
клиент прекращает автоматические попытки; для возврата подключитесь вручную.
Лимит считается отдельно на каждом профиле. Сужение разрешённых профилей
отключает только запрещённые подключения, удаление аккаунта — все его сессии.

Сброс пароля при выдаче ссылки использует ту же обработку опубликованной записи.
Если fsync отказал после rename, проверьте `published`/`reload_requested` и повторите
выдачу ссылки без сброса: сохранённый пароль можно восстановить из базы.
