# Управление UDP-буферами и проверка фактических размеров

Qeli сам запрашивает память UDP-сокетов. Лимит ОС — не размер живого сокета:
результат проверяется через `getsockopt`, журнал и метаданные каждого сокета.
Это относится к UDP-FakeTLS, UDP-padding/AWG и QUIC; TCP сохраняет свою политику
autotuning и не использует UDP-регулятор.

## Где задаётся режим

Клиент — `[qeli]` в клиентском INI; сервер — нужный `[profile:имя]`.
Значения в байтах, не в пакетах. Отдельного нового ключа `auto` нет.

| Настройка | Клиент | Сервер |
|---|---|---|
| Приём | `recv_buffer_size` | `perf.udp.recv_buffer_size` |
| Отправка | `send_buffer_size` | `perf.udp.send_buffer_size` |

- Ключ приёма **отсутствует**: auto, начальный запрос 4194304 (4 МиБ),
  следующие ступени 8/16 МиБ. На сервере старт/потолок могут быть ниже из-за
  общего RAM-бюджета всех UDP worker-сокетов.
- Явное число, включая `4194304`: фиксированный запрос, без автоматического роста.
- Явный `0`: оставить значение ОС; это не auto и не нулевой буфер.
- Максимальный ручной запрос — 67108864 (64 МиБ) на сокет. Сервер также
  проверяет суммарный бюджет с учётом числа сокетов и Linux accounting.
- Отправка по умолчанию `0`: оставить ОС. Автоматического роста send buffer нет.

Пример фиксированного приёмного буфера клиента:

```ini
[qeli]
# Остальные параметры существующего подключения сохраняются.
recv_buffer_size = 8388608
send_buffer_size = 0
```

Пример серверного профиля:

```ini
[profile:udp]
# Остальные параметры существующего профиля сохраняются.
perf.udp.recv_buffer_size = 8388608
perf.udp.send_buffer_size = 0
```

Для возврата auto удалите **строку приёма**, а не заменяйте её на `0`.
Перезапустите соответствующее подключение/слушатель. Настройки из примеров —
фрагменты существующих конфигов, не полные конфиги для запуска.

## Что делает auto и чего не делает

Контроллер примерно раз в секунду учитывает полученный wire-трафик, локальные
socket drops и задержку собственного tick. Измеренная скорость и бюджет паузы
не менее 50 мс определяют потребность; локальное переполнение тоже допускает
переход на следующую ступень. Рост ограничен потолком, уменьшения живого сокета нет.
Сетевые sequence gaps сами по себе не являются поводом увеличивать память.

Работающий UDP-контроллер Qeli **не** меняет `rmem_max`, `wmem_max`, CPU/RAM ВМ,
qdisc или TUN-очереди. Настройка системных лимитов установщиком — отдельная операция.
Запрос best-effort: ОС может отказать или выдать меньше. На Linux проверьте
`sysctl net.core.rmem_max net.core.wmem_max`. Поднимать лимиты следует отдельно,
осознанно и с учётом памяти всех сокетов. Сервер планирует общий безопасный
бюджет в пределах 12,5% `MemAvailable`, а не безусловные 16 МиБ на каждый worker.

Ограниченные попытки роста не повторяются каждую секунду бесконечно. После
изменения лимита ОС надёжный способ применить его — пересоздать сокет
переподключением/перезапуском слушателя. Большой буфер помогает пережить краткую
паузу, но не устраняет постоянную перегрузку или CPU steal гипервизора.

## Автоматическая настройка клиента Linux/OpenWrt в dev

Доработка 2 ноября 2026 находится в исходниках `dev`; ранее собранный кандидат
0.8.4 её не получает без пересборки/обновления. Все архитектуры OpenWrt и режимы
UDP-FakeTLS, QUIC-маскировка, padding/AWG и obfs используют общий контроллер.

При отсутствующем `recv_buffer_size` Linux-клиент проверяет обычный `SO_RCVBUF`.
Если фактический размер меньше запроса, он пробует `SO_RCVBUFFORCE` для своего
сокета и повторяет readback. Требуется `CAP_NET_ADMIN`; root в стандартном
OpenWrt обычно имеет это право. Более высокий глобальный `rmem_max` не нужен
для успешного FORCE, сами sysctl не изменяются. При отказе клиент продолжает
работу с фактическим буфером; запрет прав/неподдерживаемая операция не
повторяется каждую секунду. После успешного FORCE дальнейший рост использует
FORCE, чтобы обычный запрос не уменьшил очередь обратно до системного потолка.

Автоматические клиентские сокеты одного процесса делят бюджет до 12,5%
наблюдаемого `MemAvailable`. Резервирование учитывает удвоенный Linux receive
accounting и фактический send buffer. Рост резервируется до запроса; при
неизвестном readback резерв сохраняется консервативно. При нехватке/неизвестном
объёме памяти новая прибавка не разрешается, существующая очередь не уменьшается.
Ограничение 16 МиБ на auto-сокет сохраняется, фактический запрос может быть меньше.
Кандидат смены сети сохраняет свой контроллер после COMMIT; старый контроллер
удерживает резерв до завершения дренирования старого приёмника.

Явные fixed/`0`, отправка, TCP и политика серверных сокетов сохраняют прежний
смысл. FORCE применяется только к auto-клиентам Linux, а не Android/iOS/macOS/Windows.

## Android и другие клиенты

| Платформа | Может ли ограничиваться UDP-приём | Применимость доработки |
|---|---|---|
| OpenWrt/Keenetic/Linux с `CAP_NET_ADMIN` | Да, в том числе из-за `rmem_max` | Auto-клиент использует bounded FORCE |
| Linux без этого права | Да | Отказ FORCE не прерывает соединение; остаётся диагностика ограничения |
| Обычное Android-приложение | Да, тот же Linux socket-buffer cap и общий UDP-контроллер | VPN-разрешение не выдаёт `CAP_NET_ADMIN`; FORCE в Android-сборке не включён |
| Windows | Недостаточный receive buffer возможен, но Linux `rmem_max` неприменим | Сохраняется обычный auto и проверка `SO_RCVBUF` |
| macOS/iOS | Возможны собственные ограничения socket memory | Сохраняются системные API/readback; Linux FORCE неприменим |

На Android требуется измерить живые `receive_normalized_bytes`,
`receive_clamped` и socket kernel drops. Разрешение VPN и `protect(fd)` управляют
маршрутизацией, но не превращают приложение в root. См. [Android VPN](https://developer.android.com/develop/connectivity/vpn),
[sandbox](https://source.android.com/docs/security/app-sandbox) и [проверку CAP_NET_ADMIN ядром](https://github.com/torvalds/linux/blob/v6.12/net/core/sock.c#L1277).
Само сходство симптомов с роутером не доказывает ту же причину на телефоне.

В изолированной проверке на Windows 10 обычный `SO_RCVBUF` получил полные
4/8/16 МиБ. Это проверка получения буфера на одном ПК, не замер скорости и не
гарантия поведения других устройств. [Winsock SO_RCVBUF](https://learn.microsoft.com/en-us/windows/win32/winsock/sol-socket-socket-options)
и [Apple socket-memory code](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_socket2.c)
описывают отдельные платформенные механизмы.

## Установка и обновление Linux

[Аудит установки/обновления и дефолтов Recordizer 31 октября](../reports/UDP-INSTALL-DEFAULTS-2026-10-31.md).

[Реальная установка/обновление .deb и reboot на 300/301](../reports/DEB-AUTO-REBOOT-2026-10-31.md):
auto 4→16 МиБ и prefer/opportunistic подтверждены до/после reboot; ВМ восстановлены.

Полный установщик задаёт rmem/wmem max 16 МиБ. С 0.8.4 пакет `.deb` также
поставляет `/usr/lib/sysctl.d/60-qeli-udp-buffers.conf`, а `postinst configure`
при первой установке и каждом обновлении поднимает только меньшие runtime-лимиты
до 16777216 и проверяет readback. Более высокие текущие лимиты не понижаются.
Системные default-размеры всех сокетов пакет не увеличивает. Отказ ядра/контейнера
выводится как предупреждение, а не успешная настройка. Правила администратора
в `/etc/sysctl.d` могут переопределить пакетные значения после reboot.

Клиент и сервер с отсутствующими receive-ключами используют auto без ручной
настройки. Явные fixed/0 не мигрируются; клиент получает Recordizer с сервера,
по умолчанию `prefer` + `opportunistic` в 0.8.4. Обновление сохраняет конфиги.
Это гарантия обычного Linux `.deb`/полного установщика, не обещание изменить
лимиты Android/iOS или прошивки роутера: там пределы задаёт платформа.

## Диагностика размеров

При создании сокета и изменении его состояния журнал содержит строку
`UDP socket buffers: {…}`. Она включает:

| Поле | Значение |
|---|---|
| `mode` | `auto`, `fixed` или `os-default` |
| `requested_receive_bytes` / `requested_send_bytes` | Последний запрос Qeli; `0` означает отсутствие явной установки |
| `auto_receive_cap_bytes` | Потолок auto; `0` для fixed/OS-default |
| `receive_os_bytes` / `send_os_bytes` | Фактический `getsockopt` в учёте ОС |
| `receive_normalized_bytes` / `send_normalized_bytes` | Linux/Android: raw / 2; на других ОС — readback без деления |
| `receive_clamped` / `send_clamped` | Фактическое нормализованное значение меньше ненулевого запроса |
| `socket_inode` | Linux/Android inode для сопоставления с `ss`, если доступен |
| `receive_set_method` | `standard`, `force` или `os-default` |
| `receive_force_error` | Код последней ошибки FORCE либо `null` |
| `receive_budget_limited` | Рост ограничен бюджетом автоматических клиентских сокетов |

**Ошибка readback — `null`, а не запрошенный размер.** В частности, успешный
`setsockopt` не доказывает, что ОС выделила весь запрос. Рост считается только
при наблюдаемом увеличении фактического размера. При ограничении/ошибке есть
предупреждение; одинаковое диагностическое состояние не логируется каждый tick.

Linux `ss skmem rb/tb` соответствует `*_os_bytes`. Для явного запроса 4 МиБ
обычно ожидается `rb8388608`; это kernel accounting, не обещание столько же
payload-памяти. При `0` также показываются raw и raw/2, но нулевой запрос не
считается ограниченным ОС. Не путайте raw `rmem_default` нового сокета iperf
с нормализованной метрикой Qeli.

```bash
journalctl -u qeli --since '-10min' | grep 'UDP socket buffers:'
ss -uanmpe '( sport = :4443 or dport = :4443 )'
```

Замените порт на UDP-порт своего профиля. Доступ к PID/inode других пользователей
может требовать root; содержимое пакетов и ключи для этой проверки не нужны.

Подробная карта доступна также:

- Linux CLI: `stats.udp_socket_buffers` в JSON-файле, указанном существующим
  `QELI_CLIENT_STATUS`. Каталог должен быть доступен пользователю клиента.
- Сервер: `udp_socket_buffers` по профилям в ответе существующей команды
  `queue-stats` приватного Unix control socket. Это не новый открытый TCP API.
- GUI не получает нового обязательного поля. Существующие агрегатные FFI/JNI
  counters и layout ABI сохранены; `udp_recv_buffer_bytes` остаётся суммой
  известных нормализованных receive-размеров живых сокетов, а не размером одного worker.

## Как интерпретировать потери

Разделяйте socket kernel drops, внутренние queue/pool drops, TUN drops и loss
приёмника iperf. Даже достаточный буфер может переполниться при паузе обработки.
Глобальные UDP SNMP относятся ко всей ВМ/семейству IP, а не к одному inode.
Рост памяти не доказывает исправления алгоритма, а нулевой счётчик одного слоя
не доказывает отсутствие потерь на остальных.

См. [конфигурацию](CONFIG.md). Подробная карта сокетов дополняет, но не заменяет
проверку CPU, потерь и фактического буфера приёмника при измерении скорости.
