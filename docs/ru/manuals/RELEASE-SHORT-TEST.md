# Короткий лабораторный тест перед релизом

Тест проверяет транспорты и повторяемость производительности на двух выделенных
Linux ВМ. Он заменяет широкое сравнение VPN в регулярной проверке скорости, но
не CI, платформенные/security проверки и обязательные длительные release-soak gates.
Конкуренты и поиск точных UDP-потолков остаются отдельными исследованиями.

## Стенд и сохранность

[Контроллер](../../../scripts/release_short_test.py) работает на рабочей машине,
напрямую через pinned SSH к двум явно заданным гостям. VM300/301 — тестовая лаба;
Proxmox не выполняет тесты, сборки или установки. VM302 — только сборка при
необходимости нового артефакта, не во время измерений.

Нужны Python 3/Paramiko на контроллере, Python 3, iperf3, iproute2 и firewall snapshot
tools в гостях. Тест ничего не устанавливает. SSH-ключ используется на месте,
не копируется; credential/identity fixtures остаются приватными.

Новый запуск — новый `/opt/qeli-release-short-<tag>` на обеих ВМ, с частными копиями
бинарников, конфигами и raw. Preflight фиксирует SHA, boot IDs, ядро/CPU, сеть и хеши
прежних `/opt/qeli-*`. При существующих VPN/TUN/iperf, сборке, эмуляторе, netem
или lock запуск отвергается, чужая работа не останавливается. Нет reboot, пакетов
или тюнинга служб/sysctl/qdisc/offload. Cleanup останавливает только свои process
groups с проверкой PID/start identity. Сеть, firewall, проверяемые sysctl, boot IDs
и прежние файлы должны совпасть до/после. Несовпадение — ошибка, не PASS.

## План версии 1

Основные профили: `tcp-faketls`, `tcp-reality-tls`, `udp-faketls`, `udp-quic`.
Скоростная часть: required, MTU 1400, клиентская/серверная очередь 1000.
Клиент: `gateway=false`, `dns=off`, `ipv6=required`, `reconnect=false` — это
транспортный тест, не DNS/full-tunnel gate. Reality-TLS: genuine H2, handrolled,
без padding/stealth/heartbeat, с traffic shaping. Остальные варианты явно выбирают
свои padding/fragmentation/AWG; heartbeat выключен, idle timeout 300 секунд.
Конфиги каждой сессии и SHA сохраняются.

| Этап | Подключения | Окна |
|---|---:|---:|
| Все 12 профилей, required и off | 24 | 96 |
| Prefer, четыре основных профиля | 4 | 16 |
| Внешний IPv6, четыре профиля | 4 | 16 |
| Старый сервер/новый клиент и наоборот, четыре профиля | 8 | 32 |
| Три скоростных повтора четырёх профилей | 12 | 192 |
| Удлинённые окна четырёх профилей | 4 | 8 |
| Baseline до/после скоростной части | — | 24 |
| Основная матрица | 56 | 384 |

После её конечного baseline и cleanup отдельно выполняется `--mixed-only`:
четыре подключения, по две 30+2-секундные группы IPv4/IPv6. В каждой группе
одновременно идут TCP P4 download и UDP upload на младшей фиксированной ставке
(в пилоте 300 Мбит/с), через разные iperf-порты. Это ещё 16 iperf-измерений
в восьми группах. Перекрытие по timestamps должно быть не меньше 27 секунд.
Итого основной и mixed блоки: 60 подключений, 400 iperf-измерений, около пяти
добавочных минут. Mixed имеет отдельные raw/receipt и собственный cleanup;
два контроллера одновременно не запускаются.

Функциональная сессия: ping внутренних IPv4/IPv6 и четыре двухсекундные передачи:
TCP IPv4 upload, UDP IPv4 download, TCP IPv6 download, UDP IPv6 upload.
Это не все восемь сочетаний; скоростная часть покрывает оба направления обеих семей.
Внешний IPv6 подтверждается независимо от внутреннего ping. Required/prefer требуют
активного PACKET_MUX_V1; off — положительного legacy-маркера без активного mux.
Prefer здесь с поддерживающим клиентом; отрицательные переговоры остаются в protocol gates.

Скоростной повтор — новое подключение. Порядок профилей: прямой, обратный, ротация.
На подключение: TCP P1/P4 и две UDP-ставки, IPv4/IPv6 × upload/download, 16 окон.
`-t 10 -O 2`: 10 измеряемых секунд плюс 2 секунды прогрева. UDP — один поток,
payload 1200; offered rate, receiver goodput и loss раздельны. Upload/download
последовательны, bidir их не заменяет. Ставки фиксируются заранее и не снижаются
по результатам кандидата. Пилот 300/600 Мбит/с — контрольные нагрузки, не заявленные
50/80% ёмкости и не потолки. Новые ставки требуют новой версии плана/эталона.

Удлинённый блок: TCP P4, 20+2 секунды, IPv4 upload и IPv6 download на профиль.
Сам по себе он **не длительный soak и не mixed нагрузка**; короткий mixed блок
описан отдельно выше. Повторные подключения покрывает матрица; обязательные
длительные mixed-load/fault/reconnect/roaming gates сохраняются.
Baseline после функциональной матрицы, перед скоростной частью и после последней
сессии: по три TCP P1 окна на семейство/направление, 10+2 секунды.
Чистое время iperf около 50 минут, плюс SSH/setup/cleanup. 60–90 минут — ориентир,
не таймаут, который превращает неполную работу в PASS.

## Метрики и допуск

[Helper](../../../scripts/release_short_guest.py) раз в 0,5 секунды снимает CPU ВМ/всей
группы Qeli, sampled RSS, TCP_INFO через ss, TUN/qdisc, SNMP и softnet.
SS ограничен тестовыми портами. Нет payload, TLS-ключей и memory dump.
Оконный qdisc-счётчик относится к наблюдаемому TUN, а не всем физическим очередям.
Глобальные UDP SNMP по IPv4/IPv6 не различают сокеты внутри своего семейства.
Ранний helper пилота снимал только `/proc/net/snmp` (IPv4); отсутствие snmp6
отмечается как неизмеренное, не ноль. Актуальный helper сохраняет также snmp6.
FULL_RING не трассируется постоянно; TX drops сами по себе его не доказывают.
[Анализатор](../../../scripts/release_short_report.py) проверяет полноту, три повтора,
baseline и восстановление. RTT/cwnd — выборочные TCP_INFO; p95 nearest-rank по снимкам,
не ICMP и не задержка каждого пакета. CPU/RSS/drops охватывают наблюдение с прогревом;
iperf throughput/retransmits прогрев исключают. Разные интервалы не дают точного
совпадения drops и retransmits.

Начальные пороги требуют калибровки: модуль baseline drift или CV >5% — INVALID;
CV скоростной ячейки >5% — перепроверка; UDP loss >1% в любом повторе — нагрузка
не подтверждена; падение медианы >10% против совместимого эталона — NEEDS_CONFIRMATION.
Ошибка окна/маркера/направления/cleanup — FAIL, не пропуск.

Без эталона успешные критерии дают `PILOT_NO_REGRESSION_BASELINE`, не доказательство
отсутствия регрессии. Нарушение UDP-бюджета/повторяемости даёт `PILOT_REVIEW_REQUIRED`.
`--reference` требует совпадения методики, ставок, ядра/CPU/гостей,
модели CPU, памяти, версии iperf, SHA измерительных controller/helper, qdisc/sysctl/параметров интерфейсов и
нормализованных скоростных конфигов. Новый дефолт нельзя скрывать в сравнении версий.
Previous SHA выбирается явно: старый бинарник с тем же номером не обязательно
является предыдущим опубликованным релизом.

`LAB_COMPARISON_PASS` покрывает только реализованные проверки скорости/потерь Linux.
CPU/RSS/drops/задержки также просматриваются вручную. Анализатор выдаёт предупреждение
при росте sampled RTT p95 больше 20% и 2 мс одновременно, CPU на Мбит/с >15%,
RSS >20% и 10 МиБ одновременно, TUN drop ppm более чем вдвое и на 1000 ppm.
Предупреждения требуют проверки и запрещают автоматический LAB_COMPARISON_PASS;
это начальные эвристики, не доказательство утечки или конкретной причины.
Наблюдатель одинаков для кандидата/эталона, независимая
стоимость не установлена. Подозрительные ячейки перепроверяют парно; первые raw/FAIL
сохраняют, лучшие повторы не выбирают вместо неудачных.

## Запуск

Приватный JSON задаёт `hosts`, `hostnames`, `known_hosts`, `ssh_key`,
`candidate_source` (путь на клиентской ВМ), `candidate_sha256`, `previous_binary`
(пути обеих ВМ), `previous_sha256`, `fixture` (server/client), `outer_server`,
`inner_server` с ключами `"4"`/`"6"`, `outer_iface` и две возрастающие `udp_rates`
на основной профиль. Fixture — один подготовленный серверный профиль с identity
и соответствующий клиентский INI, только с лабораторными credentials.

```bash
python scripts/release_short_test.py --config private-lab.json --tag rc1 --output rc1.json --plan-only
# Необязательная проверка обвязки: четыре профиля, 16 окон, не релизный gate.
python scripts/release_short_test.py --config private-lab.json --tag setup-smoke --output setup-smoke.json --smoke-only
python -u scripts/release_short_test.py --config private-lab.json --tag rc1 --output rc1.json
# Только после complete + baseline after + cleanup основной матрицы:
python -u scripts/release_short_test.py --config private-lab.json --tag rc1-mixed --output rc1-mixed.json --mixed-only
python scripts/release_short_report.py --config private-lab.json --result rc1.json --mixed-result rc1-mixed.json --output rc1-summary.json
python scripts/release_short_report.py --config private-lab.json --result rc2.json --mixed-result rc2-mixed.json --output rc2-summary.json --reference rc1-summary.json --require-pass
```

Если все окна и baseline завершены, а cleanup подтверждён, статус
`measurements_complete_udp_failed` сохраняет полноценные данные: mixed можно выполнить
как следующий диагностический этап, затем собрать отчёт. Это не отменяет FAIL.
После неполного окна или ошибки восстановления продолжать нагрузки нельзя.

Контроллер должен пережить прогон без короткого внешнего foreground timeout.
Checkpoint атомарен между окнами. Слепого resume нет: FAIL сохраняется, cleanup
проверяется, причину разбирают до нового тега. Lock исключает второй экземпляр;
чужие нагрузки также организационно запрещены. Raw остаются на гостях, локально
компактные receipts/summary. Храните хеши runner/helper, версии инструментов, отчёт;
секретные конфиги не коммитьте. Контроллер возвращает ненулевой код при ошибке
измерений/восстановления. Анализатор без `--require-pass` сообщает успешное создание
отчёта, а не допуск релиза; с флагом только LAB_COMPARISON_PASS даёт код 0.
Пилот без эталона, INVALID и NEEDS_CONFIRMATION не проходят этот gate.
Для сравнительного PASS требуются успешные mixed receipts кандидата и эталона;
loss >1% в mixed UDP требует проверки и не даёт автоматического PASS.
Это краткая проверка под совместной нагрузкой, не поиск её устойчивого потолка.
`--smoke-only` имеет отдельную методику/статус SMOKE_ONLY; анализатор полного
плана его отвергает. В актуальном helper client device-id хранится в каталоге
запуска, а не создаётся в глобальном `/var/lib/qeli`.
Релиз автоматически не публикуется.
