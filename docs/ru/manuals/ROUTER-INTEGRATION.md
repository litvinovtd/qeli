# Необязательная интеграция роутера

Статус: экспериментальная реализация в исходниках `dev`. Нужны новый `qeli-client`
с подкомандой `router` и соответствующие шаблоны/пакет. Публичный OpenWrt feed
по-прежнему закреплён на прежнем исходном коммите; он не содержит эту доработку
до отдельного обновления pin/hash при подготовке релиза. Установка на рабочие
роутеры этой разработкой не выполнялась.

## Выбор владельца

Маршрутизация и ограничивающий firewall включаются независимо:

| routing | firewall | Поведение |
|---|---|---|
| external | external | Прежние скрипты, mwan3/PBR или политики KeeneticOS |
| client | external | Таблицы/марки Qeli; допуск и ограничения настраивает администратор |
| external | client | Существующие маршруты + ограничивающий firewall/NAT Qeli |
| client | client | Политики выбранных сетей и ограничивающий firewall/NAT Qeli |

Значения по умолчанию — `external`. Одновременно запускать два контроллера
одного компонента для одной сети нельзя. При конфликте марок/правил Qeli
отказывает в применении, а не переписывает чужие правила.

Процесс VPN и контроллер политик разделены. Перезапуск/остановка VPN не удаляет
VPN-only guard. Наличие процесса отдельно от фактического состояния туннеля:
`connecting`, `connected`, `reconnecting`, `stopped`, `error`. Отсутствующий,
устаревший или чужой статус означает «статус недоступен». Для Connected
проверяются поколение процесса, загрузка ОС, namespace, ifindex, UP и наличие
согласованных адресов. Для OpkgTun это означает ожидание назначения адреса NDM;
Qeli не присваивает себе владение интерфейсом KeeneticOS.

## Что реализовано

- Выбор существующих Linux-устройств и исходных подсетей: `direct`, `vpn_only`,
  `vpn_fallback`. Явные разрешённые локальные префиксы сохраняются; INPUT и
  административный доступ не меняются. Разрешение forwarding в fw4/NDM остаётся
  у платформы. Отдельную Wi-Fi-сеть этот код не создаёт.
- Динамический выбор свободных таблиц, приоритетов и поля conntrack-mark.
  Ответы на входящие соединения закрепляются за WAN/TUN; работающие соединения
  остаются на прежнем WAN при возврате предпочтительного. Отказ физического
  провайдера не переносит обычную TCP-сессию между разными внешними IP.
- Отдельные привязанные к интерфейсу и таблице ICMP-пробы WAN/TUN, пороги
  отказа/восстановления. Проверка интернета WAN требует маршрута подходящей
  семьи. Адреса/шлюзы читаются заново; таблицы не очищаются при каждом цикле.
- Защита от обхода VPN через WAN IPv6 для VPN-сетей. Это консервативный режим:
  IPv6 fallback в WAN не предоставляется. IPv6 через TUN зависит от плана сервера.
- Независимый 120-секундный watchdog для изменений политик. Без подтверждения
  возвращается последняя подтверждённая политика; процесс VPN не перезапускается.
  Отклонённая конфигурация не применяется повторно из старого UCI при перезапуске.
- Создаваемые таблицы/цепочки помечены владельцем; контроллер не делает
  `flush ruleset`, не меняет TUN/IP-адреса и не удаляет чужие INPUT-правила.

## OpenWrt

В LuCI → Qeli → Router integration выбираются владельцы и задаётся JSON.
Это расширенная настройка, пока не пошаговый мастер. Сначала отключите
software/hardware flow offload и подтвердите это `offload_disabled: true`.
Для маршрутизации клиента нужны `gateway=0`, `kill_switch=0`, `dns=off/system`,
`route_local=0`; пакет сам рендерит `pull_routes=false`.

Пример тела `router_policy` (имена и подсети замените по `router discover`):

```json
{
  "offload_disabled": true,
  "uplinks": [
    {"device": "wan", "probes": ["1.1.1.1", "8.8.8.8"]},
    {"device": "lan1", "probes": ["1.1.1.1", "8.8.8.8"]}
  ],
  "networks": [
    {"device": "br-vpn", "subnets": ["192.168.77.0/24"], "policy": "vpn_only"},
    {"device": "br-lan", "subnets": ["192.168.1.0/24"], "policy": "direct"}
  ],
  "local_subnets": ["192.168.1.0/24"],
  "server_addresses": ["192.0.2.10"],
  "health": {"tunnel_probes": ["1.0.0.1"], "interval_secs": 3, "timeout_secs": 1, "up": 2, "down": 3}
}
```

`192.0.2.10` — пример, не сервер. Укажите все действующие A/AAAA сервера.
Логическое UCI-имя WAN может отличаться от Linux-устройства (`wan2` → `lan1`,
`pppoe-wan` и т. п.). В JSON нужны именно Linux-устройства. Если шлюзы в
нескольких системных таблицах неоднозначны, у uplink задаётся `routing_table`.

Службы: `qeli-guard` (START=17, ранняя блокировка), `qeli-router` (START=18,
независимый procd-контроллер), `qeli` (VPN). Включите `qeli-router` в автозапуск;
выбор управляемого firewall также включает раннюю службу `qeli-guard`.
Пакетный hotplug повторяет применение при ifup/ifupdate; неизменённые
INI/пароль позволяют procd сохранить VPN-процесс при изменении только политик.

```sh
qeli-client router discover
/etc/init.d/qeli-router enable
/etc/init.d/qeli reload
# Проверить доступ НОВЫМ подключением и выход каждой выбранной сети, затем:
/etc/init.d/qeli-router confirm_policy
```

Неподтверждённая политика откатывается. Откат относится к политикам маршрутов и
ограничений, а не к произвольным изменениям сетевых UCI-секций, профиля VPN,
секретов или административного доступа. Смена backend, порядка WAN, имени TUN
или набора выделенных слотов требует сначала явного disable старого контроллера.

Возврат к ручному режиму с очисткой принадлежащих Qeli объектов:

```sh
/etc/init.d/qeli-router disable_policy
```

## Keenetic: обычный TUN и OpkgTun

Оба шаблона `S99qeli` публикуют одинаковый безопасный статус. `status` отдельно
показывает процесс и JSON состояния. Старый ручной NAT остаётся для прежних
конфигураций; при явном выборе нового контроллера он не добавляется вторым
владельцем. Имя TUN в INI, шаблоне и политике должно совпадать.

```sh
umask 077
/opt/bin/qeli-client router example --platform keenetic > /opt/etc/qeli/router.json
# Отредактировать router.json: компоненты, устройства/подсети, пробы и адреса сервера.
/opt/bin/qeli-client router check --policy /opt/etc/qeli/router.json
/opt/etc/init.d/S99qeli policy-start
# После проверки нового административного подключения:
/opt/etc/init.d/S99qeli policy-confirm
```

В INI для управляемой маршрутизации также нужны `pull_routes=false`,
`gateway=false`, `kill_switch=false`, `route_local=false`, `dns=off`.
`router_policy` должен оставаться `null`: маршрутизация исходящего трафика
самого роутера пока принадлежит NDM/внешним правилам. Внешний транспорт Qeli
сохраняет собственную привязку к underlay, включая кандидатов roaming.

`policy-start` создаёт приватный `router.enabled`. Без маркера S99 не подхватывает
случайный router.json. `policy-stop` останавливает только контроллер, сохраняя
guard; `policy-disable` удаляет только его объекты и возвращает внешний режим.
Обычный restart VPN не перезапускает контроллер. После изменения JSON
`policy-start` заменяет контроллер, сохраняя VPN-процесс.

Для VPN-only на Keenetic требуется **реально настроенный в KeeneticOS постоянный
запрет WAN** и `persistent_guard=true`: Entware загружается после сетевых служб,
и не может гарантировать раннюю защиту до монтирования `/opt`. Одного флага
недостаточно. Нужно отключить аппаратное ускорение затрагиваемого forwarding.
Сброс iptables NDM контроллер восстанавливает при следующем цикле, но это не
заменяет постоянную политику прошивки. Нативный NDM-адаптер пока не реализован.
На конкретной модели Keenetic работа ещё не проверена.

## Пароль и обновление

OpenWrt: `retain_secrets=0` сохраняет прежнее хранение только в RAM. При
`retain_secrets=1` пароль/obfs-key сохраняются в `/etc/qeli/secrets` с правами
0600 в каталоге 0700 и восстанавливаются перед запуском. Старое RAM-значение
переносится при первом явном включении; последующие записи обновляют копию.
Очистка RAM не удаляет постоянную копию. Для её удаления есть кнопка LuCI или
`/etc/init.d/qeli forget_retained_secrets`.

Keenetic: пароль может задаваться через `password_file=/tmp/qeli-status/password`.
`router store-secret` читает секрет из stdin; `--directory /opt/etc/qeli/secrets
--name pass` сохраняет его, S99 восстанавливает перед стартом. Для временного
пароля используйте `/tmp/qeli-status`; после reboot его нужно ввести снова.
Хранение obfs-key через отдельный файл INI на Keenetic этим изменением не добавлено.
Не передавайте пароль в аргументах командной строки.

OpenWrt sysupgrade сохраняет `/etc/config/qeli` и `/etc/qeli/`, включая выбранные
секреты, identity, pinning и подтверждённую политику. Установленный бинарный
пакет обычный sysupgrade **не гарантирует**: включите пакет в образ или
переустановите совместимую версию. Таблицы/правила и runtime генерируются заново.

## Границы текущей реализации и проверка

DNS-группы DoH/DoT, мастер создания DHCP/SSID, автоматическое обновление всех
DNS-адресов сервера, проверка аутентифицированного Qeli через каждый WAN,
резервные VPN-профили и нативное создание политик KeeneticOS пока остаются
внешними компонентами. JSON намеренно не принимает неизвестные поля. Выбор
ручного режима для этих задач сохраняется; полную автоматизацию из исходного
перечня требований эта версия не предоставляет.

Проверка `scripts/router_policy_netns_fixture.py` требует отдельные mount/net/PID
namespaces и PID=1, работает только с фиктивными ISP/LAN/TUN. Проверяются
VPN-only/fallback, назначение адреса, WAN failover/failback, сохранение TCP/UDP,
watchdog и приватные секреты. Это проверка Linux-политик, не тест скорости VPN
и не сертификация конкретной OpenWrt/Keenetic прошивки.
