# Compact REALITY: INNER_PQ_V1

Реализовано в разрабатываемой 0.8.4; независимый криптографический аудит не проводился.
Обсуждение: [#69](https://github.com/litvinovtd/qeli/issues/69), спасибо
[@Singijeon](https://github.com/Singijeon).

## Как включить

В профиле `mode=reality-tls`:

```ini
[qeli]
reality_compact = true
reality_split = none
```

Адрес, pin ключа сервера, short ID, SNI и credentials остаются прежними. Сначала
обновите сервер, затем native core клиентов. Внешний ClientHello остаётся
компактным, без ML-KEM share; ML-KEM передаётся уже внутри установленного TLS/H2.
Меньший ClientHello не гарантирует один TCP-пакет и сам по себе не гарантирует
обход DPI. TLS random/session_id не используются для размещения ML-KEM-ключа.

Внутренний обмен обязателен для нового compact-клиента: неподдерживаемый сервер,
неверная версия/политика или неудачное подтверждение ключа завершают соединение
до AUTH/JOIN/resume. Автоматического отката к классике, другому алгоритму или
обычному REALITY нет. Все клиенты используют один Rust-обработчик.

Новый сервер сохраняет старый raw-обмен для legacy/noncompact-клиентов. Это не
делает старые compact-клиенты постквантовыми: их тоже нужно обновить. Новый клиент
не может быть переведён на этот legacy-путь сетевой подменой. Форматы обычного
REALITY, plain, FakeTLS, obfs и UDP не меняются.

## Формат и защита от downgrade

Внутри TLS/H2 передаются два фиксированных сообщения:

| Направление | Состав | Размер |
|---|---|---:|
| Клиент → сервер | 32 нулевых байта, header(32), X25519 public(32), ML-KEM ek(1184) | 1280 байт |
| Сервер → клиент | header(32), X25519 public(32), ML-KEM ciphertext(1088) | 1152 байт |

Нулевой префикс не является допустимым legacy X25519-ключом. Сервер распознаёт
его только во внутреннем REALITY-carrier, не в plain. После распознавания ошибки
обмена не переводят парсер обратно в legacy.
Body — собственный формат INNER_PQ_V1, не TLS key_share: X25519 здесь идёт первым.

Header, смещения в байтах; числа big-endian:

| Байты | Значение |
|---|---|
| 0..8 | `QELIPQ\0C` для клиента, `QELIPQ\0S` для сервера |
| 8..10 | версия `1` |
| 10..12 | группа `0x11ec` (X25519MLKEM768) |
| 12..14 | политика `3`: PQ и static binding обязательны |
| 14..16 | размер body: `1216` у клиента, `1120` у сервера |
| 16..32 | резерв, строго нули |

Проверяется каждый байт header. Неизвестные версии, алгоритмы, флаги и длины
отклоняются. Размер буфера фиксирован, не берётся из недоверенного сообщения.
Low-order X25519-ключи и некорректные ML-KEM ek отклоняются. Некорректный ciphertext
полной длины обрабатывается implicit rejection ML-KEM, затем отклоняется проверкой
AEAD. Неполные сообщения ограничены существующим общим handshake-deadline.

## Выработка ключей и авторизация

Полный внутренний transcript включает domain, оба сообщения целиком и pinned
статический public key сервера. Он покрывает роли, версию, алгоритм, обязательную
политику, все public shares и ciphertext. Используются существующие X25519,
ML-KEM-768, HKDF-SHA256 и PacketCodec AEAD, без новых зависимостей или ABI.

```text
T    = SHA256("qeli-reality-inner-pq-v1 transcript\0" || C || S || server_pin)
PRK  = HKDF-Extract("qeli-reality-inner-pq-v1", X25519_ee || MLKEM_ss || X25519_es)
root = HKDF-Expand(PRK, "transcript-bound-session-root\0" || T, 32)
```

Из `root` как HKDF PRK выводятся отдельные ключи направлений, resume, CID и control
через существующие Expand-labels. Domain отделён от legacy KDF. Static binding
в v1 обязателен даже при `bind_static=false`. Для ML-KEM shared-secret буферов,
IKM и root применяются zeroizing-обёртки; session material и приватные ключи
сохраняют существующую zeroize-защиту. Это best-effort, не гарантия отсутствия
копий в регистрах или после оптимизаций компилятора.

Сервер отправляет существующее доказательство личности в AEAD-записи под новым
гибридным ключом. Клиент сначала расшифровывает её, проверяет pinned-идентичность
и политику доверия платформы, и только затем отправляет AUTH/JOIN/resume. Первая
валидная клиентская запись подтверждает серверу ключ обратного направления до
авторизации. Весь полезный трафик использует новые ключи. Resume-secret основной
сессии тоже выводится из PQ-root; каждый новый compact-carrier повторяет PQ-обмен.

Transcript относится к внутреннему обмену, не к TLS exporter. Внутренний
аутентифицированный сеанс не полагается на сохранение секретности внешнего TLS
при будущем взломе классического X25519. Возможность пересылать непрозрачный
шифротекст не устраняется; отдельная exporter/channel-binding гарантия не заявлена.

## Что гарантируется, а что нет

Цель — защита конфиденциальности от «записать сейчас — расшифровать потом», пока
ML-KEM остаётся стойким. Личность сервера всё ещё аутентифицируется **классическим
X25519**, не постквантовой подписью: защита от активного квантового противника не
заявляется. Независимый криптографический review желателен перед такими заявлениями.
Адреса, размеры, время и объём трафика остаются наблюдаемыми.

Есть независимый KDF known-answer fixture `conformance/inner-pq-v1.json` (Python
stdlib HKDF), проверки фрагментации IO, low-order keys, изменения версии, группы,
политики, длины, ciphertext/proof/pin, отказа trust policy и отсутствия AUTH/legacy
retry после ошибки. Проверяется AUTH и обмен данными через настоящий TLS/H2 при
классическом внешнем TLS. Реализация: `protocol/inner_pq.rs`, `crypto/derive.rs`,
`transport_core/session.rs`, `client/mod.rs`, `server/handler.rs`.

Примитивы: [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final),
