# Подключение к внешнему TUN или TAP

Подключите Linux-клиент Qeli к интерфейсу, который создаёт и обслуживает другой
контроллер. Qeli переносит пакеты; внешний владелец отвечает за L3-настройку и
сетевую политику. Типичный пример — Keenetic OpkgTun.

[Каталог и подготовка](README.md) · [English](../../eng/scenarios/EXTERNAL-TUN.md)

## Разделение ответственности

| Действие | Кто выполняет |
| --- | --- |
| Создать/удалить TUN/TAP | Внешний владелец |
| Link up, MTU, адреса и префиксы | Внешний владелец |
| Маршруты, DNS, NAT и firewall | Внешний владелец |
| AUTH, шифрование и передача пакетов | Qeli |
| Сообщить адреса IPv4/IPv6, префиксы, MTU и поколение | Qeli через `QELI_TUNIP_FILE` |

Клиент и владелец должны использовать один сетевой namespace. Нужны совместимый
тип TUN/TAP и права на `/dev/net/tun`. Состояние `IFF_NO_PI`, отсутствие
`IFF_VNET_HDR` и режим очередей должны соответствовать поддерживаемому attach;
не заменяйте интерфейс, пока клиент ещё владеет его открытым descriptor.

## Подготовка владельцем

Для примера `ext0` и штатного пользователя `qeli`, только если интерфейса ещё нет:

```sh
sudo ip tuntap add dev ext0 mode tun user qeli
sudo ip link set dev ext0 mtu 1400 up
sudo install -d -o qeli -g qeli -m 0700 /run/qeli-ext
```

Не выполняйте эту процедуру поверх интерфейса прошивки. Для него используйте
штатный контроллер. `1400` здесь — пример: согласуйте MTU с сервером и путём.
Для IPv6 внутренний MTU не должен быть ниже `1280`; поддержка меньшего внешнего
UDP-пути не означает, что внешний владелец может задать такой же MTU интерфейсу.

## Конфигурация клиента

Сохраните полный рабочий профиль подключения, добавив:

```ini
[qeli]
dev = ext0
device_type = tun
dev_attach = true
gateway = false
forward = false
gateway_nat = false
exit_node = false
dns = off
```

Для настоящего внешнего TAP задайте `device_type=tap` и подготовьте совместимый
TAP тем же владельцем. **Не задавайте `tun.tx_queue_len`**: очередь принадлежит
внешнему владельцу; явное сочетание с attach отклоняется, даже со значением `1000`.
`exit_node=true` с attach запрещён.

В окружении процесса или существующем unit Linux-клиента:

```ini
[Service]
Environment=QELI_TUNIP_FILE=/run/qeli-ext/ext0.ip
```

Это drop-in **клиентской** службы, не инструкция заменить серверный `qeli.service`.
`QELI_TUNIP_FILE` — переменная окружения, не INI-ключ. Не путайте attach по имени
с внутренним платформенным контрактом `QELI_PLATFORM_TUN_FD`.

## Адрес и маршруты после AUTH

Запустите владельца интерфейса, затем клиент. В 0.8.3 и текущей dev файл публикуется
после успешных шагов применения аутентифицированного NetworkPlan. Это **несколько
строк**, а не один IPv4. Пример dual-stack плана:

```text
10.9.0.2
ipv4=10.9.0.2/32
ipv6=fd71:e1:8000:102::2/128
mtu=1400
generation=7
```

Первая строка — основной адрес без префикса для совместимости; в IPv6-only плане
это IPv6, а не IPv4. Строки `ipv4`/`ipv6` появляются только для выданных семейств.
Именованные поля содержат адреса TUN **с их префиксами**, не размеры адресных пулов.
В частности, `/32` и `/128` допустимы для L3 TUN: не заменяйте их на `/24` или `/64`.

Контроллер читает файл один раз в снимок и разбирает данные, а не выполняет их
через shell (`source`/`eval` запрещены). Проверьте адреса по ожидаемым пулам,
допустимость префиксов и MTU, наличие нужных семейств и соответствие текущему
запуску. `generation` различает повторные AUTH внутри адаптера, в том числе с тем
же адресом, но может сбрасываться при пересоздании адаптера. Это не глобальный ID
и не heartbeat: наличие файла не доказывает, что прежняя сессия ещё жива.

Для автоматического apply/reconnect используйте согласование владельца с writer,
описанное в [Keenetic OpkgTun](../../../release/keenetic/opkgtun/README.md), включая
publication-lock для текущей dev. Одного чтения файла недостаточно, чтобы исключить
смену плана во время применения. Не удаляйте lock с неопределённым/живым владельцем.

Например, только если свежий план действительно содержит `ipv4=10.9.0.2/32`,
владелец может вручную назначить:

```sh
sudo ip address add 10.9.0.2/32 dev ext0
```

После этого владелец устанавливает нужные маршруты и firewall, сохраняя физический
маршрут к серверу вне туннеля. Сам `gateway=false` не создаст split-маршруты в
attach-режиме. Поле `ipv6`, если оно есть, сообщает адрес с префиксом, но владелец
всё равно сам применяет его и IPv6-политику. Файл не перечисляет маршруты, DNS и
правила firewall; их нельзя восстановить только из адресов и MTU.

## Проверка и остановка

Проверьте `ip -details link show dev ext0`, `ip address show dev ext0`, маршруты к
серверу и целевому ресурсу, журнал attach и реальную передачу. Сначала штатно
остановите Qeli, затем снимите **свою** политику владельца и удалите интерфейс,
если именно вы его создавали. Qeli сам не удаляет заимствованный интерфейс.

## Откат

При откате к обычному режиму уберите `dev_attach`, окружение адресного файла и
параметры внешнего владельца; не создавайте обычный TUN поверх ещё занятого `ext0`.
Менеджер внешнего TUN видит пакеты до шифрования — он входит в доверенную базу.
