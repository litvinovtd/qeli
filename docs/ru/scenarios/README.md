## Перед настройкой

Сценарии соответствуют задачам [раздела сайта](https://qeli.ru/docs/scenarios/), но
содержат отдельные процедуры настройки. Основная опубликованная база примеров —
**0.8.3 Beta**; **0.8.4 — разработка**, а не доступный по умолчанию пакет.
Мануал цепочки отдельно отмечает изменение `post_up`, требующее 0.8.4.
Наличие инструкции не означает, что каждая ОС и топология прошла новый runtime-прогон.

Сначала установите сервер и клиент по [GETTING-STARTED](../manuals/GETTING-STARTED.md)
и добейтесь обычного подключения. Сохраните работающие transport/auth-параметры:
`server`, `proto`, `mode`, `key`, `sni` и `reality_sid` должны соответствовать профилю.
Берите ключ и `qeli://` из доверенного канала, не отключайте `bind_static` ради примера.

В сетевых фрагментах `[profile:main]` — условное имя **существующего** профиля.
Замените его на своё, а строки объедините с текущей секцией; не добавляйте второй
listener на уже занятый адрес/порт. Фрагменты не заменяют полный серверный конфиг.
Не дублируйте `[qeli]` или `[user:*]`: редактируйте соответствующие секции.
Адреса `10.9.0.0/24`, `192.168.50.0/24`, `192.168.60.0/24` и имена интерфейсов —
пример; выберите непересекающиеся с вашими сетями. `203.0.113.0/24` и
`198.51.100.0/24` зарезервированы для документации, не являются списком стран.

Команды управления пользователями и identity выполняйте от владельца службы и
конфигов: для штатного пакета обычно `sudo -u qeli qeli ...`. Не меняйте службу на
root ради этих сценариев. Для Linux-маршрутов, firewall и TUN нужны отдельные сетевые
права; сохраните действующие capabilities и ограничения unit.

Перед изменением сохраните конфиги, `users.conf`, права/владельцев, маршруты и
drop-in службы в закрытом резервном каталоге. Сохраняйте SSH или консоль вне VPN.
Новые пароли создавайте через `add-client` или панель; не передавайте настоящий
пароль через `--password`, историю shell или публичный отчёт.

### Tunnel DNS на Linux

Для `dns=tunnel` Linux-клиенту нужен работающий `systemd-resolved`, используемый
системным резолвером. Qeli проверяет фактические `nameserver` в `/etc/resolv.conf`
(`127.0.0.53`/`127.0.0.54`), а не только имя symlink; одного установленного
`resolvectl` недостаточно. Перед подключением проверьте:

```sh
systemctl is-active systemd-resolved
readlink -f /etc/resolv.conf
resolvectl status
```

Проверьте также содержимое `/etc/resolv.conf`: сторонний upstream рядом со stub
не соответствует этому контракту. Доступ к resolved и нужному network namespace
должен быть у процесса клиента. При несовместимой конфигурации Qeli откажет в
применении DNS, а не начнёт незаметно переписывать чужой resolver.

Если DNS обслуживает NetworkManager/dnsmasq/прошивка, согласуйте его настройку
с владельцем сети по [CONFIG](../manuals/CONFIG.md). `dns=off`/`system` оставляет
системный resolver вне управления Qeli и не является автоматическим безопасным
исправлением ошибки: отдельно обеспечьте маршрут DNS и отсутствие нежелательного
прямого разрешения. Не заменяйте `/etc/resolv.conf` вслепую на удалённом хосте.

## Общая проверка и откат

До перезапуска проверьте оба **полных** конфига:

```sh
sudo -u qeli qeli check-config --config /etc/qeli/server.conf
sudo qeli check-config --client --config /etc/qeli/client.conf
```

Вторую команду запускайте с UID и путём фактического Linux-клиента; в GUI сохраните
полный профиль через штатный редактор. Перезапуск `qeli.service` разрывает соединения
всех его профилей; согласуйте окно и проверьте имя своей службы.

После запуска проверьте журнал, маршрут к целевому IP, DNS, разрешённые и запрещённые
направления, обе семьи IP и поведение при потере связи. Один статус «Подключено»
или успешный ping не подтверждает весь сценарий. Внешний IP проверяется, например,
через `curl -4 https://api.ipify.org` и, при наличии IPv6, `curl -6 https://api64.ipify.org`.
Это сторонние сервисы; вместо них можно использовать свой проверочный endpoint.

Для отката сначала штатно остановите затронутые подключения, верните сохранённые
конфиги с прежними правами и отмените **только свои** добавленные маршруты/правила.
Запустите прежнюю схему и повторите проверку. Не очищайте весь firewall и не удаляйте
журналы DNS/sysctl/route recovery для обхода ошибки: используйте
[восстановление](../manuals/OPERATIONS.md).
