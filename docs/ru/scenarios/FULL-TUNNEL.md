# VPS как full-tunnel VPN

Направьте интернет-трафик устройства через публичный Linux-сервер. Приложениям
не нужен SOCKS/HTTP-прокси; клиент создаёт IP-туннель, сервер выполняет NAT.

[Каталог и подготовка](README.md) · [English](../../eng/scenarios/FULL-TUNNEL.md)

## Схема и требования

`Устройство → Qeli на VPS → WAN VPS → Интернет`.

Нужны рабочий профиль, доступный TCP/UDP-порт, TUN и `iptables` на сервере.
Пример использует пул `10.9.0.0/24`, адрес сервера `10.9.0.1` и WAN `ens3`.
Узнайте настоящий WAN через `ip route get 1.1.1.1`; не копируйте имя интерфейса вслепую.
На собственном VPS проверьте также firewall облачного провайдера.

## Сервер

Добавьте сетевые поля в существующий профиль; transport, ключ и REALITY-поля сохраните:

```ini
[profile:main]
routing.nat.enabled = true
routing.nat.interface = ens3
routing.forward_private = true
dns.enabled = true
dns.listen = 10.9.0.1
dns.upstream = 1.1.1.1
```

`dns.upstream` здесь — явно выбранный администратором резолвер. Замените его своим,
если политика запрещает Cloudflare. Не открывайте серверный DNS на WAN: клиент
должен обращаться к `10.9.0.1` внутри туннеля.

Создайте отдельного пользователя и выдайте ему ссылку на этот профиль:

```sh
sudo -u qeli qeli add-client laptop --profiles main --config /etc/qeli/server.conf
sudo -u qeli qeli share-link laptop --profile main --host vpn.example.com:443 --config /etc/qeli/server.conf
```

Если ограничиваете пользователя через `allowed_networks`, разрешите необходимые
интернет-направления и DNS. Пустой ACL означает отсутствие ограничения, а не запрет.

## Клиент

Импортируйте ссылку с закреплённым ключом и задайте локальную политику:

```ini
[qeli]
gateway = true
kill_switch = true
dns = tunnel
mtu = 0
```

`gateway=true` включает full-tunnel локально; одного серверного NAT недостаточно.
На Android дополнительно включите Always-on VPN и «Блокировать без VPN» в ОС.
На iOS ключ `kill_switch` не реализует системную блокировку; on-demand сам по себе
не является доказательством отсутствия утечек. Условия платформ — в
[CONFIG](../manuals/CONFIG.md).

На Linux сначала выполните [проверку tunnel DNS](README.md#tunnel-dns-на-linux):
нужен используемый системой `systemd-resolved`. Не заменяйте ошибку настройки
резолвера безусловным `dns=off`: это меняет обещанную DNS-политику.

## IPv4, IPv6 и dual-stack

**Dual-stack — IPv4 и IPv6 внутри одного VPN одновременно.** Например, приложение
может обратиться к сайту по IPv4 или по AAAA/IPv6, и обе семьи должны получить
нужный VPN-маршрут, разрешения и рабочий выход. Это не два VPN и не переключение
между основным и резервным транспортом.

Внешнее TCP/UDP-подключение к Qeli независимо от внутреннего трафика: соединение
к IPv4-адресу VPS может переносить одновременно IPv4 и IPv6. И наоборот, подключение
к IPv6-адресу сервера само по себе не выдаёт клиенту IPv6 внутри туннеля.

Для dual-stack серверный профиль задаёт `tun.ip_mode=dual`, IPv4-адрес/пул и
`tun.ipv6_address`/`pool.ipv6.cidr`. Клиент с `ipv6=auto` принимает согласованный
план, но при неполном IPv6-контракте возможен переход к IPv4. Если IPv6 обязателен,
проверяйте с `ipv6=required`: отсутствие поддержки должно вызвать отказ, а не
считаться успешным dual-stack. Адрес IPv6 в TUN ещё не доказывает выход в интернет.

Выберите политику явно. Для IPv6-выхода серверу нужны работающий IPv6 WAN,
IPv6-адрес TUN, отдельный пул и `routing.ipv6.mode=route` либо `nat66` по схеме
[IPV6](../manuals/IPV6.md). ULA-пул сам по себе не маршрутизируется в интернет.
`route` требует маршрутизируемого префикса и обратного маршрута; `nat66` маскарадит
IPv6 через IPv6 WAN. NAT66 не превращает IPv6 в IPv4 и не заменяет NAT64.
IPv4 NAT и IPv6-выход настраиваются отдельно, как и маршруты, ACL и защита при обрыве.
Если IPv6-выход не предоставляется, проверьте, что клиент захватывает или блокирует
IPv6, а не выпускает его напрямую. Не объявляйте full-tunnel безопасным по одному IPv4-тесту.
`ipv6=off` ограничивает согласование Qeli, но не отключает IPv6 всей ОС и само по
себе не доказывает блокировку физического IPv6.

Для split/LAN-сценария dual-stack означает отдельные разрешённые IPv4- и IPv6-сети,
а не обязательно два интернет-шлюза. Проверяйте по каждой семье целевой сервис,
маршрут и DNS; для full-tunnel — ещё внешний IP и поведение при потере VPN.

Пошаговый адресный план, серверный/клиентский фрагменты и проверки:
[IPv4 и IPv6 через один VPN](DUAL-STACK.md).

## Запуск и проверка

1. Проверьте полные конфиги по [общей процедуре](README.md), перезапустите сервер
   в согласованное окно, затем подключите клиент.
2. Внешний IPv4 клиента должен совпасть с адресом VPS. Отдельно проверьте IPv6.
3. Проверьте DNS из используемого приложения: браузерный DoH не обязан использовать
   системный резолвер, даже если его соединение идёт внутри VPN.
4. На Linux посмотрите `ip route get 1.1.1.1`, `ip address` и журнал; серверные
   счётчики NAT должны увеличиваться при загрузке.
5. Имитируйте потерю сервера на тестовом подключении: при требуемом fail-closed
   обычный интернет не должен незаметно вернуться через физическую сеть.

## Откат и типовые ошибки

Отключите клиент, верните исходный профиль и выполните [общий откат](README.md).
Если туннель подключён, но интернет не работает, проверьте WAN/NAT, ACL, forwarding,
DNS и MTU; не выключайте защиту ключа или firewall целиком для диагностики.

Связанные варианты: [только LAN](HOME-LAN.md), [split routing](SPLIT-ROUTING.md),
[выход через домашний узел](EXIT-NODE.md).
