# IPv4 и IPv6 через один VPN

Настройте полный выход устройства в интернет через VPS одновременно по IPv4 и
IPv6. Приложение может выбрать любой из адресов сайта, но оба семейства должны
использовать VPN. Основной пример использует IPv4 NAT и IPv6 NAT66 на VPS.

[Каталог и подготовка](README.md) · [English](../../eng/scenarios/DUAL-STACK.md)

Настройки относятся к опубликованной 0.8.3 и текущей dev 0.8.4. Сначала получите
рабочее обычное подключение по [FULL-TUNNEL](FULL-TUNNEL.md). Ниже меняется сетевая
часть существующего профиля; установка, transport/auth и ключи не заменяются.

## Что означает dual-stack

У клиента два внутренних адреса, например `10.9.0.2` и
`fd71:e1:8000:102::2`. IPv4-пакеты и IPv6-пакеты идут внутри одного VPN, а не двух
параллельных VPN. Это не резервирование TCP/UDP и не автоматическое переключение серверов.

Внешнее соединение с сервером независимо от внутреннего трафика:

| Внешнее соединение с Qeli | Трафик внутри туннеля |
| --- | --- |
| IPv4 TCP/UDP | Может переносить одновременно IPv4 и IPv6 |
| IPv6 TCP/UDP | Также может переносить IPv4 и IPv6 |
| Любое из них, но серверный `tun.ip_mode=ipv4` | Само по себе не предоставляет внутренний IPv6 |

Провайдер клиента может давать только IPv4: внутренний IPv6 всё равно может работать
через доступный IPv4 carrier. Однако **узлу выхода** нужен собственный пригодный
IPv6-интернет. В этом примере выход — VPS; для домашнего выхода условия другие,
см. [EXIT-NODE](EXIT-NODE.md).

## Адресный план

| Параметр | Пример |
| --- | --- |
| Профиль и TUN сервера | `main`, `vpn0` |
| IPv4-пул и адрес сервера | `10.9.0.0/24`, `10.9.0.1` |
| IPv6-пул и адрес сервера | `fd71:e1:8000:102::/64`, `fd71:e1:8000:102::1` |
| IPv4 и IPv6 WAN VPS | `ens3` в примере; могут быть разными интерфейсами |
| Внешний адрес подключения | Уже работающий `vpn.example.com:443` |

Используйте свой непересекающийся ULA-префикс, а не общий пример `fd71:e1:8000::/48`.
Установщик может уже создать уникальный префикс — сохраните его. Для каждого профиля
нужен отдельный `/64`. IPv4-пул без необходимости не меняйте: сохраните резервации,
`pool.exclude` и пользовательские статические адреса в пределах действующих пулов.

ULA — внутренние адреса, не публичный IPv6-интернет. В основном примере NAT66
подставляет публичный IPv6 WAN VPS. Адреса клиентов на L3 TUN могут иметь `/32` и
`/128`: это не ошибка размера пула `/24` и `/64`.

## Подготовьте IPv6-выход VPS

До изменения Qeli проверьте адреса и маршруты самого сервера. Подставьте реальные
интерфейсы, если они отличаются от `ens3`:

```sh
ip -4 address show dev ens3
ip -6 address show dev ens3
ip -4 route show default
ip -6 route show default
sudo iptables -t nat -S
sudo ip6tables -t nat -S
```

Для NAT66 нужны публичный IPv6 на WAN, рабочий IPv6 default route и доступная NAT
таблица `ip6tables` в namespace серверного worker. Одного `fe80::` или ULA на WAN
недостаточно. При получении default route через RA учтите `accept_ra` и forwarding
по [IPV6](../manuals/IPV6.md); не меняйте sysctl массово поверх Qeli.

Проверьте выход **самого VPS** по каждой семье:

```sh
curl -4 -fsS --max-time 10 --noproxy '*' https://api64.ipify.org
curl -6 -fsS --max-time 10 --noproxy '*' https://api64.ipify.org
```

У каждой команды должен быть успешный ответ соответствующего семейства. Команды
используют публичный сервис и сообщают ему исходный IP; при необходимости замените
его своим проверочным endpoint. Семейства endpoint описаны в
[документации ipify](https://www.ipify.org/). Неудачный IPv6-тест VPS сначала
исправляется на уровне провайдера/WAN, а не добавлением адреса в VPN-пул.

## Настройте серверный профиль

Сохраните резервную копию по [общей процедуре](README.md). В существующей секции
объедините сетевые поля ниже, заменив имя профиля, интерфейсы и адреса своими.
Не создавайте второй `[profile:main]` и не меняйте ради IPv6 рабочие `bind.*`,
обфускацию, identity, `[auth]`, `[web]` и базу пользователей.

```ini
[profile:main]
tun.ip_mode = dual
tun.name = vpn0
tun.device_type = tun
tun.address = 10.9.0.1
tun.ipv6_address = fd71:e1:8000:102::1
tun.mtu = 1400
pool.cidr = 10.9.0.0/24
pool.ipv6.cidr = fd71:e1:8000:102::/64

routing.nat.enabled = true
routing.nat.interface = ens3
routing.ipv6.mode = nat66
routing.ipv6.interface = ens3
routing.ipv6.ndp_proxy = off

dns.enabled = true
dns.listen = 10.9.0.1
dns.listen_ipv6 = fd71:e1:8000:102::1
dns.port = 53
dns.push_servers = 10.9.0.1, fd71:e1:8000:102::1
dns.upstream = 1.1.1.1, 2606:4700:4700::1111
```

Здесь `dns.upstream` — явный выбор администратора, не скрытый fallback. При другой
DNS-политике замените upstream своими доступными резолверами. DNS слушает адреса
TUN, не открытый WAN. NDP proxy для NAT66 не нужен и должен оставаться `off`.
`1400` — пример внутреннего MTU; IPv6 требует не менее `1280`, но пригодность пути
всё равно нужно проверить передачей данных.

Не настраивайте всё вторым набором ручных NAT-правил: управляемые NAT44/NAT66 и их
очистка принадлежат Qeli. Сохраните правила администратора, не блокируйте необходимый
ICMPv6/PMTU и проверьте firewall провайдера. Открывать внешний IPv6 listener ради
внутреннего IPv6 необязательно — рабочее подключение к IPv4 VPS достаточно.

Пользователь должен иметь доступ к `main`. Если нужен новый пользователь:

```sh
sudo -u qeli qeli add-client laptop-dual --profiles main --config /etc/qeli/server.conf
sudo -u qeli qeli share-link laptop-dual --profile main --host vpn.example.com:443 --config /etc/qeli/server.conf
```

Для существующего пользователя не создавайте повторную учётную запись. Проверьте
его личный и групповой `allowed_networks`: непустой IPv4-only ACL не разрешит IPv6.
Нужны разрешения на фактические назначения и туннельные DNS обеих семей. Добавление
`0.0.0.0/0` и `::/0` разрешает также частные/ULA-адреса, а не только публичный
интернет; для ограниченных ролей используйте [ACCESS-PROFILES](ACCESS-PROFILES.md).

## Настройте клиент

В импортированном рабочем профиле сохраните `server`, ключ, пароль и все параметры
транспорта. Для обязательного dual-stack задайте:

```ini
[qeli]
gateway = true
ipv6 = required
dns = tunnel
kill_switch = true
mtu = 0
apps_mode = all
```

`required` требует внутренний IPv6 в согласованном плане и возможностей адаптера.
Он **не проверяет доступность интернета за IPv6 WAN**: эту проверку выполняйте
реальным запросом. `auto` допустим, если разрешён переход к IPv4, но такой переход
не считается успешным испытанием dual-stack. Уберите ненужные прямые `exclude` и
проверьте оставшиеся LAN-исключения; per-app и split-политика требуют отдельных тестов.

На Linux выполните [проверку tunnel DNS](README.md#tunnel-dns-на-linux).
На Android для блокировки без VPN включите системные Always-on/lockdown; один
INI-ключ не заменяет политику ОС. Ограничения iOS и остальных адаптеров — в
[матрице клиентов](../reference/CLIENT-CONFIG-MATRIX.md).

## Запуск и проверка обеих семей

Проверьте полные конфиги от фактических владельцев файлов. При любой ошибке
остановитесь и исправьте её до перезапуска. После успешных проверок перезапустите
сервер в согласованное окно и подключите клиент:

```sh
sudo -u qeli qeli check-config --config /etc/qeli/server.conf
sudo qeli check-config --client --config /etc/qeli/client.conf
```

Второй путь относится к Linux-клиенту; GUI-профиль проверяйте штатным редактором.
Только после успешных проверок выполните на сервере:

```sh
sudo systemctl restart qeli
```

Перезапуск затронет все профили этой службы.

На подключённом Linux-клиенте замените `vpn0` его фактическим именем TUN:

```sh
ip -4 address show dev vpn0
ip -6 address show dev vpn0
ip -4 route get 1.1.1.1
ip -6 route get 2606:4700:4700::1111
curl -4 -fsS --max-time 10 --noproxy '*' https://api64.ipify.org
curl -6 -fsS --max-time 10 --noproxy '*' https://api64.ipify.org
```

Ожидаются адреса обеих семей и туннельный путь к обоим назначениям. В режиме NAT
внешние адреса должны соответствовать выходу VPS, а не домашнему/мобильному провайдеру
клиента. На Windows используйте `curl.exe`, чтобы не вызвать PowerShell alias;
проверьте обе команды с `-4`/`-6` и маршруты через `Get-NetRoute`. На macOS —
системные маршруты и `curl`; на Android — реальную передачу из приложения и диагностику.

Для DNS отдельно проверьте A и AAAA, например `nslookup -type=A example.com` и
`nslookup -type=AAAA example.com`. DNS по IPv4 может возвращать AAAA — IPv6-транспорт
к DNS-серверу для этого не обязателен. Наличие AAAA в ответе не доказывает доставку
пакетов по IPv6. На Linux проверьте `resolvectl status`; браузерный DoH — отдельно.

На VPS сопоставьте трафик с NAT-счётчиками:

```sh
sudo iptables -t nat -nvL POSTROUTING
sudo ip6tables -t nat -nvL POSTROUTING
```

Затем проверьте TCP-загрузку, выгрузку и UDP по обеим семьям, сон/пробуждение и
reconnect. Один успешный IPv4 speed test или IPv6 ping не подтверждает весь сценарий.

## Проверка отказов

На тестовом профиле в контролируемой среде проверьте два разных события:

1. Потеря связи с VPS: при требуемом fail-closed ни IPv4, ни IPv6 не должны незаметно
   вернуться на физическую сеть клиента. Учитывайте документированные служебные
   исключения kill-switch; это не обещание блокировать каждый системный пакет.
2. Потеря только IPv6 WAN VPS при живом IPv4 carrier: соединение Qeli может оставаться
   активным, но IPv6-запрос должен отказать, а не пойти напрямую через провайдера
   клиента. Работа IPv4 не делает IPv6 исправным.

После восстановления повторите проверки обеих семей и DNS, затем выполните reboot
в согласованное окно и проверьте восстановление адресов, маршрутов и NAT. При
ошибках stop/recovery не удаляйте журналы и не обходите защиту повторным запуском.

## Когда нужен IPv6 без NAT

Если провайдер маршрутизирует отдельный публичный IPv6-префикс к VPS, используйте
`routing.ipv6.mode=route`, IPv6 TUN/pool из этого префикса и согласованный обратный
маршрут upstream. Обновите также IPv6 DNS-адреса, резервации и ACL. Просто сменить
`nat66` на `route`, сохранив ULA-пул, недостаточно для публичного интернета.

В этой схеме внешний IPv6 клиента будет его собственным выданным адресом, а не
адресом WAN VPS. Если провайдер считает клиентский префикс on-link, может потребоваться
NDP proxy; если префикс маршрутизируется обычным L3-маршрутом — нет. Настройка и
проверка топологии приведены в [IPV6](../manuals/IPV6.md). Не переносите на WAN
тот же connected-префикс, которым уже владеет TUN.

Для [домашнего exit-node](EXIT-NODE.md) не включайте NAT66 на VPS по этому примеру:
там обе семьи должны выходить из дома, а на VPS нужен запрет обходного транзита.

## Диагностика и откат

| Симптом | Что проверить |
| --- | --- |
| `ipv6=required` отклоняется | Версии обоих концов, `tun.ip_mode`, контракт адаптера и MTU не ниже 1280 |
| У VPS нет IPv6-интернета | Публичный WAN-адрес, default route, RA и ограничения провайдера |
| IPv6 в TUN есть, интернет не работает | ACL, NAT66/route, IPv6 uplink, firewall и обратный маршрут |
| A работает, AAAA отсутствует | DNS-политику и реальную запись домена; это не проверка IPv6-транзита |
| Малые пакеты проходят, загрузка зависает | MTU, внешний UDP-путь, PMTU/ICMPv6; не лечите отключением IPv6-защиты |
| Внешний IPv6 остался провайдерским | Прямые исключения, маршруты, выбранный процесс/per-app и применение VPN-плана |

Для отката штатно отключите клиент и восстановите полные серверный/клиентский
конфиги из резервной копии с прежними владельцами и правами. Проверьте их и
перезапустите только нужную службу. Не очищайте весь firewall и не удаляйте
recovery-журналы: правилами своего профиля управляет Qeli.

При возврате к IPv4-only отдельно проверьте блокировку ненужного физического IPv6.
Одного `ipv6=off` недостаточно: это политика согласования Qeli, не выключатель
IPv6 всей ОС. Если безопасного IPv6-выхода нет, не объявляйте подключение dual-stack.
