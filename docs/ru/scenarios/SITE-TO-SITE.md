# Две локальные сети через центральный сервер

Свяжите LAN двух площадок через Qeli на VPS без NAT. На каждой площадке Linux-клиент
работает маршрутизатором; обычный интернет площадок остаётся на местных шлюзах.

[Каталог и подготовка](README.md) · [English](../../eng/scenarios/SITE-TO-SITE.md)

## Адресный план

`LAN A → Linux A → VPS Qeli → Linux B → LAN B`.

| Узел | LAN | VPN-адрес |
| --- | --- | --- |
| Площадка A | `192.168.50.0/24`, Linux A: `192.168.50.2` | `10.9.0.2` |
| Площадка B | `192.168.60.0/24`, Linux B: `192.168.60.2` | `10.9.0.3` |
| Сервер | Пул `10.9.0.0/24` | `10.9.0.1` |

Все подсети должны быть разными. Достаточно исходящих подключений площадок к VPS,
поэтому Linux A/B могут находиться за NAT. Этот пример описывает IPv4; для IPv6
нужны отдельные непересекающиеся префиксы и аналогичные маршруты/ACL по [IPV6](../manuals/IPV6.md).

## Сервер и пользователи

В существующем серверном профиле:

```ini
[profile:main]
routing.client_to_client = true
routing.forward_private = true
routing.nat.enabled = false
```

Создайте `branch-a` и `branch-b` через CLI/панель. Затем дополните **существующие**
секции `users.conf`, сохранив их сгенерированные хеши:

```ini
[user:branch-a]
profiles = main
static_ip = 10.9.0.2
client_subnet = 192.168.50.0/24
route = 192.168.60.0/24 gateway=10.9.0.1
allowed_networks = 192.168.60.0/24, 10.9.0.0/24

[user:branch-b]
profiles = main
static_ip = 10.9.0.3
client_subnet = 192.168.60.0/24
route = 192.168.50.0/24 gateway=10.9.0.1
allowed_networks = 192.168.50.0/24, 10.9.0.0/24
```

`client_subnet` регистрирует сеть **за** клиентом; `route` сообщает ему путь к
другой сети; `allowed_networks` разрешает назначения. Используйте отдельного
пользователя для каждого шлюза: повторное подключение с тем же `static_ip` может
заменить предыдущую сессию. Не включайте NAT между LAN, если нужны исходные адреса.

## Linux-шлюзы и локальные роутеры

В обоих рабочих клиентских профилях, со своими учётными данными:

```ini
[qeli]
gateway = false
pull_routes = true
forward = true
gateway_nat = false
dns = system
```

`forward=true` включает маршрутизацию LAN через клиента без маскарадинга.
На обычном Linux Qeli управляет требуемыми sysctl с учётом владения; не подменяйте
это произвольным массовым изменением sysctl. Дополнительно разрешите нужные
направления в firewall шлюзов и конечных хостов.

Если Linux-шлюзы не являются default gateway своих LAN, на основных LAN-роутерах
добавьте и сохраните маршруты:

```sh
# На роутере A, после проверки отсутствия конфликтующего маршрута
sudo ip route add 192.168.60.0/24 via 192.168.50.2
# На роутере B
sudo ip route add 192.168.50.0/24 via 192.168.60.2
```

Это примеры для Linux-роутеров. На реальном оборудовании используйте штатную
постоянную конфигурацию. Запустите сервер, затем Linux A и B; разрешите их
автозапуск штатной службой клиента и проверьте права на приватный INI.

## Проверка и откат

Проверьте TCP-сервис из LAN A в LAN B и наоборот. На принимающем узле должен
сохраняться реальный адрес источника из соседней LAN, а не адрес VPS.
Интернет-IP обеих площадок должен остаться прежним. После reboot каждого шлюза
проверьте восстановление маршрутов и отсутствие лишних NAT-правил.

Если связь односторонняя, проверьте обратный маршрут, ACL, firewall конечного
устройства, перекрывающиеся подсети и регистрацию `client_subnet`.
Broadcast discovery не является тестом L3-связности: имена/обнаружение сервисов
могут требовать отдельного DNS или настройки приложения.

Для отката остановите клиентов, верните пользовательские и серверные поля,
уберите только добавленные маршруты LAN-роутеров и восстановите прежний автозапуск.
Журналы Qeli не удаляйте. Для последовательного интернет-выхода через другой сервер
нужна отдельная схема [CHAINED-SERVERS](CHAINED-SERVERS.md).
