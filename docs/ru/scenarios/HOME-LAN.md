# Доступ только к домашней сети

Подключите удалённое устройство к NAS, камерам или домашним сервисам, сохранив его
обычный выход в интернет. Основная схема — маршрутизация без NAT с видимыми VPN-адресами клиентов.

[Каталог и подготовка](README.md) · [English](../../eng/scenarios/HOME-LAN.md)

## Адресный план

| Узел или сеть | Пример |
| --- | --- |
| Домашняя LAN | `192.168.50.0/24` |
| Домашний роутер | `192.168.50.1` |
| Qeli-сервер в LAN | `192.168.50.2` |
| VPN-пул и адрес сервера | `10.9.0.0/24`, `10.9.0.1` |
| NAS | `192.168.50.10` |

Закрепите LAN-адрес сервера. Его VPN-порт должен быть доступен снаружи: при NAT
домашнего роутера потребуется проброс порта, при CGNAT входящий проброс может быть
невозможен. В таком случае рассмотрите [site-to-site через VPS](SITE-TO-SITE.md).
Удалённая LAN клиента не должна совпадать с `192.168.50.0/24`.

## Сервер и пользователь

В существующем профиле:

```ini
[profile:main]
routing.nat.enabled = false
routing.forward_private = true
route = 192.168.50.0/24 gateway=10.9.0.1 metric=100
```

Создайте пользователя через панель или `add-client`, затем дополните его секцию
в `users.conf`, сохранив настоящий хеш и остальные учётные поля:

```ini
[user:home-laptop]
profiles = main
allowed_networks = 192.168.50.0/24
```

`route` устанавливает направление у клиента, `allowed_networks` разрешает его на
сервере. ACL не создаёт маршрут. Разрешите на firewall сервера и LAN-хостов нужные
сервисы из VPN-пула; не открывайте всё только ради успешного ping.

## Клиент и обратный маршрут

В рабочем клиентском профиле:

```ini
[qeli]
gateway = false
pull_routes = true
dns = system
```

Интернет и системный DNS остаются локальными. Имена вроде `nas.home` не начнут
разрешаться автоматически: настройте доступный домашний резолвер отдельно и
расширьте ACL для него либо проверяйте сервис по IP.

На основном домашнем роутере сохраните маршрут `10.9.0.0/24` через `192.168.50.2`.
Для Linux-роутера временная проверка выглядит так:

```sh
sudo ip route add 10.9.0.0/24 via 192.168.50.2
```

Сначала проверьте, нет ли уже другого маршрута к этому пулу. Постоянную запись
создавайте штатным способом роутера/ОС. На Qeli-сервере маршрут к LAN должен идти
через физический LAN-интерфейс, а не обратно в VPN.

## Проверка

1. Валидируйте конфиги и подключитесь по [общей процедуре](README.md).
2. Откройте реальный сервис NAS, а не только ping. `ip route get 192.168.50.10`
   на Linux-клиенте должен выбрать туннель.
3. Внешний IP клиента должен остаться прежним. Проверьте также физический DNS.
4. На LAN-хосте должен быть виден источник из `10.9.0.0/24`; его ответ должен
   возвращаться через `192.168.50.2`.
5. Убедитесь, что пользователь не получил доступ к назначениям вне ACL.

## Если нельзя добавить обратный маршрут

Компромисс — включить `routing.nat.enabled=true` и задать
`routing.nat.interface` именем **LAN-интерфейса** Qeli-сервера. Клиент оставьте
с `gateway=false`. LAN будет видеть адрес сервера вместо адресов пользователей,
поэтому индивидуальные LAN-правила и журналирование станут менее точными.
Это альтернативная схема, а не замена обратного маршрута в примере без NAT.

## Откат

Отключите профиль, верните исходные поля и ACL. Удалите только добавленный вами
обратный маршрут и сохранённую запись роутера; чужие маршруты не заменяйте.
Если нужен доступ к LAN за удалённым клиентом, используйте [SITE-TO-SITE](SITE-TO-SITE.md).
