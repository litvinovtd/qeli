# Интернет через домашний выходной узел

Используйте публичный сервер как точку встречи, а Linux-клиент дома — как выход
в интернет. Домашнему узлу не нужен входящий проброс порта: он сам подключается к VPS.

[Каталог и подготовка](README.md) · [English](../../eng/scenarios/EXIT-NODE.md)

## Схема и границы

`Потребитель → VPS Qeli → домашний exit-клиент → домашний WAN → Интернет`.

`exit_node` применяется на Linux, не на Windows/Android/iOS. У домашнего узла
должен быть отдельный пригодный WAN с однозначным default route, доступ к TUN и
сетевым capabilities/iptables. Его собственный интернет не направляется в этот VPN.
Ни `gateway_nat`, ни `forward`, ни внешний `dev_attach` с `exit_node` не совмещаются.

## Подготовьте сервер

Создайте отдельный профиль для этого назначения или осознанно измените существующий:

```ini
[profile:main]
routing.client_to_client = true
routing.forward_private = true
routing.nat.enabled = false
```

Создайте пользователей `home-exit` и `traveller` через CLI/панель и сохраните их
действительные учётные поля. Для IPv4 дополните `users.conf`:

```ini
[user:home-exit]
profiles = main
client_subnet = 0.0.0.0/0

[user:traveller]
profiles = main
route = 0.0.0.0/0
```

Первый `/0` регистрирует интернет за exit-клиентом. Второй — серверное разрешение
этому потребителю использовать выход; сервер не пушит этим маркером default route.
Реальные ACL обоих пользователей должны разрешать нужные назначения, включая DNS.
Не выдавайте одну учётную запись нескольким выходным узлам.

Для **exit-only** политики дополнительно запретите прямой форвардинг VPN-пула
этого профиля в WAN VPS средствами вашего firewall. Отсутствие NAT или наличие
пользовательского `/0` само по себе не доказывает такой запрет. Это особенно важно,
если другой профиль/правило уже маскарадит тот же источник.

### Запрет выхода через WAN VPS

Для строгого варианта используйте **выделенный профиль и TUN**. Ниже `main` —
его имя, `vpn0` — фактическое `tun.name`; замените оба по своему конфигу.
Остановите потребителей и отключите их автозапуск на время настройки. Сохраните
правила своего firewall и доступ к VPS по SSH вне VPN. Команды выполняет
администратор **в том же network namespace, где находится TUN серверного worker**.

Пример для хоста с `iptables`/`ip6tables` и доступной таблицей `mangle`:

```sh
sudo iptables -w 5 -t mangle -C FORWARD -i vpn0 -m comment --comment qeli-exit-only-main -j DROP 2>/dev/null || sudo iptables -w 5 -t mangle -I FORWARD 1 -i vpn0 -m comment --comment qeli-exit-only-main -j DROP
sudo ip6tables -w 5 -t mangle -C FORWARD -i vpn0 -m comment --comment qeli-exit-only-main -j DROP 2>/dev/null || sudo ip6tables -w 5 -t mangle -I FORWARD 1 -i vpn0 -m comment --comment qeli-exit-only-main -j DROP
```

Это запрет **всего kernel-транзита из этого TUN**, а не только через текущее имя
WAN. Он остаётся применим при смене uplink и не зависит от наличия NAT. `mangle
FORWARD` обрабатывается до разрешений `filter FORWARD`. Рабочий путь потребитель
→ exit-клиент проходит напрямую между сессиями Qeli, минуя kernel FORWARD VPS.
Без подходящей exit-сессии fallback в kernel будет заблокирован. Поэтому этот TUN
нельзя одновременно использовать для обычного выхода через VPS или транзита в его LAN.

Проверьте наличие обоих правил; при любой ошибке не запускайте потребителей:

```sh
sudo iptables -w 5 -t mangle -C FORWARD -i vpn0 -m comment --comment qeli-exit-only-main -j DROP
sudo ip6tables -w 5 -t mangle -C FORWARD -i vpn0 -m comment --comment qeli-exit-only-main -j DROP
sudo iptables -w 5 -t mangle -nvL FORWARD --line-numbers
sudo ip6tables -w 5 -t mangle -nvL FORWARD --line-numbers
```

**Постоянство обязательно:** внесите эквивалентные запреты в управляемую постоянную
конфигурацию своего firewall с применением **до запуска Qeli/потребителей**, в нужном
namespace, и проверьте их после reboot и reload firewall. Если firewall обслуживает
UFW/firewalld/другой менеджер, настройте эту политику в нём: приведённые ручные команды
не создают постоянную конфигурацию. Пока она не настроена, это только ручной тест —
автозапуск потребителей не включайте. Не сохраняйте вслепую весь живой ruleset Qeli
через `iptables-save`: так можно сделать временные NAT/recovery-правила постоянными.
Не полагайтесь только на `routing.post_up`: ошибка hook сама по себе не гарантирует
отказ запуска профиля. Нужна независимая проверка защиты.

Эти правила не закрывают `INPUT` к сервисам самого VPS и не ограничивают его
`OUTPUT`, включая upstream серверного DNS-прокси. Для этого нужны отдельные ACL и
политика хоста. Не удаляйте запрет, пока потребители ещё могут использовать профиль.

## Домашний Linux-клиент

Сохраните его рабочие transport/auth-поля:

```ini
[qeli]
gateway = false
exit_node = true
gateway_nat = false
forward = false
dns = system
```

Qeli выпускает пришедший из туннеля трафик через выбранный физический WAN и
маскарадит его. Не добавляйте default route через собственный TUN. Не переименовывайте
WAN во время работы; сначала штатно остановите профиль и подтвердите очистку.

## Потребитель

```ini
[qeli]
gateway = true
kill_switch = true
dns = tunnel
dns_servers = 1.1.1.1
```

Здесь администратор явно выбирает публичный резолвер; его запросы также должны идти
через домашний выход. Если использовать DNS-прокси VPS, upstream-запросы самого
VPS могут выходить с его IP, а не из дома. Выберите подходящий вам резолвер и
проверьте его маршрут. Применимость kill-switch зависит от ОС потребителя.

Для потребителя на Linux сначала выполните [проверку tunnel DNS](README.md#tunnel-dns-на-linux).

### Если нужен dual-stack

Здесь это **оба семейства внутри VPN с выходом через дом**, а не IPv6-подключение
к самому VPS. Сохраняя IPv4-строки, добавьте `client_subnet=::/0` у exit-пользователя
и `route=::/0` у потребителя. На VPS нужны `tun.ip_mode=dual`, отдельные IPv6
TUN/pool и разрешения ACL для нужных IPv6-назначений. Не копируйте `nat66` из
обычного VPS full-tunnel: для exit-only IPv6-выход должен быть дома, не на VPS.
`routing.ipv6.mode=off` на VPS блокирует его kernel-транзит, но не прямой путь между
сессиями Qeli; сохраните и независимый запрет выше для обеих семей.

Домашнему exit-клиенту нужен рабочий IPv6 WAN/default route и поддержка `ip6tables`
NAT66: Qeli маскарадит IPv6 там. IPv4-интернета дома недостаточно для IPv6-выхода.
Для обязательной проверки задайте `ipv6=required` на выходе и потребителе, проверьте
внешние IPv4/IPv6 и обрыв каждой семьи отдельно. Пулы, префиксы и MTU — по
[IPV6](../manuals/IPV6.md); различие внешнего и внутреннего IP — по
[FULL-TUNNEL](FULL-TUNNEL.md).

Без этой настройки не разрешайте незапланированный прямой IPv6 на потребителе;
`ipv6=off` не означает отключение IPv6 всей ОС.

## Порядок запуска и проверки

1. Проверьте полные конфиги и постоянные запреты kernel-транзита VPS. Запустите VPS,
   проверьте оба правила ещё раз, затем запустите домашний exit-клиент и потребителя.
2. Проверьте внешний IPv4/IPv6 потребителя: ожидается домашний WAN, не VPS.
3. На домашнем узле проверьте журнал `Exit-node engaged`, выбранный WAN и рост
   счётчиков соответствующих правил `qeli-exit-node`; не удаляйте их вручную.
4. Проверьте DNS и TCP/UDP. Остановите выходной узел: для exit-only схемы
   интернет потребителя должен прекратиться, не перейти на WAN VPS или физическую сеть.
5. Восстановите exit-клиент и повторите проверку после reconnect/reboot. Перед
   автозапуском потребителей подтвердите восстановление запретов, DNS и обеих семей.

## Откат

Остановите потребителя, затем выход штатным способом. Уберите только свои `/0`,
поля и дополнительный firewall-запрет, верните прежнюю политику. Для ручного примера,
после проверки, что это ваши точные правила:

```sh
sudo iptables -w 5 -t mangle -D FORWARD -i vpn0 -m comment --comment qeli-exit-only-main -j DROP
sudo ip6tables -w 5 -t mangle -D FORWARD -i vpn0 -m comment --comment qeli-exit-only-main -j DROP
```

Уберите также только соответствующие постоянные записи своего firewall, иначе
они вернутся при reload/reboot. Не очищайте таблицы целиком. Ошибки очистки Qeli
разбирайте по [OPERATIONS](../manuals/OPERATIONS.md), не удалением журналов.
Это не то же самое, что [цепочка двух серверов](CHAINED-SERVERS.md).
