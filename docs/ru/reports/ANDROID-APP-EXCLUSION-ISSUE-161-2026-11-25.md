# Qeli на Android. Проверка RKNHardering и изоляции приложений

На Android 14 **RKNHardering 2.11.0 видел интерфейс `tun0` даже из списка исключений Qeli**. На стенде с двумя разными публичными IPv4 обычный HTTPS-запрос исключённого приложения получил прямой адрес при выключенном системном kill switch. При включённом kill switch запрос был заблокирован. Адрес VPS показал контрольный запрос из приложения, работающего через Qeli. [Обсуждение Qeli №161](https://github.com/litvinovtd/qeli/issues/161#issuecomment-7159527650) · [RKNHardering 2.11.0](https://github.com/xtclovver/RKNHardering/releases/tag/v2.11.0)

## Пассивная проверка RKNHardering

В изолированном эмуляторе Android 14/API 34 установили неизменённый APK RKNHardering из официального релиза. Его SHA-256 совпал с хешем GitHub `77d64f300534f9068fb8441fc62d8baa97698d2cf5e7b04e5133f0736399fc59`. Утилита работала от обычного UID приложения. Профиль оставлял две локальные проверки — флаг активного транспорта Android и перечисление сетевых интерфейсов. Активные сетевые пробы, сканирование, определение внешнего IP и дополнительные разрешения оставили выключенными. Зафиксировали результат интерфейса RKNHardering, настройки lockdown и диапазоны UID активного VPN по данным Android. [Исходники проверенной версии](https://github.com/xtclovver/RKNHardering/tree/v2.11.0)

| Состояние | Прямой признак | Список интерфейсов |
| --- | --- | --- |
| Qeli отключён, контроль в обеих сериях | `TRANSPORT_VPN: not detected` | VPN-интерфейсов нет |
| RKNHardering работает через Qeli, lockdown выключен | `TRANSPORT_VPN: detected` | `VPN interface detected: tun0` |
| RKNHardering работает через Qeli, lockdown включён | `TRANSPORT_VPN: detected` | `VPN interface detected: tun0` |
| RKNHardering исключён из Qeli, lockdown выключен | `TRANSPORT_VPN: not detected` | `VPN interface detected: tun0` |
| RKNHardering исключён из Qeli, lockdown включён | `No active network found` | `VPN interface detected: tun0` |

В начальном прогоне при подключённом Qeli сборщик результатов прочитал прямой признак, но не прокрутил список до строки с интерфейсом. После исправления прокрутки повтор снял обе строки с экрана. Общий статус повтора сохранён как `FAIL` из-за сбоя `com.android.systemui` при инициализации строки состояния эмулятора до подключения Qeli. Все три наблюдения детектора сохранились и сверены с исходным XML экрана. Серия с исключённым RKNHardering завершилась с кодом `0`. В каждой из этих двух серий отдельные контрольные приложения также прошли по 32 проверки обычных сокетов. 20 запросов пришли напрямую, восемь через VPN и четыре были заблокированы.

При работе через Qeli утилита выдала общий вердикт `Bypass detected` в обоих состояниях lockdown. Когда RKNHardering был исключён из Qeli, общий вердикт в обоих случаях был `No bypass detected`, при этом строка `VPN interface detected: tun0` присутствовала. Внешний IP, возможность отправить пакет через туннель в обход исключения, прямая привязка к TUN и HyperOS за рамками этого теста. [Репорт v2rayNG](https://github.com/2dust/v2rayNG/issues/6465)

## IP Comparison в лабе с общим публичным IPv4

В дополнительной серии использовали тот же официальный APK и включили штатный `IP Comparison` с одним HTTPS-адресом ipify. Android выбирал маршрут приложения. Для проверки маршрута лабораторный приёмник фиксировал IP источника до передачи TLS-потока к ipify. Сертификат проверяла сама утилита, TLS завершался на публичном сервисе. Системный kill switch включали переключателем Android «Блокировать соединения без VPN». [Реализация IP Comparison](https://github.com/xtclovver/RKNHardering/blob/v2.11.0/app/src/main/java/com/notcvnt/rknhardering/checker/IpComparisonChecker.kt)

Два сервера лаборатории имеют общий публичный IPv4. Поэтому совпадение показанного ipify числа само по себе ничего не говорит о маршруте запроса. В этой серии маршрут определяется по адресу источника, который записал лабораторный приёмник. Публичный адрес стенда обозначен в отчёте как `[PUBLIC_IPV4]`.

| Положение RKNHardering | Системный kill switch | Показание IP Comparison | Запрос на лабораторном приёмнике |
| --- | --- | --- | --- |
| Qeli выключен, контроль в обеих сериях | Выключен | `IP: [PUBLIC_IPV4]` | Прямой путь, `198.19.0.1` |
| Приложение работает через Qeli | Выключен | `IP: [PUBLIC_IPV4]` | Через Qeli, `10.86.0.2` |
| Приложение работает через Qeli | Включён | `IP: [PUBLIC_IPV4]` | Через Qeli, `10.86.0.2` |
| Приложение исключено из Qeli | Выключен | `IP: [PUBLIC_IPV4]` | Прямой путь, `198.19.0.1` |
| Приложение исключено из Qeli | Включён | Ошибка DNS и подключения, IP не показан | Ни одного HTTPS-соединения |

Первая попытка остановилась на таймауте прямого IPv6 в обвязке до запуска RKNHardering. Исходный отказ сохранён. Результаты этого раздела относятся к определению публичного IPv4 обычным HTTPS-запросом. Активные пробы обхода изоляции оставались выключенными.

Контроль внутри VPN завершился с кодом `0`. В повторе с исключением общий статус обвязки остался `FAIL` из-за сбоя `com.android.systemui` при запуске эмулятора. Он произошёл в 14:50:47 по часам стенда, а Android включил постоянную VPN в 14:52:25. Все запланированные проверки выполнились после сбоя. Строки RKNHardering сверены с исходным XML экрана, маршрут — с журналом HTTPS-приёмника и диапазонами UID VPN. В обоих прогонах сохранены исходное состояние сети и данные эмулятора.

В каждой серии дополнительно выполнено по 20 обычных проверок сокетов контрольными приложениями. Десять запросов пришли напрямую, восемь через VPN и два были заблокированы. В ответе контрольного HTTPS-запроса через VPN с включённым kill switch утилита показала публичный IPv4. Реле также записало для этого соединения `Broken pipe`, сохранив адрес источника и передачу байтов в обе стороны.

## Повтор с внешним Qeli и двумя публичными IPv4

Android 14 подключался к действующему Qeli 0.8.5 на внешнем VPS по TCP/fake-tls. Выполнили два прогона с официальным RKNHardering 2.11.0. IP Comparison отправлял обычный HTTPS-запрос к ipify. Прямой публичный IPv4 эмулятора обозначен как `A`, независимое измерение с VPS дало `B`. Адреса различались. VPN-подключение подтверждено состоянием Android, принадлежность RKNHardering к туннелю — по UID. Показания IP сверены с XML экрана.

До обеих серий отдельный контроль из Android без VPN подтвердил адрес `A`. Он совпал с независимым измерением с Linux-хоста лабы. Первая попытка контроля остановилась на таймауте ADB, повтор завершился с кодом `0`. Во внешних прогонах HTTPS-запрос шёл к ipify без лабораторного TLS-реле.

| Состояние | Показание IP Comparison |
| --- | --- |
| VPN отключён | `A` |
| RKNHardering включён в Qeli, kill switch выключен | `B` |
| RKNHardering включён в Qeli, kill switch включён | `B` |
| RKNHardering исключён, kill switch выключен | `A` |
| RKNHardering исключён, kill switch включён | Ошибка DNS и подключения, IP отсутствует |
| VPN отключён после обеих серий | `A` |

Обычный HTTPS-запрос исключённого приложения использовал прямой выход при выключенном системном kill switch. Включение kill switch заблокировало запрос. Обе серии завершились с кодом `0`. Первый запуск остановился до подключения из-за отсутствия разрешения Android VPN на чистом эмуляторе. Результат первичного запуска сохранён. Тестовый пользователь удалён. Проверка SHA-256 подтвердила исходное состояние файла пользователей, а PID действующего Qeli сохранился.

### Что осталось вне стенда

Отдельной проверки требуют принудительный выбор TUN исключённым приложением, определение входного адреса VPN по системным данным, внешний IPv6, полная DNS-матрица, рабочий профиль Android, Ozon на HyperOS и экранный Ping. Утверждения об этих сценариях в результатах стенда отсутствуют.

## Какие меры подходят Qeli

| Мера из обсуждения | Применимость |
| --- | --- |
| Закрыть локальный SOCKS/HTTP-прокси, доступ из LAN и API внешнего управления | В просмотренных Android-путях Qeli такого прокси и сетевого API для сторонних приложений нет. Оставить поверхности закрытыми. |
| Убрать автоматически добавленный маршрут к входному IP VPN | Android-клиент привязывает и защищает внешний сокет через `Network.bindSocket()` и `VpnService.protect()`. Автоматический маршрут `/32` или `/128` к этому адресу для работы этого механизма не требуется. |
| Отбрасывать трафик исключённых и неизвестных UID | Это потенциальная дополнительная проверка в Qeli. Сейчас список приложений применяет Android, а Qeli получает из TUN IP-пакет без UID. |
| Перенести Xray TUN, `routeOnly` и правила доменной маршрутизации | Эти параметры относятся к архитектуре v2rayNG. Дополнительную проверку права приложения можно спроектировать на входе в существующий TUN Qeli. |

### Вариант без новых зависимостей

Если поступит подтверждение обхода на Qeli, первый кандидат — **дополнительная проверка владельца TCP/UDP-потока на Android API 29+ в режиме per-app**. Политика действует перед передачей пакета из TUN в транспорт. `VpnService` определяет UID через системный `ConnectivityManager.getConnectionOwnerUid()` и сверяет его с политикой текущего подключения. Отбросы и случаи, когда владельца определить не удалось, учитываются раздельными счётчиками в локальной диагностике.

AOSP ограничивает выдачу UID областью действия текущей VPN. `INVALID_UID` возможен и для исключённого владельца, и при отсутствии записи о сокете. Поэтому первый прототип стоит начать со счётчиков, а строгую блокировку неизвестного UID проверять отдельно. Проверка на каждый пакет создаст лишние вызовы к системной службе. Подходит ограниченный по размеру и времени кеш на поток с очисткой при смене политики или поколения туннеля. Особого покрытия требуют короткие UDP-потоки, повторное использование сокетов, DNS, ICMP, фрагменты и восстановление подключения. Системный API покрывает TCP/UDP с API 29. Для ICMP и API 28 результат такого фильтра нельзя заявлять. [Android API](https://developer.android.com/reference/android/net/ConnectivityManager#getConnectionOwnerUid(int,java.net.InetSocketAddress,java.net.InetSocketAddress)) · [Ограничение видимости UID в AOSP](https://android.googlesource.com/platform/packages/modules/Connectivity/+/75cd08977dce9f5a9bb24846743860e1ed8f0b01/service/src/com/android/server/ConnectivityService.java)
