# Цепочка A → B через INI-хуки: проверка 30 октября 2026

Итог: **17 эксплуатационных сценариев прошли**, включая повторное применение команд,
рестарты, обрыв связи и реальные перезагрузки A/B. Правила и маршруты не дублируются.
Сетевые действия выполняет Qeli из INI; init-система только запускает процессы.
Код и бинарник не менялись, релиз не публиковался. Дополнительно проверены полные
INI с post_down: 8 контрольных состояний, 68 runtime-проверок без отказов.

Этот отчёт сохраняет результаты **0.8.3**. Текущая
[инструкция](../scenarios/CHAINED-SERVERS.md) уже описывает планируемую 0.8.4;
[повтор post_up и автозапуск панели проверены отдельно](CHAINED-SERVERS-084-2026-10-30.md).

[Инструкция в четыре действия с автозагрузкой](../scenarios/CHAINED-SERVERS.md) ·

## Стенд и методика

- A — VM300, B — VM301: по **2 vCPU / 2 GiB**.
- Независимые клиент C и контрольный узел T — VM304/305: по 1 vCPU / 1 GiB.
- Linux amd64 **0.8.3**, SHA-256:
  `9cc1dfb84ccdee3bc0fb23aa3b0745882b0d520a325134112be2575512b62a1d`.
- Использован сохранённый `/opt/qeli-chain-e2e-20261030-r08/qeli`, без новых копий/сборок.
  VM302 не использовалась; вычислений или установки ПО на Proxmox не было.
- TCP FakeTLS на обоих плечах, **Recordizer required**, внутренний IPv4, MTU 1400.
  Heartbeat: 1000 мс, jitter 100 мс; клиентский timeout 3 с.
- Сетевые команды запускались от root в изолированных namespaces. A/B hooks из
  мануала совпадают с сохранённым recipe.json; заменяется только WAN-интерфейс B.
- Серверный routing.post_up устанавливает таблицу/rule на A и NAT на B;
  клиентский post_up — рабочий маршрут на A. Наблюдателя за маршрутом на A нет.
- Клиент A → B: **reconnect=false**, служба **Restart=always / RestartSec=5**.
- Проверки используют малые HTTP-пробы, не новый скоростной бенчмарк. Для каждого
  восстановленного состояния подтверждается адрес выхода B и отдельный собственный WAN A/B.

Всего **17 контрольных состояний**, 79 верхнеуровневых runtime-проверок без отказов.
В каждом состоянии ровно: одна rule 20800, один рабочий default qeli-out metric 10,
один blackhole default metric 32767, по одному заданному IPv4/IPv6 firewall-правилу
на A и одно помеченное NAT-правило на B. Каждое из этих условий проверялось отдельно.

Выполнены **три реальные перезагрузки**: A, B, A; смена boot ID сохранена.
Собственные WAN-пробы A/B сохраняли прежние адреса, в том числе при недоступности
связи A → B и загрузке A до B. Обычный маршрут хоста к 1.1.1.1 не менялся.
Доступность перезагружаемой машины во время её reboot не подразумевается.

## Почему reconnect=false

Предыдущая целевая серия показала: при reconnect=true клиент пересоздаёт qeli-out,
но не повторяет post_up в том же процессе. Рабочий маршрут исчезает.
Это поведение проверенного бинарника 0.8.3. В текущем dev/0.8.4
[клиентский lifecycle](../../../qeli/src/client/mod.rs) уже изменён; его исходники
не выдаются за исходники исторической сборки.

Новый процесс с reconnect=false и Restart=always выполняет hook заново.
Эта комбинация проверена при рестартах, обрыве и reboot и использовалась в прежней
редакции мануала. Вариант 0.8.4 с reconnect=true проверен новой отдельной серией.

## Границы проверки и первичные отказы

- Проверена указанная IPv4-схема, а не все транспорты, IPv6-транзит или произвольные
  пользовательские firewall. Таблица 208/приоритет 20800 должны принадлежать этой схеме.
- Hooks не являются постоянным reconciler: после намеренного удаления маршрута/NAT
  проверялось восстановление **рестартом владельца**, не самопроизвольное исправление.
- Пакетная установка и её ограничения пользователя qeli не квалифицировались этим
  namespace-тестом. Мануал явно указывает root для сетевых hooks и настройку пользователя
  службы; создание пользователей остаётся штатной пакетной процедурой.
- r01 ранней серии: пример содержал неизвестный INI-ключ routing=split-tunnel;
  check-config остановил запуск. Строка удалена, gateway=false/pull_routes=false сохранены.
- r02/r03: TUN-observers потеряли соответственно 79/35 пакетов захвата; серии остановлены.
  Это потери захвата, не VPN UDP loss. Нагрузочные raw сохранены отдельно.
- r04 уточнил lifecycle/reconnect. Финальная эксплуатационная проверка — отдельная
  **operational-r01**, а не переписанный результат предыдущих попыток.

## Дополнение: полные конфиги с post_down

В мануале команды теперь включены непосредственно в полные конфиги B, A и upstream.
Post_up не менялся. Отдельная серия **cleanup-r03** проверила новые команды post_down
на том же SHA/стенде, без изменения ресурсов и без новых перезагрузок:

- Штатная остановка сервера A удаляет его дополнительные firewall-правила, rule 20800
  и резервный blackhole; рабочий маршрут upstream остаётся его собственностью.
- Штатная остановка upstream удаляет только рабочий маршрут, не правила сервера A.
- Остановка B удаляет только помеченный NAT этой схемы.
- Каждый post_down дополнительно вызван трижды при уже отсутствующих записях — без ошибок.
- После запуска/повторного рестарта каждого процесса цепочка вернулась, дублей нет.
- В namespaces A/B установлена политика FORWARD DROP: соединение работает благодаря
  разрешениям самого Qeli при routing.forward_private=true. Глобальный ACCEPT не нужен.
- Собственные WAN-пробы A/B прошли и при остановленных процессах.

Всего 8 контрольных состояний и 68 runtime-проверок, все успешны. Проверки reboot из
основной серии относятся к прежнему варианту без пользовательской очистки post_down;
новое дополнение проверяло остановку/повторный старт, а не повторяло reboot-матрицу.
При SIGKILL/потере питания выполнение post_down не обещается.

Первичные raw также сохранены: cleanup-r01 остановился из-за ошибочного критерия
наблюдателя (iptables -C штатно пишет «Bad rule» для отсутствующего правила, сам hook
завершился успешно). Наблюдатель исправлен на перечисление правил через -S.
Cleanup-r02 остановился до запуска Qeli из-за EEXIST при создании VLAN тестовой сети C;
после cleanup подтверждено отсутствие тестовых процессов/namespaces, затем выполнен r03.
Это отказы сборщика/подготовки стенда, не результаты исправленного финального прогона.

Новые raw: /opt/qeli-chain-hooks-cleanup-20261030-r01 … -r03 на A/B/C/T.
Для r03 сохранены cleanup-recipe.json, конфиги, журналы вызовов hooks и результаты.
Все четыре ВМ восстановлены, отдельный read-only audit подтвердил сеть, службы,
полные qdisc, отсутствие тестовых unit/lease и неизменность SHA.
