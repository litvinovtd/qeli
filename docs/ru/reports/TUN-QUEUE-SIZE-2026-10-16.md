# Размер клиентской TUN очереди Linux

16 октября 2026. На VM300/301 размер клиентской очереди заметно влияет на upload,
но эффект зависит от транспорта. В основной серии Reality-TLS при 500 / 1000 / 2000
пакетах медиана IPv4 upload составила 644,5 / 1150,5 / 1485,2 Мбит/с, а внутренний
TCP RTT — 8,13 / 8,50 / 12,36 мс. Больший буфер помогает пережить всплески, но
не ускоряет reader и не устраняет все потери. Default остаётся `1000`, без auto.

Таблицы ниже относятся к **первому измеренному кандидату**, не к финальной сборке.
После проверки верхней границы допуск изменён с 65535 на 32767; финальный кандидат
проверен отдельно короткой функциональной серией. Исходный код data path между
этими кандидатами не менялся. Это не новая серия сравнения исторических версий.

- Измеренный клиент: `2ede49f35ad0f974568df07863aae101be52be0dbdf3a8b78396036a34a53576`.
- Финальный клиент с диапазоном `1..32767`: `cbf81924bde599ff8400e19a6ca3d628ba3a038eb8cccbc35643ae2855a2762a`.
- Сервер: неизменный архивный Qeli 0.8.2, `a3ab7bc6d857892a4258e22a18a03acd6aefbd0a1f9699be4048b60b2f6d96b6`.
- VM300/server и VM301/client: по 2 vCPU / 2 GiB, Linux `6.12.111+deb13-amd64`.
  IPv4/IPv6 проверялись **внутри** туннеля; carrier шёл по изолированной IPv4-сети лабы.
- Сборка и unit-проверки — только на VM302. На Proxmox-хосте не выполнялись сборки,
  установки или тестовые контроллеры. Старые бинарники, конфиги и результаты сохранены.

Кандидат основан на исходном HEAD `e7a90130f0bd206e549d0757819c92dbd0e8e135`
с доработкой очереди; это не побайтовая реконструкция старого архивного 0.8.2 плюс
единственная правка. Между размерами очереди в основной серии бинарник один и тот же.

## Методика

Три профиля: `tcp-faketls`, `tcp-reality-tls`, `udp-quic`; только Recordizer required,
для Reality — подтверждённый genuine H2. Клиентский INI менялся между 250 / 500 / 1000 /
2000 пакетами. Серверная очередь оставалась 1000, MTU 1400; размеры до/после окна
проверялись по одному ifindex. Остальные настройки внутри профиля не менялись.

На каждый профиль/размер — три повтора TCP P4, IPv4/IPv6 upload/download:
`iperf3 -t 6 -O 1 -P 4`, всего 144 окна. Очереди проходились в прямом, обратном
и смешанном порядке; порядок профилей циклически менялся. Для каждой пары
размер/повтор создавалась новая Qeli-сессия. UDP: 300 Мбит/с, payload 1200,
по одному окну в каждой семье/направлении при 500 и 1000, всего 24.
Ещё 6 TCP-окон без наблюдателей обрамляли наблюдаемое IPv4 upload при 1000.

Использовался отдельный тестовый профиль на основе normalized-конфига. В клиенте
явно заданы `gateway=false`, `dns=off`, `ipv6=required`, `reconnect=false`:
новый клиент не принимает прежний минимальный full-tunnel без резолвера.
Настройки одинаковы для всех размеров; системные сетевые параметры не тюнились.

Наблюдение: `ss`/TCP_INFO 4 Гц и ограниченный metadata-only tracepoint
`kfree_skb`, отфильтрованный по проверенному диапазону `tun_net_xmit`,
единственному тестовому TUN и IPv4/IPv6 EtherType. Payload, TLS-ключи, память
процессов и management-трафик не захватывались. Raw содержит CPU/RSS обеих групп
Qeli, очереди, qdisc и TCP-счётчики; RSS процесса не измеряет память kernel TUN-очереди.

## Потери и задержки при IPv4 upload

FULL_RING — сумма трёх полных trace-окон, включая warmup; retransmits — медиана
iperf после `-O 1`. Их интервалы различаются: эти числа нельзя приравнивать.
Drops ppm — медиана доли TUN TX drops среди отправленных и отброшенных пакетов.
cwnd — медиана per-flow samples, затем медиана повторов.
RTT — smoothed TCP RTT из `ss`; p95 относится к этим samples, не к распределению
задержки каждого пакета или полноценному latency-under-load тесту реального WAN.

различия особенно в QUIC не следует превращать в универсальное обещание ускорения.

## Как выбирать размер

- `250/500`: меньше потенциальный backlog, но всплески раньше теряются.
  Сокращение очереди не гарантирует меньший end-to-end RTT: восстановление потерь
  может перекрыть выигрыш. В Reality при 250 скорость особенно ограничена.
- `1000`: базовый компромисс. В измеренном Reality upload почти сравнялся
  с download; это не оптимум для каждого устройства или канала.
- `2000`: в Reality ещё около 29% к upload относительно 1000, но RTT вырос
  примерно с 8,50 до 12,36 мс. FakeTLS получил около 5,6%, QUIC — около 3,2%
  IPv4 upload; у обоих RTT заметно вырос. Не выбирайте 2000 только ради большего числа.
- `1..32767`: границы допуска, не рекомендуемая рабочая вилка.
  Верхняя граница согласована с [лимитом Linux S16_MAX](https://kernel.googlesource.com/pub/scm/linux/kernel/git/netdev/net/+/66ab4c59b74db7ab53a1c9083feaaede393a96a0).
  Проверка 65535 на первом кандидате выявила отказ Linux и корректный rollback;
  финальная сборка отвергает 32768+ до подключения, а не молча обрезает значение.

Синтаксис, ownership, применение через перезапуск клиента и ограничения
`dev_attach`: [CONFIG](../manuals/CONFIG.md#client-tun-tx-queue).
Очередь — kernel → Qeli, включая исходящие ACK при download; это не H2 window,
не socket buffer и не число `tun.queues`. Причина пауз самого reader этой серией
не установлена, H2 flow control не менялся.

## Проверка финальной сборки и восстановление

На финальном SHA отдельно проверены 17 подключений: четыре размера и отсутствие
ключа во всех трёх профилях, плюс реальные границы 1 и 32767 для Reality с IPv4/IPv6.
Прошли 48 TCP P4 и 12 UDP-окон (`-t 3 -O 1`, UDP 300 Мбит/с при 1000).
Это функциональная проверка, **не три новых повтора скорости финального SHA**.
Default фактически равен 1000. Восемь неправильных значений, включая 32768,
65535, 0, auto и дробное число, отвергнуты до подключения.

Финальные build/unit проверки на VM302: fmt PASS; 2469 library PASS, 61 ignored;
54 config-editor PASS; locked release с jemalloc PASS. Проверки контракта/примеров
в Python и оба языка документации проверяются отдельно. Полный cross-platform CI
не объявляется пройденным: GUI native cores остались прежними, provenance gate
показывает STALE и требует отдельной пересборки/квалификации до релиза.
Keenetic/OpenWrt MIPS/ARM, TAP performance и реальный WAN этой серией не квалифицированы.

Исходный FAIL локального atomic-save OneDrive сохранён. После 71 готового окна
контроллер завершил cleanup; в новом манифесте выполнены только недостающие логические
окна. TCP-окна не переснимались и не отбрасывались, а оставшиеся UDP-окна QUIC
получили отдельную новую сессию. Ошибка старого минимального DNS-конфига и отказ
65535 тоже сохранены отдельно, не выданы за измерения производительности.

После обеих серий проверены исходные boot IDs, SHA старых бинарников, хеши прежних
файлов, адреса, маршруты/rules, firewall, qdisc и выбранные sysctl. До/после
нагрузочных тестов Qeli и TUN отсутствовали; после cleanup это состояние восстановлено.
Финальная проверка дополнительно подтвердила неизменность raw основной серии.
Никакого reboot, netem, смены offload или установки пакетов на VM300/301 не было.

Raw: на VM300/301 `/opt/qeli-tun-queue-range-20261016` и
`/opt/qeli-tun-queue-final-20261016`. Build receipt/артефакты: VM302,
`/opt/qeli-tun-queue-dev-20261016/review-20261016`. Релиз, тег, push и PR
не создавались; старые результаты на Proxmox не перезаписывались.
