# 0.8.4: повтор post_up при reconnect и автозапуск панели

30 октября 2026. **Кандидат прошёл 9 сценариев / 53 runtime-проверки**, включая три
реальные перезагрузки. Отдельной клиентской службы на A нет: используется встроенный
ClientManager, профиль `autostart=true`, клиентский `reconnect=true`.
Это экспериментальная сборка из dev, **не опубликованный релиз и не проверка release/dist**.

[Мануал A → B](../scenarios/CHAINED-SERVERS.md) ·
[Компактные результаты](../../data/chained_servers_panel_084_2026-10-30.json).

## Причина и исправление

В проверенной 0.8.3 первый вызов забирал команду через `self.post_up.take()`.
При полном reconnect TUN пересоздавался, его маршрут исчезал, а команды уже не было.
Ранние наблюдения и raw сохранены в [отчёте 0.8.3](CHAINED-SERVERS-HOOKS-2026-10-30.md).

В [Linux-адаптере](../../../qeli/src/client/mod.rs) 0.8.4 команда теперь сохраняется,
а последнее обслуженное поколение NetworkPlan учитывается отдельно.
Hook разрешается только после успешных platform apply и ACK; повтор одного поколения
не вызывает его снова. Полный reconnect с новым поколением повторяет post_up.
Восстановление carrier, сохраняющее TUN/план, не требует повторной настройки.
Post_down остаётся терминальной очисткой, а не парой на каждый reconnect.

Доверенность локального файла, запрет записи hooks из панели/API, контекст без секретов,
30-секундный лимит и best-effort обработка ошибок не менялись. Post_up должен быть
идемпотентным: в мануале используется route replace и проверки наличия firewall-правил.

## Наблюдения

| Сценарий | PID клиента A | Вызовов post_up, накопительно | Результат |
| --- | ---: | ---: | --- |
| Первый автозапуск менеджером панели | 5261 | 1 | OK |
| Три повторных Connect | 5261 | 1 | OK |
| Перезапуск B №1 | 5261 | 2 | OK |
| Перезапуск B №2 | 5261 | 3 | OK |
| Перезапуск B №3 | 5261 | 4 | OK |
| Disconnect → Connect в панели | 5878 | 5 | OK |
| Реальный reboot B | 5878 | 6 | OK |
| Reboot A при готовом B | 834 | 7 | OK |
| Reboot A до запуска B | 828 | 8 | OK |

При трёх рестартах B один и тот же PID **5261** выполнил hook повторно:
**1 → 2 → 3 → 4**. Рабочий default в table 208 восстановился без ручных команд.
Три Connect для уже живого клиента оставили один процесс и один вызов hook.
Ручной Disconnect не удалил серверную rule; следующий Connect поднял новый клиент.

После reboot B клиент A сохранил PID 5878 и повторил hook. После reboot A профиль
поднялся самим менеджером панели. При загрузке A до B процесс уже существовал и
после запуска B восстановился без смены PID. Изменения boot ID для B/A/A сохранены.

Во всех девяти контрольных состояниях: панель показывает autostart=true/connected/up,
один дочерний клиент, одна rule 20800, один рабочий маршрут и один помеченный NAT;
выход C подтверждён через B, собственные WAN-пробы A/B прошли.
Доступность перезагружаемого хоста во время самого reboot не подразумевается.

## Автоматические проверки и ограничения

- lifecycle_adapter_tests: **13 passed**, в том числе два новых regression cases:
  повтор после нового поколения, отсутствие дублей, отсутствие плана/пустая команда,
  непубликация неуспешного плана и обновлённый контекст.
- hooks: **3 passed / 3 ignored**; ignored не считаются выполненными.
- client_manager: **7 passed**. Проверки native, client-only и FFI compilation прошли;
  release-сборка и форматирование успешны.
- Это функциональная IPv4/TCP FakeTLS квалификация, не скоростной тест, не все 12
  профилей и не подтверждение мобильных hooks (они там не исполняются).
- Запуск проверен от root в изолированных namespaces, не как отдельная приёмка
  пакетной установки, её UID/прав каталогов и systemd hardening на произвольном сервере.
- Сохранение TUN при carrier recovery проверяется unit-контрактом дедупликации;
  отдельная live-матрица hard-resume здесь не проводилась.
- Autostart не стал watchdog для завершившегося процесса: после ручного Disconnect
  он не перезапустился сам, последующий Connect работает. Менялся lifecycle hook, не менеджер.
- Hooks остаются file-only. Наличие autostart в файле соответствует галочке панели,
  но сохранение shell-команд через UI/API не разрешено.
- 0.8.3 не исправлялась задним числом. Для 0.8.4 поведение реализовано в кандидате;
  публикация релиза в этой задаче не выполнялась.
