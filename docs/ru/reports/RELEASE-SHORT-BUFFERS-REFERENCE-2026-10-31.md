# Три повтора короткого теста с проверкой буферов — 31 октября 2026

**120/120 окон завершены, 300/301 восстановлены. Устойчивый эталон всей матрицы
не принят:** `PERFORMANCE_REFERENCE_REVIEW_REQUIRED`. Baseline валиден, но две

  `gateway=false`, `dns=off`, внешний IPv4. Нормализованные конфиги всех трёх

- На профиль три свежих подключения; порядок профилей прямой, обратный,
  сдвинутый. TCP P4 и UDP600: inner IPv4/IPv6 up/down, `-t 10 -O 2`,

  по три на семейство/направление до и после. Не выполнялись P1 внутри VPN,

| Приращение drops сокетов Qeli, server | 10957 | 2702 |
| Server IPv4 UdpRcvbufErrors | 10957 | 2702 |
| Server IPv6 Udp6RcvbufErrors | 2043 | 0 |
| Client TUN TX drops | 7420 | 14780 |

На низком TCP UDP-FakeTLS IPv6 upload также зафиксирован steal:
server 16.69%, client 10.89%. Во втором QUIC TCP IPv6 download — 7.31% / 8.58%.
Это оконные доли из `/proc/stat`, включая прогрев, не мгновенные пики.
Linux определяет [steal как involuntary wait](https://www.kernel.org/doc/html/latest/filesystems/proc.html#miscellaneous-kernel-statistics-in-proc-stat):
доступность CPU ВМ в этих окнах была существенно нарушена. Baseline до/после
не исключает кратковременную конкуренцию за vCPU **внутри** серии.

Одновременно подтверждены переполнения приёмных сокетов Qeli на внешнем IPv4
при реально выданных 4 МиБ и drops клиентского TUN. В UDP-FakeTLS есть также
IPv6 receive errors на приёмной ВМ: глобальный семейный счётчик не является
строгой per-inode атрибуцией iperf. Нельзя объявить все потери только ошибкой
Qeli, только iperf или только малым буфером. Конкретная причина CPU-конкуренции
и причина пауз reader этим тестом не локализованы; соседняя ВМ/процесс не определялись.
Не доказано, что у бинарника нет собственного вклада в чувствительность к таким паузам.

## Вердикт и дальнейшее применение

Для FakeTLS TCP и Reality-TLS получилась хорошая повторяемость; у остальных
прошедших ячеек есть полезные измеренные ориентиры. Однако весь набор нельзя
использовать как принятый автоматический эталон или доказательство регрессии версии.
CV/loss-пороги после просмотра результатов не ослаблялись; «лучшие два из трёх»
не выбирались. Отдельного постфактум steal-порога в допуск не добавляли.

Следующий шаг — обеспечить доступность CPU стенда без смены бинарника/параметров
и адресно перепроверить проблемные IPv6-направления с теми же счётчиками.
Перед принятием полного эталона нужна новая целая согласованная серия, сохранив эту.
Автоматического увеличения буферов, CPU/RAM, смены qdisc или дополнительного прогона не было.
