## Что именно проверено

Обе ВМ начинали без установленного пакета Qeli. Сначала новый пакет установлен
на обе ВМ через настоящий dpkg. На сервере использована штатная `qeli.service`
с пользователем `qeli`, включённая в автозагрузку. Клиент запускался установленным
`/usr/bin/qeli client`; после reboot — повторным запуском CLI. Это не тест
автозапуска клиентского приложения.

Для первого этапа взят поставляемый `server-ipv6.conf.example` с явными
`prefer/opportunistic`. Заменены только лабораторная адресация, локальный DNS,
аутентификация и маршрутизация для связи с самим сервером. NAT выключен, IPv6
routing manual: выход в Интернет/NAT здесь не квалифицировался. Настройки
приёмных/отправляющих буферов Qeli не задавались.

После первого reboot проверка повторена. Затем установлен настоящий `.deb`
0.8.3; подготовлен конфиг **без Recordizer-ключей и UDP buffer overrides**.
VM300 обновлена через `update-qeli-server.sh` с локальным `QELI_DEB`, VM301 —
через dpkg. Конфиги, users DB и identity-файлы сохранили SHA256. После обновления
и ещё одного reboot новые дефолты подтверждены фактическим соединением.

| Случай | rmem/wmem max на обеих ВМ | Recordizer после AUTH | Активный RX сервера | RX клиента |
|---|---:|---|---:|---:|
| Чистая установка | 16 МиБ | prefer / opportunistic | 4→16 МиБ | 4→16 МиБ |
| Reboot после установки | 16 МиБ | prefer / opportunistic | 4→16 МиБ | 4→16 МиБ |
| Обновление с 0.8.3 | 16 МиБ | prefer / opportunistic | 4→16 МиБ | 4→16 МиБ |
| Reboot после обновления | 16 МиБ | prefer / opportunistic | 4→16 МиБ | 4→16 МиБ |

Фактический normalized RX 16 МиБ соответствует raw `SO_RCVBUF`/`ss rb`
**33554432**. Значения проверены по inode; `mode=auto`, cap 16777216,
ограничение ОС отсутствует. Простаивающие серверные worker-сокеты могут остаться
на 4 МиБ — это нормально. Системные `rmem_default/wmem_default` остались
**212992**: пакет не увеличивал default всех сокетов.

В каждом случае прошли внутренние IPv4/IPv6 ping, `PACKET_MUX_V1 active`,
`Recordizer batching: opportunistic` и `plan.data_plane.recordizer_policy=prefer`.
Проверен UDP-FakeTLS; это не новый прогон всех 12 режимов.

## Проверка роста, не скоростной эталон

Восемь UDP-окон: upload/download каждого случая, offered 800 Мбит/с,
payload 1200, 8 с + 1 с прогрева. Чтобы воспроизводимо пройти ступени auto,
приёмнику Qeli дважды задавались контролируемые паузы по 200 мс; PID/exe
проверялись перед сигналами, возобновление выполнялось в finally.
Только сокеты генератора/приёмника iperf явно запрашивали 4 МиБ.

Эти паузы намеренно создают очередь/потери. Скорость/loss окон не являются
release performance reference и не доказывают устранения всех сетевых потерь.
Reboot может сбросить непостоянный qdisc; скоростного A/B между случаями нет.

## Сохранённые отказы обвязки

Первый запуск остановился до трафика: при замене TUN-адреса сборщик оставил
старый `dns.listen`; валидатор правильно отказал. Конфиг исправлен, бинарник
не менялся. Также исправлено ожидание reboot после раннего разрыва SSH.
Первоначальный raw `r01` сохранён, восстановление проверено отдельно.

После восьми окон cleanup gate обнаружил пустые ACCEPT-таблицы и ошибку возврата
FQ rate: JSON использует bytes/s, CLI tc — bits/s. Измерения не повторялись и
не перезаписывались. Возвращены исходные параметры qdisc и отсутствие таблиц;
использовались только iptables/ip6tables, без команд nft. Исходный collector FAIL
и отдельное подтверждение окончательного восстановления сохранены.

ОС пополнены тестовыми событиями — это не побайтовый откат работающей ОС.

Итог для обычной Linux `.deb` установки/обновления: ручные buffer-параметры
клиента/сервера не нужны при отсутствии явных overrides. Администраторские
sysctl.d-переопределения и запреты контейнера остаются отдельными ограничениями.
