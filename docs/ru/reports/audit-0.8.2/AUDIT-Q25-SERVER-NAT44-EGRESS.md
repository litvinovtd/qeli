# Q25-F136: граница NAT44 для выхода через другой интерфейс

25 сентября 2026. База: `2fd8bea4`. Группа D06 остаётся **IN_PROGRESS**.

## Дефект и решение

При `FORWARD ACCEPT` MASQUERADE действует только на выбранном WAN. Если маршрут
к адресу клиента идёт через другой интерфейс, сервер выпускал пакет с
исходным адресом клиента без NAT. Пакетный опыт с двумя WAN подтвердил это
для `10.73.0.2 → 192.0.2.1`. Безусловный запрет `-i TUN ! -o WAN` не подходит:
он одновременно разрывает доступ к приватной сети `10.50.0.0/24` за сервером.

NAT44 теперь ставит обязательное правило `FORWARD DROP` для пакетов из TUN,
выходящих не через выбранный WAN **и направленных вне RFC1918**. Оно
устанавливается выше разрешающих правил хоста, проверяется `iptables -C`
и сохраняется в журнале точного удаления. Правило сопоставляет весь TUN,
включая аутентифицированный `client_subnet`, а не только пул адресов.
Приватные назначения `10/8`, `172.16/12`, `192.168/16` остаются под
существующей политикой firewall администратора: Qeli не добавляет для них
нового разрешения и не применяет MASQUERADE вне WAN. При невозможности
установить защиту запуск NAT44 отказывает.

## Проверки

Изолированная Linux-лаба `.11`, новые NET/mount/PID namespaces. На
`iptables-nft` и `iptables-legacy` пакет от клиента к адресу вне RFC1918
через второй WAN блокируется; к RFC1918 LAN доходит с исходным адресом;
выход через выбранный WAN получает MASQUERADE. Оба backend приняли
повторяемые отрицательные `iprange --dst-range`; `-C` и точное `-D`
прошли. Ни один тест не менял установленные службы лабы или сервер `.10`.

Rustfmt, **19/19** тестов `server::nat`, **11/11** тестов
`nat_firewall_journal`, строгий Clippy и Linux-сборка прошли. Первый
запуск настоящего worker обнаружил, что долговечный журнал firewall
отвергает незнакомый модуль `iprange` ещё до установки правила. Валидатор
теперь допускает только точную форму нового guard: IPv4 `filter/FORWARD`,
три отрицательных диапазона RFC1918, правильный comment и `DROP`; иные
диапазоны, отрицание или IPv6 отвергаются. Имя интерфейса `iprange` само
по себе не распознаётся как модуль.

Повторный настоящий worker (`tcp`, IPv6 `off`) прошёл: правило видно в
`iptables-save`, второй процесс отвергнут, неудачная перезагрузка конфига
сохранила поколение, штатная остановка сняла TUN, правила, forwarding lease
и socket; сетевой снимок до/после совпал. Исходный бинарник после финальной
сборки: SHA256 `d3cf473f75af6eb2f60e017864a33a3de59522c9e864cbbb467206501b4a5b17`.
`nat.rs`: SHA256 `5017508c81c38b03867ee23d1ccb4d3aada7d64dd550f9df80bdb8a2b26ccb8c`.
`firewall_journal.rs`: SHA256 `9a0362dee8affc7fa129cf1eef02023066669020f0d7e762cca13640c421e3f1`.

## Граница

Это правило защищает **не-RFC1918 назначения**. Если другая сеть за сервером
использует публичную, CGNAT или иную адресацию вне RFC1918, такой транзит
на невыбранном интерфейсе будет заблокирован. Для него нужен отдельный
маршрут без NAT либо выбранный WAN. Выход к RFC1918 через другой интерфейс
всё ещё зависит от политики хостового firewall; это не строгая привязка
каждого пакета к физическому WAN. Явный/policy WAN, замена устройства при
сохранении имени, смена маршрутов во время работы и mixed-backend recovery
остаются в D06/D10.
