# Q25-F105: применение NetworkPlan вне async-потока

25 сентября 2026. База `2b3011b7`. D05/D09, Linux и общий контракт подготовки TUN.

## Проблема

`ClientPlatform::prepare_tunnel` был синхронным. Linux применял весь NetworkPlan
в async-потоке: TUN, адреса, gateway/sysctl, маршруты и DNS. Ожидание системного вызова
или дочерней команды задерживало соседние async-задачи; в однопоточном runtime это
останавливало обработку сигнала и публикацию статуса. Нативный адаптер также ожидал
подтверждения NetworkPlan через `std::thread::sleep` внутри транспортного runtime.

Простая отмена `spawn_blocking` не решает владение ресурсами: операция может продолжить
изменять сеть после освобождения внешнего namespace lease, а потерянный результат
с TUN должен сначала откатить настройки в исходном контексте.

## Исправление

Подготовка TUN стала асинхронной в общем внутреннем контракте TCP/UDP. Удалён
неиспользуемый параметр HandshakeNetwork. Нативный адаптер сохраняет прежние проверки
ACK/отмены и 45-секундный срок, но ожидает через async sleep. Публичный C ABI и INI
не изменены; поставляемые библиотеки клиентов требуют отдельной пересборки D11.

Linux передаёт собственные config/plan и cleanup-owners в новый поток. Он наследует
контекст вызывающего потока; открытые fd закрепляют NET/mount namespace. Контекст
проверяется перед работой и перед принятием результата. Переиспользуемого пула потоков
и `setns` здесь нет.

Результат остаётся у worker до решения клиента. При принятии нет новой точки `await`
между решением и передачей результата через `join`: отмена не может потерять успешно
созданный TUN в этот промежуток. При отказе worker уничтожает результат и выполняет
его откат в исходном namespace; клиент асинхронно ждёт завершения этого отката, затем
присоединяет поток. Нормальная остановка ставит общий cancel-флаг и ждёт уже начатую
операцию. Проверка отмены до ACK не допускает подтверждение заведомо остановленной сессии.
Ошибка ACK также запускает отдельный присоединяемый откат; ошибка очистки остаётся
в общем реестре Failures и запрещает успешный restart.

Принудительное уничтожение ожидающего future имеет синхронный `Drop`-fallback:
он закрывает принятие результата и присоединяет worker до освобождения внешнего
владельца. Это сохраняет порядок очистки, но может блокировать вызвавший Drop поток.
Нельзя трактовать этот путь как жёсткую быструю отмену системной мутации.

## Проверки

- 7 новых переносимых тестов: отзывчивость однопоточного runtime, отмена до старта,
  ожидание начатой работы и отката, принудительный Drop, однократная передача ресурса,
  ошибка/panic worker. Ещё 1 Linux-тест проверяет stop во время apply: откат до Running
  и сохранение ошибки очистки; 4 прежних теста адаптера переведены на async.
- 1 новый privileged-тест проверяет наследование NET/mount namespace. После смены
  NET-контекста ожидающего потока результат отвергается и уничтожается в исходных
  NET/mount namespace worker.
- Контрольная копия с синхронным `work()` воспроизводит отказ теста отзывчивости
  (exit 101); исправленная копия проходит (exit 0). Это контрольная мутация helper,
  а не запуск прежнего полного бинарника; production-файлы при проверке не менялись.
- Реальные подключения TCP/UDP × задержка после создания TUN / после `ip link ... up`:
  **4/4 PASS**. Сервер и тестовый клиент используют текущую Qeli; клиентский driver
  запускает библиотеку на однопоточном Tokio runtime с heartbeat каждые 100 мс.
  Во всех случаях heartbeat продвинулся на 7–8 тиков за 800 мс блокировки setup и
  на 8 тиков за 800 мс после SIGTERM. TUN оставался у операции до снятия задержки;
  `post_up` не запускался, итог — `stopped`, exit 0, точное восстановление исходных
  правил и маршрутов, отсутствие TUN и оставшихся `*.state`.
- Выход после снятия барьера: TCP create 0,315 с, TCP up 1,868 с, UDP create 0,365 с,
  UDP up 1,868 с. Это измерения четырёх сценариев, не benchmark или обещание deadline.
- Повторена hostname-матрица mixed firewall: IPv4 nft / IPv6 legacy без firewalld и
  IPv4 legacy / IPv6 nft с firewalld. **38/38 ячеек**, 34 crash/recovery, 1220 основных
  утверждений, 806 вложенных проверок PASS. Все 1088 запрещённых UDP-попыток дали
  нулевую доставку с проверкой счётчиков DROP; 656 разрешённых проб получили ответ.
- Полный снимок: **1551 host + 71 config; 2106 Linux + 45 privileged + 8 worker lifecycle
  PASS**. Все 9 команд host/cross/feature/lint/format прошли; Clippy сохраняет прежнее
  исключение `chunks_exact_to_as_chunks` для различия toolchain. Проверка RU/EN-документации
  и `git diff --check` проходят. Платформенная компиляция не означает runtime-сертификацию.

локально Windows / Rust 1.98. Рабочий сервер `10.66.116.10` не использовался.

`/run`, `/var/lib`, `/var/log`, `/etc/qeli`, `/tmp`. Использованы iptables 1.8.11
(nft/legacy), nft 1.1.3 и приватный firewalld 2.3.1.

D05 остаётся **IN_PROGRESS**. Обычная очистка уже работающего TCP/UDP-туннеля,
kill-switch setup/refresh/cleanup, внутренние locks/I/O и публикация диагностических

командные бюджеты; нельзя обещать общий срок остановки по времени этого стенда.

лимит на число клиентских процессов. Изменение внешним root между проверками не имеет
обещания атомарной защиты. D06/D10/D13, benchmark и сертификация остаются открытыми.

этап не подтверждает runtime этих платформ или свежий Android-пакет.
