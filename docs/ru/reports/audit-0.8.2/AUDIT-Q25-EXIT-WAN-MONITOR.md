# Q25-F127: смена exit WAN без VPN path COMMIT

Дата: 25 сентября 2026. База: `edc70b93`. D06 остаётся **IN_PROGRESS**.

## Дефект и исправление

Exit-node обновлял WAN-зависимые MARK/NAT/FORWARD-правила только при VPN path
COMMIT. В двухканальном хосте физический путь к VPN-серверу может остаться на
WAN A, а default route для выходящего трафика смениться на WAN B. Защитный
guard блокировал такой трафик, но без COMMIT правила B не появлялись.

Linux TCP и UDP data-plane теперь запускают один монитор только для
`exit_node`. Раз в 5 секунд он получает read-only снимок активных IPv4/IPv6
default WAN и запускает существующий `refresh_exit_paths_if_active` при смене
снимка. Успех запоминается лишь после полного refresh: имя WAN записывается
в учёт очистки **до** завершения установки, поэтому частичная ошибка должна
повторяться. Старые правила остаются до teardown для текущих потоков.
Монитор принадлежит TaskGroup соединения: группа останавливает и дожидается
его сетевой операции до очистки NetworkPlan, TUN, DNS и firewall.
Обычные клиенты монитор не запускают.

Сквозной тест выявил отдельную ошибку очистки: `iptables -S` показывает
`--comment "qeli-exit-node:lockdown"` в кавычках. Проверка позиции lockdown
принимала лишь запись без кавычек и оставляла защиту включённой после
остановки (первый содержательный TCP-прогон: 34 PASS, 1 FAIL). Парсер теперь
узнаёт обе точные формы и по-прежнему отвергает ACCEPT перед lockdown.

## Проверки и границы

На изолированном сервере `.11` прошли 116/116 gateway-тестов и
`cargo fmt --check`. Реальные TCP/fake-tls и UDP/fake-tls прогоны дали по
**35 PASS, 0 FAIL**: carrier/маршрут к серверу оставался на A, exit default
менялся на B; новый MARK/NAT/permit появлялся без VPN COMMIT, consumer-трафик
шёл через B с NAT, вторичной AUTH/реконнекта не было. Clean stop удалил
правила обоих WAN и восстановил `ip_forward` и `rp_filter`.
Скрипт и финальные логи:
`C:/Users/litvi/OneDrive/Documents/qeli/audit-debt-20260925/tun-attach-context-phase/wan-monitor-e2e.sh`,
`wanmonitortcp5.log`, `wanmonitorudp3.log`. Прогоны были в частных
network/mount/PID namespaces, с отдельными `STATE_DIRECTORY` для всех
процессов. Установленные сервисы и сервер `.10` не менялись.

Монитор отслеживает default WAN по **имени** и не решает повторное
использование имени другим устройством [Q25-A125](AUDIT-Q25-WAN-NAME-REUSE.md).
Он не подменяет маршрут отдельного пакета при policy routing: off-WAN пакет
по-прежнему блокирует guard [Q25-F124](AUDIT-Q25-EXIT-POLICY-ROUTING.md).
Отсутствующий маршрут или неудачная установка оставляют блокировку и ведут к
повторной попытке на следующем тике; оператор должен проверить журнал и
маршруты, если связь не восстанавливается. Identity-bound backend и
mixed-backend recovery остаются D06/D10.
