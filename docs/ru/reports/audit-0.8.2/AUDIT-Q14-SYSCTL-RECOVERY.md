# Q14: результат восстановления sysctl и повторное получение lease

Дата: 23 сентября 2026. Исходный коммит: `66f2714d`.
Разделы 14, 17, 18 и 19: **IN_PROGRESS**.

## Подтверждённые дефекты

**Q14-F029, P2 — ложный успех восстановления stale sysctl.** Предварительный проход
`with_locked_journal` удалял умерших владельцев, пытался восстановить параметры и
сохранял неустранённые записи. Однако `recover()` затем безусловно возвращал Ok.
В результате `nat::cleanup_all()` мог пропустить неудачное восстановление при старте worker.

Теперь после сохранения журнала `recover()` проверяет оставшиеся записи без владельцев.
Они дают ошибку `could not restore stale host sysctl value(s): ...` со списком путей.
Все записи проходят предварительную попытку восстановления; сбой одной не пропускает
остальные. Журнал сохраняется до возврата ошибки и позволяет повторить попытку.
Записи с живыми владельцами не считаются неудачей восстановления.

**Q14-F030, P2 — неудачный повторный acquire удалял прежнего владельца.** Уже работающий
компонент мог повторно запросить тот же параметр. Если текущее значение отличалось от
managed и повторная запись не удавалась, rollback удалял owner, даже когда его lease
был успешно получен раньше. Поздний recovery мог восстановить original под живым компонентом.

Теперь acquire сохраняет результат вставки owner. При ошибке записи удаляется только
владелец, добавленный текущим вызовом. Ранее существовавший lease остаётся в журнале;
чужие owners также сохраняются. Для нового неудачного acquire по-прежнему остаётся пустая
запись: проверка записи могла отказать после фактического изменения значения.

## Проверка

Изолированная копия production `sysctl.rs` использует фикстуры чтения/записи sysctl,
идентичности процесса и boot-id, FileLock и атомарной записи. Алгоритмы acquire, prune,
release, recover, формата журнала и проверки владения сохранены. Сам журнал записывается
в отдельный каталог; системный `/proc` не изменяется, межпроцессный flock не проверяется.

На baseline два сценария подтверждают дефекты, два контрольных проверяют живого владельца
и внешнее изменение, ещё один проверяет грамматику журнала. После исправления **7 проверок
PASS**: исправленные сценарии, прежние контроли, сохранение чужого владельца при отказе
нового acquire и продолжение восстановления остальных записей после сбоя, плюс грамматика.
После успешного retry временный отказ больше не мешает `recover()` вернуть Ok.
Те же семь проверок на исходном коде дают три ожидаемых отказа и четыре успешных
контроля; на исправленном проходят все семь. Эти проверки не прибавляются к общей матрице проекта.
