# Q25-F111: последовательная запись диагностики вне async-потока

25 сентября 2026. База `300a6c78`. D05/D09, Linux.

## Дефект и исправление

`ClientStatusReporter::publish` создавал каталог, сериализовал снимок и выполнял
атомарную запись с fsync на async-потоке. Медленное хранилище задерживало соседние
задачи, регистрацию/обработку stop и завершение клиента. На многопоточном runtime
sampler и публикация событий могли писать параллельно: копирование состояния под
mutex не упорядочивало последующие записи, поэтому старый снимок мог затереть новый.
Ранее `client_tasks::finish` уже защищал итоговый статус от живого sampler, но не
устранял файловые блокировки или перестановку промежуточных снимков.

Теперь каждый Linux-клиент с `QELI_CLIENT_STATUS` создаёт один поток `qeli-status`.
Он наследует NET/mount-контекст вызывающего потока и последовательно выполняет I/O.
В памяти хранится не более одного выполняемого и одного ожидающего снимка; новый
ожидающий снимок заменяет предыдущий. State mutex удерживается до помещения снимка
в очередь, а файловые операции и сериализация байтов выполняются вне этого mutex.
Статус остаётся снимком текущего состояния, а не журналом всех переходов.

Владелец writer отделён от клонируемых отправителей. Обычный выход сначала прекращает
и присоединяет sampler/watchers, затем публикует terminal, закрывает очередь, ждёт её
опустошения и присоединяет writer. Отменённое ожидание `finish` сохраняет ownership и
может быть повторено. Принудительный Drop синхронно присоединяет поток, включая
оставшийся снимок; он не оставляет запись работать после освобождения владельца.
Паника writer закрывает приём и обнаруживается при join. Без пути статуса поток не
создаётся; ошибка его запуска отключает диагностику с предупреждением.

Атомарная замена, file/directory fsync и режим `0600` используют прежний общий helper.
Ошибка записи остаётся best effort: она не меняет результат VPN и не вызывает reconnect.
При отказе итоговой записи файл может содержать предыдущий статус; код выхода и журнал
нужно проверять отдельно. Schema 1, поля API и формат INI не менялись; служебный JSON
состояния сохраняется согласно согласованному контракту.

## Проверки

- **5 новых переносимых регрессий**: медленный writer и отзывчивый current-thread runtime;
  10 000 обновлений при одной ожидающей записи; terminal последним; отказ новых снимков
  после close; отмена и повтор finish; живые sender clones; join при Drop, panic и
  медленном destructor callback.
- **1 новая privileged Linux-регрессия**: worker наследует именно частные NET/mount
  namespaces вызывающего потока; namespaces основного процесса не меняются.
- **2 baseline + 4 fixed fsync-сценария** на реальном `run_client` с однопоточным runtime.
  Две контрольные проверки старого бинарника воспроизводят 0 heartbeat тиков во время
  первой и итоговой записи. Fixed даёт **7–8** тиков за интервал около 800 мс.
  Удержанная итоговая запись не позволяет клиенту вернуть результат раньше времени.
  Проверены `failed` после отказа password command, `stopped` по SIGTERM, восстановление
  публикации после EIO первой записи и сохранение старого файла при EIO итоговой записи.
  Эти сценарии заканчиваются до подключения; TCP/UDP задаются в конфиге.
- Отдельно **2 baseline + 4 fixed сценария действующего TCP/UDP-туннеля** повторяют
  существующий teardown harness: `running` → `stopped`, либо sticky `failed` при отказе
  route cleanup; **2/2 явных повторных запусков** очищают оставшийся kill-switch.
  Исходные маршруты/операторские firewall-правила восстанавливаются, TUN удалён.
- В fsync-fixture проверены приватное mount-view (исходный файл вне bind mount не
  изменён), `0600`, отсутствие незавершённых временных файлов, стабильный итоговый
  файл и отсутствие изменений сети. LD_PRELOAD загружается только в тестовый клиент.
- **1569 host + 71 config; 2133 Linux + 48 privileged + 8 lifecycle PASS**.
  Все 9 host/cross/feature/lint/format команд PASS; сохранено существующее исключение
  Clippy `chunks_exact_to_as_chunks`. RU/EN docs и diff проверены перед коммитом.
