# Q25-F106: асинхронная очистка установленного туннеля

25 сентября 2026. База `1bd60ed3`. D05/D09, Linux TCP/UDP.

## Проблема

После остановки задач соединения оба transport выполняли DNS restore, route cleanup
и восстановление forwarding синхронно в async-потоке. Задержка команды удаления
маршрута останавливала соседние задачи однопоточного runtime. Исправление setup в
Q25-F105 не затрагивало этот путь. Последовательность очистки дублировалась в TCP и UDP.

## Исправление

Оба transport вызывают общий `TunGuard::shutdown`. Один новый поток владеет TunGuard
от начала очистки до конца, включая исходный TUN descriptor, DNS lease и RouteOwner.
Он наследует и закрепляет NET/mount-контекст вызывающего потока. Порядок сохранён:

1. Worker восстанавливает DNS и передаёт уведомление ожидающей async-задаче.
2. Async-задача закрывает sender, останавливает и присоединяет TUN packet workers.
3. Тот же сетевой worker очищает свои маршруты, восстанавливает forwarding и уничтожает
   guard. Ошибка DNS не пропускает остальные стадии. Guard отключается только при
   успешной явной очистке; повтор при ошибке также выполняется на этом worker.
4. Клиент получает результат после завершения Drop и присоединения потока.

Ресурс не переносится обратно в async-задачу между стадиями. Смена namespace ожидающего
потока во время остановки pump не меняет контекст завершающей очистки. Attach-режим
сохраняет запрет удаления внешнего интерфейса и его маршрутов.

Если ожидающий future уничтожен во время работы, сначала уничтожается future остановки
pump (его Drop останавливает/присоединяет packet workers), затем закрывается продолжение
и присоединяется сетевой worker. Непродолженный worker выполняет прежний fallback guard.
Это может синхронно блокировать уничтожающий поток; отделённой сетевой мутации не остаётся.
Ошибка создания потока или получения контекста также не пропускает остановку pump.

Ошибки создания/контекста/panic worker записываются в общие Failures отдельной категорией
`network transaction`. Как и DNS/routes/forwarding, она хранит первую ошибку с лимитом
2048 Unicode-символов. Неопределённая очистка запрещает reconnect и снятие включённого
kill-switch. Успешный fallback-повтор не стирает ранее сообщённый отказ. Ошибка соединения,
включая типизированный terminal kick, сохраняется при добавлении ошибки очистки.

INI, публичный C ABI и пользовательские параметры не изменены.

## Проверки

- 5 новых переносимых тестов: отзывчивость обеих блокирующих стадий, один поток
  владения и порядок Drop, продолжение после ошибки первой стадии, panic до/после pump,
  уничтожение ожидающего future во время pump с ожиданием fallback. Два существующих
  теста Failures расширены на новую категорию, её лимит и конкурентную запись.
- 1 новый privileged-тест: смена NET/mount namespace ожидающей задачи между стадиями
  не меняет исходный контекст последующей очистки и Drop ресурса.
- Реальные подключения на однопоточном Tokio runtime: **2 baseline-воспроизведения**
  на замороженном driver предыдущего commit и **4/4 fixed PASS** — TCP/UDP × обычная
  задержка удаления маршрута / задержка с ошибкой команды. Driver запускает текущую
  библиотеку клиента, heartbeat — каждые 100 мс; это не имитация транспорта.
- До stop все 6 запусков дали по 8 тиков за 800 мс. При задержке cleanup baseline
  TCP и UDP дали **0 тиков**, fixed — **7–8 тиков**. Пока команда удерживалась,
  TUN сохранялся и kill-switch обоих семейств оставался установленным.
- Обычные fixed TCP/UDP: exit 0, статус `stopped`, точное восстановление исходных
  маршрутов и правил, без оставшихся TUN/`*.state`. При инъекции отказа: exit 1,
  статус `failed`, исходные маршруты восстановлены повтором guard, но ошибка сохранена
  и kill-switch не снят. **2/2 новых явных запуска после устранения отказа** восстановили
  сохранённое состояние firewall и завершились чисто. Ошибку не посчитали успешным stop.
- Выход после снятия задержки в fixed-сценариях занял 0,819–1,133 с. Это только наблюдение
  данного стенда, не критерий ускорения и не гарантия общего срока shutdown.
- Повторена hostname mixed-firewall матрица: IPv4 nft / IPv6 legacy без firewalld и
  IPv4 legacy / IPv6 nft с firewalld. **38/38 ячеек**, 34 crash/recovery,
  1220 основных утверждений, 806 вложенных проверок PASS. Все 1088 запрещённых UDP-проб
  дали нулевую доставку с проверкой счётчиков DROP; 656 разрешённых получили ответ.
- Полный снимок: **1556 host + 71 config; 2111 Linux + 46 privileged + 8 worker lifecycle
  PASS**. Все 9 команд host/cross/feature/lint/format прошли; сохранено прежнее исключение
  Clippy `chunks_exact_to_as_chunks`. RU/EN-документация и `git diff --check` проходят.

## Границы

Закрыт синхронный штатный путь очистки TunGuard после завершения data plane. Ранний
выход через `?`, unwind и принудительный Drop сохраняют синхронный fallback. Kill-switch
setup/refresh/cleanup, отдельные locks/I/O и публикация диагностических файлов остаются
предметом D05. Общего deadline для NetworkPlan/shutdown по-прежнему нет; запущенный
syscall не прерывается. Тайминги fixture не являются benchmark или гарантией срока.

В новых runtime-сценариях DNS выключен: реальная задержка/ошибка инъецируется на удалении
маршрута. Порядок обеих блокирующих стадий, исключения и контекст проверены unit/privileged
тестами; весь контракт DNS и прочие комбинации покрываются прежними проверками и матрицей
в пределах их отчётов. Это не отдельная новая сертификация всех DNS-backend.

D05 остаётся **IN_PROGRESS**. D06/D10/D11/D12/D13 и итоговый benchmark открыты.
Windows VM, Mac/iOS и физический роутер — **SKIPPED по решению пользователя**.
Свежий Android-пакет на этом этапе не проверяется. Новые разделы полного аудита не открыты.
