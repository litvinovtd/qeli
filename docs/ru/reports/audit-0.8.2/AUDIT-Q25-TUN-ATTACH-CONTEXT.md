# Q25-F123: контекст sysfs при TUN dev_attach

Дата: 25 сентября 2026. База: `bf95bcdf`. D06 остаётся **IN_PROGRESS**.

При переходе процесса в другой network namespace mount `/sys` может продолжать показывать
интерфейсы прежнего namespace. В приватном стенде .11 создано два TUN с именем
`qeli-audit0`: текущий link получил `ifindex=3`, унаследованный sysfs показывал
`ifindex=2` и `tun_flags=0x1801`. Ранее `TunInterface::attach` доверял этому
`tun_flags`. Если флаги двух устройств различаются, первый `TUNSETIFF` мог
передать чужой набор features текущему устройству.

Перед чтением `tun_flags` Qeli теперь запрашивает индекс имени через socket ioctl
в текущем network namespace и сверяет его с `/sys/class/net/<имя>/ifindex`.
Несовпадение даёт явную ошибку `refusing foreign tun_flags` до `TUNSETIFF`.
После разбора флагов индексы проверяются снова; обычная замена между наблюдениями
также отклоняется. Внешний менеджер должен удерживать устройство стабильным
до завершения attach.

Linux-тест создаёт mount и два network namespace только на одноразовом потоке,
проверяет успешный attach при соответствующем sysfs, затем одноимённый TUN
в другом namespace с иным индексом и отказ до открытия дополнительной очереди.
Ресурсы остаются в приватных namespace и исчезают с потоком.

Это **частичная защита**, а не доказательство namespace identity. Разные namespace
могут выдать устройствам одинаковый числовой `ifindex`; проверка не распознает
такой случай. Также остаётся гонка внешней замены между последней проверкой и
`TUNSETIFF`. Netlink не предоставляет все используемые TUN features, поэтому
простая замена чтения `tun_flags` на netlink без изменения контракта может сбросить
features. Использование `dev_attach` с унаследованным чужим sysfs не сертифицировано;
нужно предоставить sysfs текущего network namespace либо не использовать attach
в таком окружении. Процент закрытия техдолга не меняется.
