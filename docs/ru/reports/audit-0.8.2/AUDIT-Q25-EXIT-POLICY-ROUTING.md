# Q25-F124: exit-node и policy routing на другом WAN

Дата: 25 сентября 2026. База: `eab70d71`. Приоритет: P1. D06 остаётся **IN_PROGRESS**.

В `exit_node` интерфейс NAT выбирался по основной default route. Правило MARK
срабатывало только для `-i <tun> -o <выбранный-WAN>`, а MASQUERADE — только
на выбранном WAN и при наличии метки. Policy routing пересылаемых пакетов
может выбрать другой интерфейс, даже когда локальный `ip route get` и
основная default route указывают на прежний. Если FORWARD разрешает этот
пакет, он выходил без MASQUERADE с исходным адресом клиента.

Изолированная лаборатория .11 подтвердила случай на трёх network namespace.
Основная default route выбрала `wan-main`, правило `iif qeli-in lookup 100`
направило пакет через `wan-policy`. До исправления tcpdump на стороне
`wan-policy` увидел `10.0.0.2 > 203.0.113.9`; счётчики Qeli MARK и
MASQUERADE остались нулевыми.

Теперь exit-node сначала запоминает владельца WAN и устанавливает в
filter/FORWARD правило DROP для всех пакетов из своего TUN без
зарезервированной метки `0x51/0x51`. Оно получает приоритет в FORWARD; при нескольких exit-профилях может
стоять после их безопасных правил, но всегда перед собственными permit.
Существующий FORWARD-hook kill-switch для того же TUN вызывает отказ:
его цепочка способна принять пакет до защитного DROP.
NAT устанавливается до MARK, чтобы начало установки не допускало отмеченный,
но ещё не маскируемый трафик. При roaming новые permit остаются после
защитного DROP. Отсутствие обязательных правил FORWARD больше не заменяется
fallback на политику ACCEPT.
Собственный TUN переводится в up только после успешной установки защиты
для всех согласованных семейств. `dev_attach = true` отклоняется: уже поднятый
внешний интерфейс оставил бы окно до установки правил. Пустой набор
аутентифицированных IPv4/IPv6-адресов также отклоняется.

Очистка сначала ставит отдельный DROP для *всего* выхода из этого TUN:
так уже отмеченный пакет не пройдёт после удаления NAT. При любой ошибке
удаления правило lockdown остаётся для повтора. Сочетание `exit_node` с
`gateway_nat` или `forward` в одном профиле отклоняется: эти режимы требуют
разных правил для трафика из TUN.

В пакетной контрольной проверке с тем же policy route защитное правило
заблокировало пакет (счётчик DROP: 1, tcpdump не получил пакет). После
добавления `wan-policy` в набор разрешённых WAN tcpdump увидел уже
`198.51.100.2 > 203.0.113.9`, MARK и MASQUERADE сработали по одному разу.
Артефакты: `C:/Users/litvi/OneDrive/Documents/qeli/audit-debt-20260925/tun-attach-context-phase/wanpacket.log`
и `wanpacketfixed.log` в том же каталоге.

Проверка финального кода: `cargo fmt`, 111 целевых gateway-тестов,
INI-регрессии и полный Linux lib-прогон: 2182 PASS, 0 FAIL,
59 ignored. Для полного прогона лимит открытых файлов поднят с 1024 до
4096: отдельный DNS TCP-тест держит 512 клиентских и серверных сокетов
в одном процессе. Логи: `wanfinal.log`, `wanfullfinal.log` в каталоге
артефактов выше.

Граница: защитная метка зарезервирована за Qeli; внешние mangle-правила не
должны выставлять те же биты, а внешний firewall не должен ставить
опережающий ACCEPT. Трафик к другому WAN блокируется до успешного refresh.
Rename/reuse физического интерфейса и полная матрица работающего Qeli
остаются открытыми в D06.
