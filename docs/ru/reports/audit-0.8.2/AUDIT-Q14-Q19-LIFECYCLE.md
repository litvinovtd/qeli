# Аудит Q14/Q19: завершение профиля и DNS-слушатели

Дата: 23 сентября 2026. База: `7995affd`, после
[EDNS/RDATA](AUDIT-Q19-DNS-EDNS.md). Разделы 14 и 19 остаются **IN_PROGRESS**.

## Область

Проверены владение async-задачами поколения профиля, ранние ошибки запуска,
повторное/отменённое ожидание остановки, реальные UDP/TCP DNS-слушатели и
освобождение сокетов. Production `ProfileTasks` перенесён из `server/mod.rs`
в `server/tasks.rs`; те же слушатели и менеджер задач теперь доступны host-тестам.
Неиспользуемый аргумент `Arc<ServerState>` удалён из UDP-слушателя и обоих вызовов.
Новых зависимостей, параметров INI и изменений клиентского ABI нет.

## Находки

| ID | Приоритет | Условие и проблема | Исправление |
|---|---|---|---|
| Q14-F001 | P2 | NDP или IPv4 DNS уже запущены; следующий bind IPv6, firewall/DHCP setup или другой шаг возвращает ошибку. Локальные JoinSet уничтожались внутри `run_profile_generation`: abort запрашивался, но ожидания деструкторов не было. Внешний wrapper мог перейти к удалению ресурсов профиля, пока службы ещё ими владели. | Обе группы служб/слушателей принадлежат внешнему `run_profile`. После любого обычного возврата из запуска закрывается admission, отменяются и join-ятся службы, слушатели и дочерние задачи; затем удаляются registry/TUN/firewall-ресурсы. |
| Q14-F002 | P2 | Первый `ProfileTasks::shutdown` забирал все handles в локальный вектор. Второй вызов возвращался сразу; отмена первого ожидания тоже лишала последующий вызов возможности дождаться задач. | Pending handles остаются в общем JoinSet. Async mutex сериализует ожидающих, cancel-safe polling сохраняет возможность продолжить join после отмены. |

Q14-F001 найден по достижимым путям `?` после spawn. Штатная остановка в базе
уже join-ила группы: дефект относится именно к раннему возврату. Loopback-тесты
проверяют новый общий cleanup, занятый дополнительный bind и немедленное повторное
занятие портов. Полный `run_profile` с TUN/firewall на Linux здесь не запускался.

Q14-F002 воспроизведён двумя тестами на прежнем production tracker после переноса
без изменения алгоритма: оба упали с `shutdown returned before its children were dropped`.
Обычный supervisor использует один ожидающий вызов; это исправление контракта
при конкуренции/отмене, а не доказательство частого сбоя штатного stop.

При переходе на JoinSet также убраны полный обход всех живых handles на каждом
spawn и молчаливое удаление результата завершившейся задачи. Готовые задачи
собираются через очередь завершений; panic записывается в лог. Измерений ускорения нет.

## Проверки

**727 Rust unit + 52 editor/policy + 7 examples + 12 server INI = 798**, PASS.
Из unit-набора: 52 resolver, 7 listener и 7 task-ownership тестов. Добавлены 14
новых тестов; один прежний Linux-only тест перенесён в общий host-набор.

- Оба старых дефекта ожидания: конкурентные вызовы и отмена первого ожидания.
- Отмена ожидания групп служб с последующим продолжением; запрет новых детей.
- Гонка восьми производителей с shutdown: 1024 захваченных ресурса освобождены.
- Сбор завершившихся/panicked задач без сохранения старых handles.
- IPv4/IPv6 UDP, TCP pipeline и несколько обменов на одном соединении.
- 32 запроса, ожидающих cache lock, плюс неполный TCP body: stop освобождает
  ссылки и порты; соседний DNS-профиль продолжает отвечать.
- Реальный запрос к молчащему loopback upstream: после stop его wildcard UDP-порт
  можно занять повторно, не ожидая 30-секундного timeout.
- Неполные TCP prefix/body завершаются по deadline; короткий frame изолирован.
- 512 активных TCP-соединений: следующее закрывается, после disconnect место
  доступно снова. Это функциональная проверка предела, не нагрузочный бенчмарк.

Проходят 3 Python DNS-fixture теста, минимальный клиентский FFI, rustfmt, diff и
9 проверок документации. Linux all-targets Clippy проходит с исключением
`clippy::chunks_exact_to_as_chunks`; строгий запуск отдельно фиксирует прежнее
предупреждение в `qeli/src/server/ndp_proxy.rs:504` на Rust 1.98. Файл не изменялся. Linux runtime не подменяется
этой cross-compilation.

Первый вариант нового тестового стенда ошибочно использовал IP:port в `dns.upstream`:
production принимает bare IP и порт 53. Исправлены fixtures, конфигурационный
контракт сохранён. Проверка освобождения upstream повторяет его wildcard bind:
на Windows bind конкретного адреса рядом с wildcard не доказывает владение портом.
Оба промежуточных падения сохранены отдельно от регрессий исходного кода.

## Открытые проверки

Нужен Linux E2E: ошибка после NDP/IPv4 DNS spawn, rollback реальных TUN/firewall,
restart/reload/control/hook failures и изоляция соседних профилей. Принудительная
отмена самого wrapper или panic использует синхронный Drop/abort fallback и
не получает гарантию async join; этот сценарий не объявлен закрытым.

Остаются очередь TUN threads, внешняя совместимость, длительная нагрузка/RSS/fd,
DNSSEC/RRset и применение/восстановление DNS ОС. Реальная сеть ОС, внешние SSH-стенды
и неизменённые native-клиенты не использовались. Следующий проход — supervisor,
watch/control shutdown и восстановление после ошибок запуска в разделе 14.

Продолжение от 23 сентября: [Q14-F022/F023](AUDIT-Q14-H2-TASKS.md) добавляет join
серверных H2 driver/bridge и flush отказа в профиль, а также удержание pre-auth permit
до освобождения отклонённого соединения. Standalone API и остальные ограничения остаются.
