# Q25: неопределённые операции и освобождение осиротевших записей маршрутов

Дата: 23 сентября 2026. Baseline: `06759c30`.
Q25-F031/F032 исправлены в указанных ниже границах. Разделы 22/23/25 остаются **IN_PROGRESS**.

## Находки

**Q25-F031, P2 — неизвестный результат мог исчезнуть из учёта после остановки.**
Managed roaming правильно возвращал `PlatformStateUnknown`, но не сохранял отдельную
запись неопределённой операции. После фактически выполненного add с потерей результата
маршрут оставался без ownership-записи. Cleanup мог сообщить успех, последний lease —
освободить имя, а другой owner — принять маршрут как внешний и заимствовать его.
Failed replace мог потерять последнюю запись при проверке изменившихся параметров.
Восстановление ранее удалённого маршрута с недоступной последующей проверкой имело
аналогичный пробел. Право удалить такой маршрут из факта неизвестной команды не следует.

Кроме того, ошибка commit сама по себе не закрывала приём следующих операций адаптера.
До начала cleanup повторный commit мог вызвать gateway refresh. Это касается и отказа
отката известного маршрута, когда отдельной неопределённой add-операции нет.

**Q25-F032, P2 — осиротевшая запись навсегда блокировала имя даже после удаления остатка.**
Когда cleanup физического маршрута не удавался, оба interface flush проходили и последний
guard освобождался, reservation оставалась без способа повторной проверки. Даже после
внешнего удаления остатка новое подключение того же процесса всегда получало отказ.

## Исправление

Journal хранит `pending` отдельно от доказанных записей ownership. Неизвестные результаты
roaming add/replace/retirement и неподтверждённое восстановление с возможным остатком
резервируют destination. Такая запись не считается созданным Qeli маршрутом и не
авторизует delete. Другой Qeli owner не может заимствовать или заменить зарезервированный
ключ, включая эквивалентное обозначение host-префикса. Запись переживает последний lease.

Все `RouteCommitStateUnknown` из commit закрывают приём операций под общей блокировкой,
до возврата контроллеру. Повторный commit не доходит до gateway callback.
Транзакция с подтверждённым обратимым отказом продолжает прежнее поведение.

Cleanup сначала обрабатывает ранее доказанные ownership-записи по существующим
селекторам, затем проверяет pending. Только подтверждённое отсутствие снимает pending;
любой существующий маршрут, включая совпадающий и чужой, или ошибка чтения сохраняет
резервирование и выдаёт ошибку cleanup. Живой guard может повторить проверку. Успешный
повтор cleanup не оживляет закрытый owner.

Journal отдельно хранит факт освобождения последнего lease и результат interface flush.
Новое подключение может освободить старую reservation только если guard уже отсутствует,
предыдущий cleanup успешно обработал обе семьи interface flush, все записанные destinations
сейчас отсутствуют и read-only запросы IPv4/IPv6 показывают пустые маршруты интерфейса.
Проверки выполняются под operation lock, без удержания registry mutex во время команд.

Recovery ничего не удаляет, не присваивает и не восстанавливает. Присутствующий маршрут,
повреждённый/неоднозначный снимок, недоступный запрос или непустой интерфейс сохраняет
старую запись. Без cleanup или после неуспешного interface flush автоматического
освобождения нет. Новый owner получает новую идентичность: повтор имени и generation
не оживляет прежний план.

## Границы и следующий проход

Это учёт неизвестного результата и read-only освобождение доказанно отсутствующих
остатков внутри живого процесса. Journal не постоянный; crash/restart recovery,
автоматическое удаление неподтверждённого маршрута и межпроцессное владение не реализованы.
Совпадающий снимок после неизвестного результата не доказывает авторство маршрута.
Предыдущий flush gate использует существующий статус команд; перед освобождением orphan
дополнительно проверяется отсутствие маршрутов интерфейса. Живой teardown и его flush
postconditions требуют отдельной проверки.

В этом проходе pending подключён к roaming-транзакции. Initial setup carrier/exclude/
blackhole и прочие route mutations ещё требуют того же аудита потери результата.
Следующий шаг — эти setup-ветви, затем ограничение времени route/kill-switch/gateway-команд.
Общий operation lock всё ещё может удерживаться зависшей командой, теперь и read-only
orphan-проверкой. Kernel CAS, полная identity/multipath/VRF, общий gateway rollback,
Q14-F027 TUN workers/FD, native certification и полный benchmark остаются открытыми.

Предыдущий этап: [подтверждение retirement/restore](AUDIT-Q25-ROUTE-POSTCONDITIONS.md).

Продолжение: [Q25-F033/F034](AUDIT-Q25-SETUP-FLUSH.md) переносит pending-контракт
в initial setup carrier/exclude/blackhole и подтверждает постусловия interface flush.
Отрицательный статус при доказанном отсутствии больше не блокирует cleanup; отсутствующий
TUN подтверждается отдельным link inventory. Постоянный crash recovery остаётся открытым.

Продолжение D04: [Q25-F100](AUDIT-Q25-ROUTE-JOURNAL.md) добавляет постоянное владение физическими маршрутами и recovery после аварии. Описанный здесь process-local контракт дополнен durable intent/confirmed state; неопределённые операции по-прежнему не дают права удалить маршрут.
