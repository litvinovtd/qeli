## Q05-F005, P2 — неограниченные tar и потоки stdin

Структурная проверка загруженного архива уже имела лимиты, но download, чтение
архивного INI, snapshot и extraction использовали отдельные неограниченные команды.
Подача архива через stdin создавалась отдельным потоком. Дочерний процесс мог
перестать читать, бесконечно писать stdout/stderr или зависнуть, удерживая config lock.

Общий runner теперь поддерживает необязательный stdin в том же owned future, где
читаются оба выхода и ожидается процесс. Срок/ошибка вывода прекращает все три pipe
операции, затем уничтожает и reap-ит процесс. Отдельный поток подачи архива удалён.
Синхронные вызывающие стороны используют прежний joined worker с частным runtime.
Обычные сетевые команды и hooks по-прежнему получают закрытый stdin.

Download/restore получают общий бюджет подготовки **60 секунд**, включая ожидание
config lock, структурную проверку, tar и network preflight. Остаток срока передаётся
между фазами. Просроченный restore отказывается до публикации. Если публикация уже
началась, filesystem renames/prune/cleanup заканчиваются под блокировкой: таймер не
должен сам создавать половину восстановленного дерева. Ошибки I/O остаются ошибками;
атомарность всего дерева и автоматический rollback здесь не добавлены.

Вывод ограничен: portable gzip — **16 МиБ**, столько же допускает загрузка панели;
pre-restore gzip — **64 МиБ**; listing/архивный INI/extraction diagnostics — **16 МиБ**
на поток. При превышении частичный результат не используется. Полный снимок сначала
успешно собирается в ограниченный буфер, затем сохраняется атомарно с mode 0600.
Предыдущие валидные snapshots не ротируются после провала новой команды.
Структурные лимиты restore **5000 записей / 64 МиБ распакованных данных** сохранены.

Все tar-фазы используют одинаковые явные опции, `LC_ALL=C`, удалённые из окружения
`TAR_OPTIONS` и `GZIP`. Это устраняет расхождение поведения listing и extraction.
Конфигурации остаются INI; служебный формат API не менялся.

## Q05-F006, P1 — неполный rollback snapshot считался успешным

Snapshot перед заменой дерева использовал `--ignore-failed-read`. GNU tar мог
пропустить нечитаемый файл и вернуть exit 0: restore продолжался, хотя обещанной
полной копии старого состояния не было. У snapshot этот флаг удалён; неуспешный tar
останавливает restore до публикации. У portable download прежняя политика optional
файлов сохранена: обязательные runtime-зависимости проверяются по реальному архиву.

## Q05-F007, P2 — второй restore вставал в очередь

Внутренний try-lock restore брался уже после общего config lock. Второй HTTP-запрос
ждал первый, а затем выполнял ещё одно восстановление, несмотря на обещанный отказ
при конкуренции. Допуск теперь резервируется через try-lock до ожидания config lock
и переносится в blocking worker вместе с работой. Дубликат сразу получает HTTP 409,
включая случай, когда первый restore ещё ждёт другое сохранение. Отмена первого
запроса не снимает допуск с продолжающего работу worker.

## Оставшиеся границы

D05 не закрыт целиком: остальные сетевые последовательности и ожидания всё ещё
требуют общего бюджета. Filesystem/kernel I/O и kill/reap могут выйти за мягкий срок;
это не обещание жёсткого 60-секундного отклика. После старта публикации ошибки диска
могут оставить частичный результат; pre-restore snapshot сохраняет способ ручного
восстановления. Crash/ENOSPC на каждой границе публикации и полный HTTP/systemd E2E
остаются D07/D09. Ограничение compressed размера не заменяет проверку остальных
условий допустимости restore. Рабочая `/etc/qeli` стенда не изменялась.
