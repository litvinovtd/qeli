## Проверенные слои

| Слой | Контракт и результат |
|---|---|
| INI и панель | DHCP-поля сохраняет exhaustive fixture сериализатора; охвачены все 163 parser key names и три динамических семейства. IPv6-only DHCP, неправильные границы пула, нулевая аренда, слишком длинный домен и недопустимые binds отвергаются общей валидацией. Границы 63/64 direct DNS дополнительно проверены настоящим CLI. |

| Wire | Dispatch DISCOVER, REQUEST, DECLINE, RELEASE; framing OFFER/ACK/NAK, xid, MAC, адрес, gateway, mask, DNS, domain, timers. Main/overloaded streams ограничены. Padding и корректные неизвестные TLV разрешены. Повтор xid/MAC сохраняет исходный offer. |
| Владение | Общий IpPool — источник истины: fixed REQUEST не вытесняет VPN allocation. Отказ не занимает fallback-адрес. RELEASE/DECLINE требуют точных MAC и адреса владельца; REQUEST к другому server-ID остаётся без ответа. |
| Сроки | Monotonic expiry; OFFER резервирует на 30 секунд, REQUEST фиксирует срок аренды; последующий DISCOVER его не сокращает. Периодический reaper и reaping при allocation возвращают shared reservation. DECLINE исключает адрес на 600 секунд. |
| Исчерпание и блокировки | Пустые/занятые диапазоны не дают underflow и не вытесняют активные VPN-адреса. Порядок lease/decline/shared-pool locks согласован; allocation держит исключительный доступ до фиксации адреса в пуле. Unit и реальные пакеты проверяют возврат после expiry/release. |
| Мёртвый код | Production helpers используются dispatch, allocation, reaping или энкодером ответов. Wrapper поиска опций включён только в тестах и не является второй production-реализацией. |

Описание wire-полей: [RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html),
[RFC 2132](https://www.rfc-editor.org/rfc/rfc2132.html). Проверен поддерживаемый
Ethernet DHCPv4 subset Qeli; полное соответствие всем DHCP-функциям не заявляется.

## Проверки

- Четыре поведенческих теста падают на прежнем production: malformed allocation,
  MAC collision, T2 длинной аренды и переполнение DNS-length. Десять прежних
  DHCP-тестов в том же контрольном прогоне проходят.
- **2383 Linux unit PASS, 60 ignored**, строгий all-target Clippy и release-сборка
  PASS. Добавлены семь тестов: в том числе overloaded options, исчерпание пула
  при активном VPN allocation и общая валидация конфига. В DHCP-модуле проходят
  16 тестов; serializer/panel API проверяются тем же полным прогоном.
- **35 смысловых DHCP-проверок PASS** плюс 60 запросов для заполнения лимита:
  всего 95 записей. Fixture запускает настоящий server worker, открывает
  дополнительную очередь его multiqueue TAP, подаёт Ethernet/IPv4/UDP frames и
  наблюдает реальные исходящие пакеты через AF_PACKET. Покрыты broadcast из
  0.0.0.0, повтор xid/MAC, ACK/renewal, NAK, чужой RELEASE, DECLINE, quarantine,
  исчерпание, expiry, malformed input с хвостом за 1500 байт, overloaded options,
  независимые лимиты MAC, INI admission и clean stop.
- Прежний бинарник действительно отправляет OFFER на повреждённый пакет и
  принимает DHCP-конфиг с 64 DNS-адресами; исправленный отвергает оба случая.
  Ранние калибровки fixture сохранены и не выданы за успешную проверку негативных
  пакетов.
- **13 свежих authenticated IPv4 TCP VPN checks PASS** на этом кандидате. Четыре
  native target проходят независимые A/B-сборки: Windows x86_64, macOS universal2,
  Android arm64-v8a и x86_64. Канонические/клиентские копии совпадают; provenance
  соответствует текущим Rust inputs. Это компиляция, а не device E2E.

Оба рабочих сервиса лабы и хеши их исполняемых файлов сохранены. Android-сборка
сначала отказалась из-за недостаточного места; удалены только проверенные
неактивные частные unit/Clippy caches. Desktop сохраняет ранее допустимое внешнее
изменение трёх legacy firewall rules. Рабочие бинарники не заменялись; нового
бенчмарка, push или физического платформенного прогона не было.

## Границы

Аренды хранятся в памяти процесса и не переживают перезапуск профиля. Client-ID
не заменяет MAC-ключ; DHCPINFORM и внешние LAN conflict probes не реализованы.
MAC можно подделать, поэтому важна привязка сервиса к интерфейсу профиля. DHCP
отделён от выдачи адреса через VPN AUTH. TAP-проверка подтверждает настоящий
DHCP-сервис, а не клиентский DHCP daemon или установленное мобильное приложение.
Исключённые пользователем Mac/router/Windows VM runtime, 60 ignored tests и
принятое ограничение Q25-A125 WAN replacement сохраняют свою отдельную область.
