# Q25: ошибки жизненного цикла ядра должны проходить через очистку

Дата: 23 сентября 2026. Исходный коммит: `3fc5bf8b`. Разделы 14/25: **IN_PROGRESS**.

## Замечания и изменения

**Q25-F004, P2 — ошибка запуска ядра обходила очистку клиента и post_down.**
После настройки kill-switch цикл использовал `begin_connection(...)?`. Возвращённая ошибка
сразу переводила управление к финализации статуса, минуя очистку forwarding и терминальный
хук. Теперь при отказе запуска выполняются попытка остановки ядра, очистка сети и один вызов
разрешённого post_down; клиент возвращает ошибку. После неудачного begin не выполняется dial
или reconnect. Если последующая остановка ядра и очистка forwarding успешны, kill-switch
можно снять; успешная очистка не отменяет исходную ошибку запуска.

**Q25-F005, P1 — ошибка остановки ядра могла стать успешной остановкой клиента.**
Ошибки finish_connection только записывались в лог. Затем цикл мог снять kill-switch,
сообщить об успешной остановке по сигналу или перейти к reconnect. ClientCore::stop может
вернуть EventQueueFull: отмена запрашивается, но состояние и остальная очистка не завершаются
до обработки заполненной очереди вызывающей стороной. Переносимый тест заполняет реальную
очередь из двух слотов событиями Created/Connecting и подтверждает отказ stop при состоянии
Connecting. Это управляемое воспроизведение отказа API ядра, а не доказательство заполнения
штатной очереди при первом Linux-соединении или возможности вызвать отказ удалённо.

Теперь ошибка остановки терминальна и обрабатывается до веток успешного выхода по сигналу
и reconnect. Очистка gateway/exit-node всё равно выполняется; включённый kill-switch
сохраняется, пока остановка ядра и очистка forwarding не завершатся успешно. Отключённая
защита не затрагивается и не объявляется сохранённой. При нескольких ошибках диагностика
содержит причины запуска/соединения и очистки; тип первичной ошибки остаётся доступен через
downcast. Ошибка разбора событий тоже считается отказом, даже если stop уже изменил состояние:
при неподтверждённом завершении адаптера защита сохраняется консервативно.

post_down получает причину/код `core_start_failed`/`core_start` либо
`core_stop_failed`/`core_stop`. При отказе обоих этапов приоритет у stop. Пользовательские
хуки могут самостоятельно менять firewall. Новых INI-ключей, изменений ABI, безусловной
очистки в Drop или автоматического повтора core.stop нет. Сохранение защиты после crash/
SIGKILL остаётся прежним; для восстановления может потребоваться администратор.

## Проверка

Шесть новых host-регрессий: реальный отказ ядра при полной очереди и явное восстановление,
совместные ошибки core/forwarding, ошибка запуска при успешной/неудачной очистке,
выключенный kill-switch и сохранение типов первичных ошибок.

**834 host unit + 52 editor/policy + 7 examples + 12 server INI = 905 Rust tests PASS.**
Linux all-targets Clippy, client-only, server-only и minimal FFI проходят. Сохраняются прежнее
исключение chunks_exact_to_as_chunks в неизменённом ndp_proxy.rs и 23 transport dead-code
warnings в server-only. Rustfmt, diff и девять проверок документации проходят.
Материалы: C:/Users/litvi/OneDrive/Documents/qeli/client-lifecycle-audit-20260923.

Host-тесты используют реальное состояние ClientCore и подставные операции очистки сети.
Ветки Linux-адаптера проверены чтением и cross-compile; на Linux они не выполнялись. Live
firewall, VPN E2E, внешний SSH, systemd, GitHub Actions и бенчмарк не запускались.

## Что осталось

Ошибки очистки маршрутов/DNS в нижележащих guards, сроки выполнения firewall subprocesses,
Linux fault injection и владение вложенными задачами требуют дальнейшего аудита. Этот проход
не доказывает полный откат состояния ядра ОС или доступность сети после неопределённой очистки.

Продолжение: [аудит очистки TUN](AUDIT-Q25-TUN-CLEANUP.md) передаёт ошибки явной очистки и guards отката в политику остановки клиента. Live Linux E2E и полное завершение задач ещё открыты.
