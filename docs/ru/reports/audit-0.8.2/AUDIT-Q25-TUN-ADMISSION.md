# Q25: безопасный допуск и создание Linux TUN/TAP

Дата: 23 сентября 2026. База: `a380ac77`.
Q25-F054–F056 исправлены в описанных пределах; разделы 14/21/25 остаются **IN_PROGRESS**.

## Подтверждённые проблемы

**Q25-F054, P2 — неполное наблюдение разрешало удаление занятого TUN.**
`tun_fd_holders` пропускал ошибки чтения procfs, fd и fdinfo. Если список содержал
только свой PID, `reclaim_stale_tun` считал устройство собственным остатком и вызывал
удаление. Невидимый другой владелец или заимствованный дескриптор опровергают такой
вывод. Также `Path::exists` сводил ошибку наблюдения к отсутствию интерфейса.

Поиск владельцев через procfs и разрушающее восстановление удалены. Клиент проверяет
имя в network namespace вызывающего потока через `if_nametoindex`: только `ENODEV`
означает отсутствие, прочие ошибки прерывают setup.
Это соответствует [контракту if_nametoindex(3)](https://man7.org/linux/man-pages/man3/if_indextoname.3.html).

При занятом имени клиент только ждёт: максимум 120 пауз по 50 мс и повторных проверок,
то есть около 6 секунд плюс время запросов. Это относится к интерфейсу любого типа.
Исчезновение допускает попытку создания; смена наблюдаемого ifindex, ошибка проверки
или таймаут завершают setup отказом. Эта ветка не удаляет устройство, не отсоединяет
очереди и не меняет persistence. Собственный non-persistent TUN должен освободиться
после закрытия последних дескрипторов предыдущего соединения. Утечка fd теперь
остаётся видимой ошибкой, а не основанием для захвата устройства.
`dev_attach=true` требует существующий интерфейс и не запускает ожидание освобождения.

**Q25-F055, P2 — создание могло подключиться к чужому устройству.**
Между предварительной проверкой и `TUNSETIFF` мог появиться другой TUN. Без
эксклюзивного флага ioctl допускает подключение к существующему устройству.
Кроме того, multiqueue повторно передавал исходное имя: при шаблоне `tun%d` очереди
могли оказаться разными устройствами.

Общая политика открытия задаёт `IFF_TUN_EXCL` для одиночного создания TUN/TAP и первой
очереди multiqueue. Следующие очереди открываются без этого флага по фактическому имени,
возвращённому первой очередью; `IFF_MULTI_QUEUE` и `IFF_NO_PI` сохраняются.
Ошибка любой очереди освобождает уже открытые дескрипторы через RAII.
В Linux [tun.c v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/drivers/net/tun.c)
занятое имя вместе с `IFF_TUN_EXCL` даёт `EBUSY` под блокировкой rtnl; значение флага
определено в [if_tun.h](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/uapi/linux/if_tun.h).
Поэтому предварительное отсутствие имени само по себе не считается владением.

Клиент и сервер используют один Linux backend. Серверная предварительная проверка
также переведена с sysfs на запрос текущего network namespace; сервер отказывает
при занятом имени сразу. Клиентская reservation по-прежнему координирует только
участвующих клиентов и не заменяет эксклюзивное создание.
Новых INI-ключей, форматов конфигурации или изменений FFI ABI нет.

**Q25-F056, P3 — Linux-тесты примеров не собирались без server feature.**
Два обращения к `qeli::server::validate_profiles` были ограничены только ОС Linux,
хотя сам модуль требует `feature = "server"`. Дополнительный `cargo check --tests --lib`
для Linux с `--no-default-features` воспроизвёл два E0433. Условия теперь совпадают
с доступностью модуля: общие проверки INI остаются, серверная runtime-валидация
собирается только вместе с сервером. Тот же compile-check после исправления PASS.
Это проверка компиляции; Linux-тесты не исполнялись.

## Проверка и доказательства

Добавлено **20 host-тестов**: 11 для допуска/ожидания и 9 для открытия очередей.
На адаптерах прежней логики получено **7 FAIL / 4 PASS**: неполный список владельцев,
ошибки начальной и повторной проверки, смена ifindex, одиночное и multiqueue создание
поверх чужого устройства, повторное использование исходного шаблона имени.
Семь регрессионных тел после rustfmt сохранены неизменными.

Это воспроизведение на моделях control flow и kernel-open contract, а не выполнение
исходного Linux procfs/ioctl на Windows. После исправления те же тесты вызывают
production-политику; I/O, ожидание и ядро подменены. Модель ioctl использует
`AlreadyExists` для отказа; точный Linux errno не проверяется host-тестом.
Дополнительные сценарии: release на последнем опросе, таймаут, ошибка attach,
эксклюзивность только первой очереди, сохранение внешнего владельца и rollback
при частичном открытии.

Девять команд матрицы PASS: host unit, config integration, Linux all-targets Clippy,
client-only, server-only, minimal FFI, no-roaming, no-features и rustfmt.

## Ограничения и следующий этап

Реальные TUN/TAP, ioctl, netns, параллельные процессы и reconnect здесь не запускались.
Нужны Linux E2E: гонка создания, persistent/non-persistent устройство, single/multiqueue,
задержанное закрытие reader, faulted lookup, server/client conflict и отсутствие
изменений внешнего устройства после отказа.

`dev_attach` всё ещё проверяет устройство до неэксклюзивного ioctl: исчезновение
между этими действиями остаётся отдельной гонкой. Проверка identity перед cleanup
и удалением по имени также не решена этим проходом. Сам ifindex не является вечным
идентификатором; ожидание не получает права удалять даже при его совпадении.
Эксклюзивность первой очереди не сертифицирует поведение при принудительном удалении
или переименовании устройства внешним привилегированным процессом между очередями.
Шаблоны и усечение имён на границе parser/backend, блокирующее ожидание setup,
namespace inode reuse, journal file trust, deadlines и crash recovery остаются в плане.
Новый benchmark и native certification не выполнялись; полный PASS не заявляется.

Продолжение: [Q25-F057–F058](AUDIT-Q25-TUN-ATTACH.md) запрещает регистрацию нового
устройства при attach и сохраняет поддерживаемые features; VNET_HDR отклоняется.
Identity уже существующей замены, sysfs и cleanup по имени остаются открыты.
