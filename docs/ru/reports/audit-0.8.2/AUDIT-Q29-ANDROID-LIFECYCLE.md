## F277: поздний NetworkPlan после начала остановки

Отмена корутины не прерывает синхронный Builder.establish(). Обработчик проверял только activeConfig и identity ядра: между началом остановки и очисткой этих полей он мог продолжить настройку. Отдельная очистка одновременно читала/закрывала vpnInterface. При самостоятельном onDestroy флаг stopping не устанавливался. Устаревший обработчик мог менять маршруты и состояние интерфейса уже после начала остановки.

Установка/публикация NetworkPlan, startVpn, stopVpn, onRevoke, onDestroy и forceReconnect теперь используют один монитор сервиса. Отсоединение Java-дескриптора и сброс поколения также выполняются под ним. Поздний план при stopping отклоняется до логирования Auth OK и выбора сети. onDestroy устанавливает terminal stopping, сохраняя ранее записанное желание подключения для штатной redelivery.

runner.join остаётся **вне монитора**: ожидание рабочего потока не блокирует ему доступ к сервису. DISCONNECTED по-прежнему публикуется после завершения runner. Поведение системных Binder-вызовов и их максимальная задержка этой правкой не гарантируются.

## Проверки и границы

Добавлены пять instrumented-тестов с библиотекой из APK: отказ позднему плану, блокировка при входе в обработчик (а не внутри выбора сети), отказ старому/отменённому ACK, владение native-копией дескриптора, stop/free при runner, ожидающем socket protection.

Два теста вызывают production adapter на объекте сервиса с присоединённым Context через reflection; это **не** полный сценарий системного onRevoke/onDestroy. Проверка копии FD использует pipe, а не настоящий TUN. Отдельный прежний TUN-тест устанавливает split/full/dual интерфейсы Android. Отмена runner проверяется в настоящем JNI до выдачи protect ACK, без VPN-сервера и полезного трафика.

Прежние 1248 .NET результатов переиспользованы только для неизменённых managed/Swift исходников и DLL.
