## Q25-F078, P2 — частичная запись оставляла временный файл

Общий `util::write_atomic[_private]` удалял временный файл при ошибке rename,
но выход через ошибку `write_all` или `sync_all` обходил cleanup. После нехватки
места/квоты или I/O-ошибки оставались `.qeli-tmp-*`, включая фрагменты приватного
состояния. Режим 0600 сохранялся, но место и ненужные копии накапливались.

Созданный этой операцией файл теперь принадлежит guard до успешного rename.
При ошибке подготовки или unwind дескриптор закрывается до удаления файла;
ошибка удаления явно журналируется. После публикации guard отключается и не
удаляет новый destination. Удаление при SIGKILL или неисправной/недоступной
файловой системе этим guard не гарантируется.

## Q25-F079, P2 — синхронизация данных не закрепляла имя файла

После file fsync и rename функция возвращала успех без fsync родительского
каталога. Sysctl также удалял последний journal без directory fsync. Поэтому
завершённая операция не подтверждала сохранение изменения имени после crash.

На Unix каталог открывается до записи, затем выполняется file fsync → rename →
directory fsync. Удаление `sysctls.state` также синхронизирует каталог. Повторное
удаление уже отсутствующего файла повторяет fsync: предыдущая попытка могла
выполнить unlink, но не завершить синхронизацию.

Ошибка до rename оставляет прежний destination. Ошибка directory fsync после
rename возвращает `published ... persistence is uncertain`: новые данные уже
видимы, автоматического rollback нет. Для удаления сообщение аналогично.
Перед повторным сохранением конфигурации следует перечитать её и revision;
не следует трактовать любой write error как доказательство отсутствия изменения.
INI и публичные ABI не меняются. На Windows сохранено прежнее поведение
file sync/rename; гарантия Unix directory fsync на Windows не переносится.

## Проверки

- 4 новые portable-регрессии: failed rename, parent open, directory fsync после
  публикации и повторная синхронизация после уже выполненного unlink.
- Linux: дочерний процесс с `RLIMIT_FSIZE=1024` и обработкой SIGXFSZ вызывает
  настоящую частичную запись 8192 байт. Обычная и приватная запись существующего
  файла, приватная запись нового файла: старые данные сохранены, fragments отсутствуют.
  Лимит не меняется в основном test runner.
- Отдельный `LD_PRELOAD` observer в одноразовом процессе фиксирует четыре пары
  file/directory fsync. Инъекция EIO отдельно в file fsync подтверждает отсутствие
  публикации и временных файлов; EIO в directory fsync подтверждает уже опубликованные
  байты и явную ошибку неопределённой сохранности. Два дочерних теста намеренно
  завершаются 101 на unwrap; внешний проверяющий скрипт требует этот отказ и проверяет
  файлы. Это ожидаемые fault probes, не провал полного прогона.
