# Q25: подтверждение удаления и восстановления carrier-маршрутов

Дата: 23 сентября 2026. Baseline: `8eca565d`.
Q25-F029/F030 исправлены в описанных ниже границах. Разделы 22, 23 и 25 остаются **IN_PROGRESS**.

## Находки

**Q25-F029, P2 — retirement доверял статусу команды вместо состояния маршрута.**
При смене пути успешный `ip route del` или сообщение об уже отсутствующем маршруте
удаляло запись владельца без повторной проверки. Если маршрут оставался, commit
завершался с незамеченным остатком. Обратная ошибка: фактически выполненное удаление
с потерянным результатом признавалось неопределённым даже при подтверждаемом отсутствии.
Ветка «уже отсутствует» также не добавляла удалённый маршрут в список восстановления
при отказе следующего retirement.

**Q25-F030, P2 — rollback считал успешный статус доказательством восстановления.**
И откат replace, и восстановление ранее удалённых carrier-маршрутов доверяли `add/replace`.
Команда могла вернуть успех без восстановления прежнего снимка; журнал при этом
присваивал старую спецификацию, а транзакция сообщала об обычном обратимом отказе.
Потеря результата уже выполненного восстановления, наоборот, давала лишний неизвестный
исход. Чтение carrier-снимка допускало некорректный destination и lossy UTF-8, хотя
проверка ownership уже требовала корректный снимок.

Предусловие — managed Linux roaming и частичный отказ/потеря результата route-команды
либо изменение маршрута между шагами транзакции. Детерминированная модель команд
проверяет реальные функции route adapter. Она не измеряет частоту таких событий
в Linux и не доказывает атомарную защиту от внешнего оператора.

## Исправление

Перед retirement Qeli снова сверяет полный снимок с сохранённым. Уже исчезнувший
или изменённый маршрут не удаляется и не создаётся заново; устаревшее владение снимается.
После delete маршрут считается удалённым только при подтверждённом отсутствии,
независимо от exit status или I/O-ошибки. Такое удаление всегда включается в список
отката на случай отказа следующего шага. Оставшийся маршрут отклоняет commit.

Откат replace и восстановление retirement используют общий `restore_carrier_snapshot`.
Запись выполняется только в отсутствующий destination либо поверх наблюдаемого
собственного candidate. Другой наблюдаемый маршрут сохраняется. После команды
заново читается снимок и сравнивается вся последовательность токенов с прежней:
лишь точное совпадение подтверждает восстановление и возвращает прежнюю cleanup-запись.
Это работает и при потере результата команды. Ложный успех, иной снимок или ошибка
чтения не объявляются восстановлением; повторной слепой перезаписи нет.

Обычный отказ с сохранением прежнего пути допустим только после подтверждения всех
необходимых откатов и неизменности неудавшегося retirement. Иначе возвращается
`RouteCommitStateUnknown`, который контроллер передаёт как `PlatformStateUnknown`:
текущее поколение соединения должно остановиться.

Carrier и ownership используют общий `parse_route_snapshot`: строгий UTF-8, не более
одной непустой строки, корректный совпадающий destination. Неоднозначный, повреждённый
или относящийся к другому адресу вывод не становится доказательством состояния.
Убрано дублирующее хранение признака IPv6: семейство определяется по адресу.

Пользовательские INI, матрица параметров, API и ABI не изменены. Служебные JSON-артефакты
аудита не являются форматом конфигурации.

## Границы и следующий проход

Подтверждение снимка не является kernel compare-and-swap. Внешний процесс может изменить
маршрут после проверки; полной identity, multipath/VRF и семантической нормализации
всех атрибутов нет. Изменение порядка/динамических атрибутов может консервативно дать
неизвестный результат. Успешный host suite не сертифицирует несколько полных клиентов.

Неизвестный add, восстановление с недоступной последующей проверкой, осиротевшие
владельцы и crash/restart recovery остаются открытыми. После фактического восстановления
с ошибкой чтения маршрут может остаться без вновь подтверждённого владения.
Остановка поколения не доказывает удаления всех неопределённых маршрутов.
Ранее доказанная запись, если она есть, сохраняется для последующей проверки cleanup.

Следующий этап — контракт pending operations и восстановления осиротевших записей,
затем сроки route/kill-switch/gateway-команд. Registry остаётся в памяти процесса;
общая блокировка операций всё ещё может удерживаться зависшей командой.
Полный rollback gateway, Q14-F027 TUN workers/FD, Linux E2E, native certification
и новый benchmark здесь не закрыты.

Предыдущий этап: [владельцы подключений](AUDIT-Q25-ROUTE-SCOPE.md).

Продолжение: [Q25-F031/F032](AUDIT-Q25-ROUTE-PENDING.md) сохраняет отдельные pending
reservations для неопределённых roaming-операций и закрывает admission при любом
неизвестном исходе commit. После подтверждения отсутствия остатков возможно read-only
освобождение orphan в пределах процесса; постоянный crash recovery остаётся открытым.
