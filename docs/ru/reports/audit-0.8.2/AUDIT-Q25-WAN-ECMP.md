# Q25-F129: неоднозначный ECMP default WAN

Дата: 25 сентября 2026. База: `79004b0f`. D06 остаётся **IN_PROGRESS**.

В приватном Linux network namespace `ip route show default` для двухканального ECMP вывел строку `default` без `dev` и две вложенные `nexthop`-строки для `wan0` и `wan1`. Прежний parser не находил `dev` в заголовке и делал fallback `route get 1.1.1.1`: он выбрал `wan0`. Среди 64 других назначений ядро выбрало `wan0` для 36 и `wan1` для 28. Exit-node мог объявить себя готовым с правилами лишь одного WAN; guard блокировал бы часть клиентских потоков. Это дефект доступности и диагностики, не доказанная утечка адресов.
Отдельный IPv6 probe показал `default metric 1024 pref medium` с такими же
вложенными nexthop: фиксированный `route get` выбрал `wan0`, 64 назначений
распределились **36/28** между двумя WAN. Сценарий и лог: `wan-ecmp-ipv6-probe.sh`
и `wanecmpipv6c.log` в том же каталоге артефактов.

Parser теперь собирает устройства всех nexthop в каждом default route и сравнивает кандидатов минимальной метрики. Если у лучшего маршрута более одного имени интерфейса или равноприоритетные лучшие маршруты ведут к разным именам, выбор считается неоднозначным. Fallback `route get` в таком случае запрещён: он отражает только один адресный hash bucket. При меньшей метрике одного WAN более дорогой ECMP не мешает выбору; несколько nexthop через **тот же** интерфейс остаются допустимыми. Ошибки setup/monitor/refresh теперь говорят об отсутствии единственного default WAN.

Общий IPv6 gateway тоже использует этот parser для сохранения `accept_ra` перед включением forwarding. Простое сведение неоднозначности к «маршрута нет» позволило бы пропустить RA-настройку и проверку сохранения native IPv6. Поэтому выбор теперь возвращает отдельное состояние `Ambiguous`: gateway отвергает его до записи ownership и sysctl/firewall, а после включения forwarding также различает неоднозначность и исчезновение default route. LAN-only путь без default route сохраняется.

Четыре новых unit-теста выполняют IPv4 и IPv6 варианты: ECMP, равные метрики разных WAN, меньшая метрика одного WAN и одинаковый интерфейс при равных метриках. Ещё одна регрессия проверяет
ранний отказ IPv6 gateway без sysctl/firewall изменений и записи ownership. Финальная Linux-проверка `.11`: **11/11** WAN parser tests и **103/103**
gateway rollback tests, `cargo fmt --check` и
`cargo clippy --lib -- -D warnings` — PASS. Четыре исходных файла
побайтово сверены с локальными. Лог:
`C:/Users/litvi/OneDrive/Documents/qeli/audit-debt-20260925/tun-attach-context-phase/wanecmpfinal2.log`.
IPv4/IPv6 kernel probes и сценарии `wanecmpprobe.log`,
`wanecmpipv6c.log`, `wan-ecmp-probe.sh`, `wan-ecmp-ipv6-probe.sh` лежат в
том же каталоге. Установленные сервисы и сервер `.10` не изменялись.

Граница: это явный отказ в автоматическом выборе, а не полноценная поддержка ECMP через разные интерфейсы. При уже активном профиле прежние правила сохранены до cleanup; потоки через старый авторизованный WAN могут проходить, через новый — блокироваться guard. Ошибка получения `route show` всё ещё допускает fallback `route get`; индивидуальные policy routes и повторное использование имени WAN остаются отдельными границами D06/D10.
