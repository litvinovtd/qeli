## Находки и изменения

**Q25-F025, P2 — журнал по одному destination позволял удалить или перезаписать заменённый маршрут.**
При создании физических carrier/exclude routes записывалась команда `route del <destination>`
без установленного gateway/interface. Roaming доверял записи по destination; cleanup мог
удалить последующую замену администратора, а rollback — перезаписать её.

Журнал в памяти теперь сохраняет спецификацию удаления из успешной команды установки:
переданные gateway, device, source и остальные аргументы. Успешный roaming обновляет
запись по ключу family/type/destination; rollback возвращает прежнюю спецификацию.
Legacy setup также сохраняет известные gateway/device. Для blackhole сохраняется тип.

Перед заменой или retirement существующего carrier адаптер сравнивает известные параметры
владения с наблюдаемым маршрутом. Несовпадение удаляет устаревшую запись: конфликтующий
чужой маршрут блокирует replace, чужой маршрут не удаляется при retirement.
Rollback читает текущее состояние перед восстановлением. Наблюдаемая чужая замена
сохраняется, а результат становится unknown state. Отсутствующий маршрут восстанавливается
через `add`, чтобы не перезаписать безусловно маршрут, появившийся после проверки.

Сравниваются destination/type, переданные `via/dev/src/metric/proto` и отсутствие `via`
для direct route. Это не полная identity ядра и не атомарный маркер владения.
Добавленные ядром значения по умолчанию не считаются запрошенными параметрами.

**Q25-F026, P2 — cleanup забывал ownership только по exit status или тексту ошибки.**
Успех delete и сообщение «уже отсутствует» прежде удаляли запись без проверки таблицы.
Обратно, I/O-ошибка сохраняла её даже после фактически выполненного удаления.
Теперь cleanup читает `route show exact <destination>` до удаления и после него.
Отсутствующий маршрут не удаляется повторно; изменённая identity сохраняется.
Оставшийся совпадающий маршрут, недоступный/повреждённый снимок или несколько непустых
строк дают ошибку и сохраняют спецификацию для retry. Подтверждённое отсутствие позволяет
закончить очистку даже после потери результата delete. Обе попытки flush TUN-family
по-прежнему выполняются.

Общий helper удаления используется и для rollback добавленных candidate routes.
Восстановление replacement/retirement обновляет спецификации журнала после успеха.
Команды пока используют прежний runner: сроки выполнения здесь не добавлены.
Пользовательские INI, API и ABI не изменены.

## Семантика ядра и границы

Поведение interface/gateway selectors в fixture сверено с первичными исходниками:
[Linux 6.12 IPv4 fib_nh_match](https://github.com/torvalds/linux/blob/v6.12/net/ipv4/fib_semantics.c#L823)
и [IPv6 ip6_route_del](https://github.com/torvalds/linux/blob/v6.12/net/ipv6/route.c#L3786).
Это чтение исходников, не запуск на поддерживаемых роутерах/ядрах.
IPv6 delete не сопоставляет preferred source так же, как IPv4; непереданные поля и
маршруты с nexthop object также ограничивают гарантии. Поэтому снимок плюс уточнённое
удаление не образуют общую атомарную compare-and-swap транзакцию.

Остаются конкурентные изменения после проверки (особенно replace), полная identity,
multipath/VRF, проверка результата retirement/restore, pending operations с неизвестным
результатом и постоянный recovery journal. Журнал всё ещё общий для процесса, без
владельца TUN/generation; пересекающиеся профили и устаревшая очистка требуют отдельного
исправления. Неопределённый add по-прежнему не присваивается вслепую.

Сроки отдельных команд и всей операции не ограничены. Реальные Linux TUN/firewall/
handover, crash/restart, устройства, native release и новый benchmark не запускались.
