# Q25: начальная установка физических маршрутов и подтверждённый flush

Дата: 23 сентября 2026. Baseline: `78f74e14`.
Q25-F033/F034 исправлены в описанных границах. Разделы 22/23/25 остаются **IN_PROGRESS**.

## Находки

**Q25-F033, P2 — initial setup терял неизвестный результат и доверял ложному успеху.**
Carrier pin, exclude и blackhole записывали ownership только по успешному статусу
`ip route add`. Выполненная команда с потерянным/отрицательным результатом оставляла
маршрут без записи и позволяла cleanup сообщить успех. Обратный случай — успешный
статус без установки маршрута — объявлял setup успешным и создавал недоказанную запись.
Эти ветви не использовали pending-контракт, ранее добавленный для roaming.

**Q25-F034, P2 — interface flush не проверял фактическое отсутствие маршрутов.**
Успех или диагностическая строка «интерфейс отсутствует» считались завершённой очисткой
даже при оставшихся маршрутах. Потеря результата выполненного flush, напротив,
оставляла ошибку при фактически пустом состоянии. После удаления TUN повторный route
query может вернуть ошибку: её нельзя считать ни доказательством наличия, ни доказательством
отсутствия устройства без отдельной проверки.

Восемь регрессий воспроизвели обе группы ошибок на исходном production-коде.
Модель команд дополнена настоящими эффектами flush по семье и интерфейсу;
реальные ip/firewall-команды на хосте не выполнялись.

## Исправление

`install_physical_route` объединяет carrier, exclude и blackhole. До записи проверяется
чужое Qeli ownership/pending и читается строгий exact-снимок destination. Совпадающий
существующий маршрут используется без add и без нового ownership; конфликт отклоняется
до изменения. Недоступный/повреждённый/неоднозначный снимок также предотвращает запись.

После add всегда читается новый снимок. Только успешный статус вместе с совпадающими
параметрами подтверждает новую ownership-запись. Отсутствие после команды отклоняет
setup без присвоения. Существующий неподтверждённый маршрут или невозможность проверки
записывается в pending, закрывает приём операций owner и требует ошибки setup.
Даже `File exists` после подтверждённого начального отсутствия не разрешает заимствовать
внезапно появившийся маршрут. В pending нет права delete; совпадение параметров после
потери результата не доказывает авторство.

Удалены три отдельных реализации проверки результата add. Initial setup больше
не использует для этих ветвей слабую проверку подстрок и отдельные прямые route-show
команды. Pending доступен и в сборке без experimental roaming.
Другие функции добавления TUN/pushed/local routes этим helper не заменялись.

Cleanup выполняет IPv4 и IPv6 flush независимо, затем для каждой семьи подтверждает
пустой `route show dev`. Ошибка одной семьи не пропускает другую. Статус команды или
I/O-ошибка сами по себе не определяют итог: подтверждённое пустое состояние допускает
успех, оставшийся маршрут либо ошибка проверки сохраняет неуспешную очистку.

После отрицательного результата route-query Qeli дополнительно выполняет read-only
`ip -o link show`. Только успешный корректный UTF-8 список, в котором нет точного имени
интерфейса (с учётом суффикса `@peer`), подтверждает исчезнувший TUN. Похожее имя не
считается совпадением. Ошибка выполнения/I/O, повреждённый список или найденный интерфейс
не разрешают очистку. При I/O-ошибке самого route-query результат остаётся непроверенным.

Эта проверка общая для cleanup и освобождения orphan. `interface_flushed` теперь означает
подтверждённое постусловие обеих семей. Повтор после удаления TUN не требует слепо
принимать сообщение `Cannot find device`. Сопоставление таких строк оставлено только
в Linux test fixtures, не в production-классификации результата cleanup.

## Проверки

**8/8 целевых baseline tests FAIL → 8/8 PASS после исправления.** Ещё 12 контролей:
успешные add/cleanup для трёх ветвей и обеих семей, существующий операторский маршрут,
конфликт и on-link/via, гонка `File exists`, invalid UTF-8/неоднозначный/чужой снимок,

невалидный link inventory и ошибка flush при уже пустом состоянии.

server-only, client без roaming, minimal FFI, compatibility без features, rustfmt.

## Границы и следующий проход

Нет атомарного kernel CAS и доказательства авторства при внешней гонке. Проверка работает
в обычном контексте route show/flush без расширения на произвольные policy tables,
VRF и multipath. Link inventory проверяет структуру идентификатора и имени, а не все
атрибуты устройства. Journal остаётся в памяти; crash/restart recovery не добавлен.

Следующий этап — сроки и ограничения вывода route/kill-switch/gateway-команд с сохранением
pending-контракта. Общий operation mutex всё ещё может удерживаться зависшим процессом.
Другие TUN/pushed/local route paths, общий gateway rollback, Q14-F027 TUN workers/FD,
межпроцессная изоляция и Q05 preflight deadline/async waits остаются в плане.
Реальные Linux E2E, native certification, устройства и новый benchmark не запускались.
Пользовательские INI, API и ABI не изменены.

Предыдущий этап: [pending и orphan](AUDIT-Q25-ROUTE-PENDING.md).
