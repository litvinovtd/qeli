# Q25-F135: отказ NAT auto-WAN при неполном списке default routes

25 сентября 2026. База: `fcdc7f72`. D06 остаётся **IN_PROGRESS**.

## Дефект и исправление

После Q25-F132 сервер отклонял видимый ECMP, но при ошибке либо непригодном
выводе `ip route show default` переходил к `ip route get` для одного
фиксированного адреса. Этот ответ представляет только один ECMP hash bucket.
NAT44 или NAT66 могли запуститься с MASQUERADE для одного WAN, даже когда
другие адреса выходят через другой интерфейс.

Автоматический WAN для **NAT44 и NAT66** теперь требует успешного
`route show default` и одного пригодного выбранного интерфейса. Ошибка
команды, пустой/непригодный список и наблюдаемая неоднозначность дают отказ
до включения forwarding и установки правил. `route` и `manual` сохраняют
прежний `route get` fallback: LAN-only и policy-routed IPv6 маршрутизация
не обязана иметь default route. Явно заданный WAN остаётся ответственностью
администратора; историческое IPv4 значение `eth0` означает auto даже при
записи в INI, поэтому его нельзя использовать как явный override.

Clippy, сборка. Два новых unit-теста проверяют пустой, повреждённый и

## Отдельная подтверждённая граница NAT44

Пакетный тест с `FORWARD ACCEPT` и двумя выходными сетями доказал: адрес
`10.73.0.2` достигает чужого публичного WAN **без MASQUERADE**, но тот же
исходный адрес должен проходить к LAN `10.50.0.0/24` за сервером. Пробное
безусловное `-i <tun> ! -o <wan> -j DROP` заблокировало **оба** пути;
выбранный WAN продолжал NAT44. Поэтому правило NAT66 нельзя переносить
на NAT44 без определения исключений для server-side LAN. Это не закрыто
данным коммитом. Остаются также явный/policy WAN, изменение маршрута во
время работы, повторное использование имени и mixed backend D06/D10.
