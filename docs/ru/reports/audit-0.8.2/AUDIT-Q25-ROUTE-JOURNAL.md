# Q25: восстановление физических маршрутов клиента после аварии

Дата: 24 сентября 2026. Baseline: `9b650ed6`.
Q25-F100 исправлен в описанных пределах. D04 остаётся **IN_PROGRESS**.

## Находка

**Q25-F100, P2 — после SIGKILL терялось владение физическими маршрутами.**
При закрытии последнего дескриптора непостоянный TUN исчезал, но carrier bypass,
exclude и blackhole оставались в ядре. Новый процесс считал подходящие записи чужими
и использовал их без права удаления. После повторного подключения и штатного stop
обходной маршрут и блокировка IPv6 могли оставаться на хосте.

Настоящий baseline-бинарник с handshake и трафиком дал **18 PASS, 3 FAIL**:
остались carrier bypass и IPv6 blackhole, прямой IPv6 после stop не восстановился.
Повторное подключение при этом работало: успешный reconnect сам по себе не доказывал
очистку состояния. Проверялся TCP fake-tls outer IPv4 / inner IPv4, полный туннель.

## Исправление

Linux managed-клиент использует `/var/lib/qeli/client-routes.state` и стабильный
`client-routes.state.lock`. Каталог закреплён открытым дескриптором; проверяются
владельцы, права, отсутствие symlink, размер и структура файла. Каждая операция
маршрутов держит общую межпроцессную блокировку. Публикация файла атомарная с fsync
данных и каталога. Лимиты: 8 MiB, 128 групп, 8192 записей суммарно.

Группа определяется boot ID, `SO_NETNS_COOKIE` и именем TUN. Абстрактный сокет
`qeli.client.routes:<tun>` не даёт второму живому владельцу занять тот же TUN в той же
сети даже через другой state path. Владение физическим destination между разными
TUN проверяется по общему журналу до использования/изменения. Для этого все клиенты
в одной сети должны видеть один доверенный `/var/lib/qeli` и его lock.

Перед add/replace сохраняется intent. Подтверждённое ownership записывается только
после успешной команды и свежей точной проверки маршрута. Ошибка журнала прекращает
приём новых операций; roaming получает terminal/unknown-state ошибку, включая отказ
записи после удаления старого пути. RAM сохраняет доказанное владение до успешного
сохранения результата cleanup, поэтому очистку можно повторить после устранения I/O
ошибки. Незавершённый intent не превращается в право удалить маршрут.

При старте recovery выполняется до DNS resolution/handshake и повторно перед
созданием managed TUN. Для текущей группы требуется отсутствие TUN; существующий
или persistent интерфейс не удаляется и не присваивается. У подтверждённых записей
сравниваются все поддержанные явные и неявные атрибуты; операторская замена сохраняется.
Неуспешные удаления остаются в журнале, успешные освобождаются по отдельности.
Pending-запись снимается только после подтверждённого отсутствия destination.

Из файла допускаются только проверенные точные main-table unicast/blackhole
спецификации; произвольные команды, чужие таблицы/протоколы и неподдержанные атрибуты
не исполняются. Группы другого namespace/TUN сохраняются. После смены boot ID старые
валидные записи сбрасываются без команд; повреждённый файл не маскируется перезагрузкой.
Пустой журнал и lock после штатной очистки нормальны. TUN-маршруты не записываются
в постоянный журнал; существующее descriptor-based управление TUN не меняется.
Attach не включает управление физическими маршрутами. Конфиги остаются **INI**;
формат внутреннего state не является пользовательским конфигом. ABI/протокол не менялись.

## Границы и следующий шаг

Это recovery при следующем запуске, а не автоматическая очистка сразу после аварии.
При SIGKILL между командой и подтверждением остаётся pending: нужна ручная проверка,
а не безусловный retry/delete. Проверка таблицы и команда не атомарны; идентичное
воссоздание другим root не различается. Старые бинарники без журнала и разные mount
views одного `/var/lib/qeli` не участвуют в общем владении. Нельзя переносить файл
в другую сеть, переписывать cookie/boot или удалять lock для обхода отказа.

Командный/lock deadline 15 секунд не прерывает внутренний filesystem I/O. Длительный
churn, рост чужих групп и финальные release-измерения остаются D13/D14. Legacy global
DNS, live persistent TUN recovery и полная mixed nft/firewalld матрица остаются D04.
Общий статус долга: **3/15 DONE, 10 IN_PROGRESS, 2 TODO (20% по закрытым группам)**.
Проверки выполнялись в приватных namespaces `.11`; `.10` не изменялся.
Windows VM/Mac/iOS/router runtime остаются SKIPPED по решению пользователя.
