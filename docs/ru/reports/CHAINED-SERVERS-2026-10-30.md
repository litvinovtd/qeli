# C → A → B: квалификация цепочки Linux, 30 октября 2026

Статус: проверка завершена. Пройдены 168 проверок основной серии r08, включая
20 циклов отказов, реальные reboot A/B и 30 минут смешанной нагрузки. VM300/301
восстановлены; первоначальный строгий cleanup FAIL из-за сброшенного при reboot
qdisc не переписан — точное восстановление и повторная сверка записаны отдельно.
Это датированная инженерная проверка, не публикация релиза.

Практическая инструкция: [цепочка серверов в четыре действия](../scenarios/CHAINED-SERVERS.md),
с вводными данными и разделом автозагрузки. Этот отчёт проверял вариант с отдельным
лабораторным наблюдателем. Перенос сетевых действий в INI проверен
[отдельной серией](CHAINED-SERVERS-HOOKS-2026-10-30.md); результаты не смешиваются.

## Что проверяется и чем

- A действительно достигает T напрямую; C до VPN имеет рабочий маршрутизируемый
  внешний ULA IPv6. Добавлен отдельный /128 route к loopback T, NDP не предполагается.
- Внешние header-only observers на T/router видят WAN A и WAN C. Положительные
  контроли фиксируют прямые пакеты. Они не перезапускаются при reboot A/B.
- В A ранний iptables/ip6tables mangle/FORWARD guard плюс policy table 208 с
  постоянным blackhole; watcher восстанавливает route по имени нового TUN.
- На C native kill-switch дополнен namespace platform OUTPUT guard. DNS задан
  через namespace resolv.conf **и** NSS hosts files/dns, а не host resolved socket.
- HTTP peer, 2 MiB файл с SHA, DNS UDP/TCP, обычный getent, C/C2, частный no-NAT
  путь и header-only captures на A-in/A-out/B-tun/T проверяются независимо.

Использованы штатные iptables/ip6tables v1.8.11 с backend nf_tables; прямых команд
nft в r06–r08 нет, alternatives не менялись. Название backend не означает вызов nft.

## Три функциональных повтора

Окна по 5 секунд, offered 20 Мбит/с, TCP P1; UDP payload 1200. Это проверка доставки
с ограниченной нагрузкой, **не поиск максимальной скорости**. Upload: C→T; download: T→C.

| Повтор | TCP up / down, Мбит/с | TCP retrans up / down | UDP up / down, Мбит/с | UDP loss up / down |
| --- | --- | --- | --- | --- |
| 1 | 20,03 / 20,13 | 7 / 4 | 19,92 / 20,02 | 0% / 0% |
| 2 | 20,05 / 20,13 | 1 / 5 | 19,90 / 20,02 | 0% / 0% |
| 3 | 20,03 / 20,13 | 1 / 0 | 19,91 / 20,01 | 0% / 0% |

Во всех трёх повторах: HTTP видит WAN B; частная цель видит настоящий C; DNS обеих
транспортных форм и getent успешны; SHA файла совпадает; ответы обоим пользователям
правильные. Captures показывают source C на обоих TUN A и TUN B, source B на WAN T.
Capture drops этих четырёх observers равны нулю. После подключения внешний IPv6
блокируется; внутренний IPv6-forwarding не тестировался. TCP retrans не нулевые;
их причины и TUN drops этот функциональный тест не локализует.

## Отказы и перезагрузки

По четыре цикла каждого вида, всего 20. Во время каждого отказа первый C→A
пингуется, T недоступен; после снятия отказа связь возвращается без ручного route add.

| Отказ | Циклы | От внесения отказа до успешного HTTP, с |
| --- | --- | --- |
| Блокировка транспорта A→B | 4 | 1,43–2,46 |
| Остановка upstream A | 4 | 3,22–6,77 |
| Удаление рабочего route при приостановленном watcher | 4 | 1,49–1,52 |
| SIGKILL upstream A | 4 | 5,56–6,91 |
| Остановка/старт сервера B | 4 | 4,31–4,35 |

При stop/crash/B restart подтверждён новый ifindex qeli-out. Отдельно пройдены
остановленный watcher + удалённый route и удаление самой policy rule: последующее
падение в main блокируется firewall. Это разные уровни защиты, не один неуспешный curl.

Настоящий reboot A: восстановление за **23,78 с**; B: **24,93 с**; в обоих случаях
boot ID изменился. C/T не перезагружались, observers T оставались active.
Эти времена включают внесение отказа, заданные паузы, service restart и проверку HTTP;
это не чистое время handshake или гарантированный SLA.

## Длинная фаза и восстановление

Два длинных соединения завершились, полные raw iperf JSON и systemd journal
подтверждают фактическую длительность:

| Нагрузка | Длительность, с | Receiver goodput, Мбит/с | Потери / retransmits |
| --- | --- | --- | --- |
| TCP upload C, offered 20 Мбит/с | 1800,017 | 20,000 | 237 TCP retransmits |
| UDP download C2, offered 10 Мбит/с | 1800,001 | 10,000 | 0% по отчёту receiver, 0 lost из 1 874 988 |

Последний UDP jitter iperf — 1,436 мс: это агрегат iperf, **не** p95/p99 задержки.
Sender/receiver завершили окна в разные моменты; их packet totals не следует
подменять одним общим счётчиком потерь. Максимальная скорость не измерялась.

В устойчивой длинной фазе **8024** новых HTTP-наблюдения: все успешны и все видят B;
все её DNS UDP/TCP-пробы успешны. За весь журнал — 8509 HTTP-наблюдений, 8393 успеха
и 116 отказов во время намеренных отказов/перезагрузок, не скрытых из raw.
Оба внешних observers работали примерно **2013,9 с**, включая fault/reboot interval:
**0 прямых T-пакетов и 0 capture drops** на каждом. Положительные контроли до этого
были ненулевыми. Это основание вывода об отсутствии измеренного обхода к T.

Успешно завершённые transient-units systemd удаляет. Поэтому их поздний
`ExecMainStatus=0` сам по себе не использован как единственное доказательство:
дополнительно проверены полный JSON, реальные 1800 секунд и journal успешного выхода.

После reboot B прежний runtime-only `fq` eth1 сменился на boot default `fq_codel`.
Это единственная разница строгого initial cleanup, оставленного со статусом FAIL.
Полный сохранённый tc snapshot предыдущего опыта с тем же исходным boot ID позволил
вернуть **fq handle 8001:, limit 10000, flow_limit 100** и все остальные options;
повторный JSON tc совпал полностью. Это восстановление **после** теста, не подбор
скорости; длинная фаза после reboot шла с загрузочным qdisc, что исключает её
интерпретацию как чистого скоростного A/B.

Повторная сверка всех четырёх ВМ: адреса/интерфейсы, routes IPv4/IPv6, rules,
iptables/ip6tables, forwarding/rp_filter и состояния штатных служб совпали с исходными
(кроме ожидаемых boot IDs и динамических lifetimes/ifindex). Тестовых namespaces,
lease locks и установленных qcf-units нет. SHA raw-копий A/B/C и исходного dist
не изменился. Старые бинарники и результаты не перезаписывались.

Дополнительно проверены helpers первоначального лабораторного варианта в одноразовых namespaces
на C: повторная установка, отказ readiness без policy rule, отказ на чужую цепочку,
точечный rollback и NAT start/stop без удаления контрольного чужого правила.
Синтаксис/зависимости systemd проверены на копиях с существующими executable paths
(не отдельный production-deploy/reboot этих шаблонов). Пять portable unit-тестов
[helpers](../../../scripts/test_qeli_chain_helpers.py) и девять проверок docs прошли.

## Первичные отказы сохранены

До r08 были ошибки подготовки/сборщика, не замаскированные повторными окнами:

| Попытка | Причина и исправление |
| --- | --- |
| sandbox 01/02 | Ошибочный путь runner; затем отсутствующий IPv6 /128 route на underlay, до Qeli |
| r01/r02 | Ошибки синтаксиса раннего firewall-варианта; далее по указанию пользователя только iptables/ip6tables |
| r03 | Недостаточно приватный родитель control socket и преждевременная проверка readiness |

| r06 | UDP DNS fixture с wildcard bind отвечал не с адреса назначения; точный bind исправлен, iperf также привязан явно |
| r07 | NSS обращался к host resolved через Unix socket; добавлен namespace nsswitch hosts files/dns |

Raw каждой попытки и результаты её cleanup сохранены отдельно, старые FAIL не
переписаны. Ни одна из этих ошибок сама по себе не доказывает регрессию бинарника.

## Raw и границы вывода

На каждой из A/B/C/T raw текущей серии лежит в `/opt/qeli-chain-e2e-20261030-r08`:
точная копия бинарника A/B/C, controller/helper и SHA исходников, приватные конфиги,
runtime logs, raw iperf JSON, header-only PCAP с counters, журнал HTTP/DNS-проб,
before/after snapshots и systemd journals. r01–r07 лежат в соседних отдельных каталогах.
Приватные конфиги/identity и большие raw в публичные документы не копируются.

В raw добавлены qualification-result.json, final-evidence.json и отдельный
restoration-followup.json; проверка примеров — в подкаталоге manual-validation на C.
[Компактные данные](../../data/chained_servers_2026-10-30.json) сохраняют числа,
168 checks и provenance исходного FAIL без приватных конфигов.

Отчёт относится к контролируемым T-целям, одному внешнему транспорту и root-командам
в изолированных namespaces. Не проверены произвольные host DNS/IPC API приложений,
non-root apps, reboot C, реальный Интернет, все 12 профилей или максимальный throughput.
Лабораторные systemd-шаблоны сохраняются как материалы этого опыта, но не являются
зависимостью актуального мануала. Его раздел автозагрузки ссылается на отдельные
проверки INI-хуков: 17 сценариев запуска и восстановления без дублей. Чужие firewall/сетевые менеджеры требуют
отдельной приёмки. Данные этого отчёта не менялись после редактирования инструкции.
